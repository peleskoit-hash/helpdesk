## 1. Главный принцип: задача состоит из трёх сущностей

Внутренняя задача — **не отдельный тип Ticket**. Настройка и история создаваемых экземпляров хранятся отдельно, а работа исполнителя происходит через стандартный механизм задач ES DESK.

| Сущность | За что отвечает | Ключевые связи и ограничения |
|---|---|---|
| `InternalTaskDefinition` | Шаблон, кто создал, кому назначать, дедлайн, способ запуска и расписание, состояние | `id`, `company_id`, `creator_admin_id`, `responsible_admin_id`, `schedule_kind`, `state`, `generation_not_before_utc` |
| `InternalTaskOccurrence` | **Факт одного запуска** и неизменяемый для данного запуска снимок параметров | `definition_id`, точное `occurrence_at_utc`, `ticket_id`; пара `(definition_id, occurrence_at_utc)` уникальна по декларации модели/схемы |
| `Ticket` | Реальное задание сотруднику, переписка, назначение, смена статусов, закрытие | `workflow_type=task`, `task_kind=normal`, `intake_state=ready`, технический клиент «Система»; связь по `InternalTaskOccurrence.ticket_id` |

Схема взаимодействия:

1. Администратор создаёт определение (`Definition`) — немедленное, отложенное или повторяющееся.
2. Немедленный API или планировщик выбирает **конкретный UTC-момент** запуска.
3. Сервис `materialize_internal_task()` создаёт `Occurrence`, обычный `Ticket`, номер и начальные сообщения; выполняет назначение.
4. Агент/стажёр обрабатывает `Ticket` обычными средствами staff-интерфейса.
5. При штатном завершении при выполнении условий отправляется **сотрудническое** уведомление ответственному администратору, но не клиентское сообщение техническому клиенту.

`Occurrence` — принципиальная граница идемпотентности и сохранности истории. Она хранит `title_snapshot`, `description_snapshot`, `creator_admin_id`, `responsible_admin_id`, `display_author`, `effective_assignment_mode`, `effective_assignee_user_id`, `notify_on_completion`, `deadline_at_utc`, `materialized_at_utc`. При редактировании `Definition` ранее созданные снимки не переписываются. При этом **текущий исполнитель** читается отдельно из `Ticket.assignee_id`: он может измениться после запуска и не обязан совпадать с `effective_assignee_user_id`.

**Важная деталь БД:** в исследованной декларации `InternalTaskOccurrence.ticket_id` — уникальный идентификатор без FK на `tickets.id`. Поэтому сохранение маркера после hard delete допустимо в текущей модели, но наличие маркера само по себе **не доказывает наличие Ticket**. Реальные индексы конкретной legacy БД на этом шаге не сверялись.

## 2. Технический клиент, автор и начальная карточка

`_technical_internal_client()` ищет или создаёт для каждой компании одного клиента с именем **«Система»**:

- ID вычисляется детерминированно как `uuid5` от постоянного namespace и `company_id`, а не генерируется заново на каждый запуск.
- При существующем техническом клиенте имя приводится к «Система».
- При создании на PostgreSQL используется `pg_advisory_xact_lock(hashtext('internal_task_client:<company_id>'))`, чтобы сериализовать именно эту операцию внутри транзакции. На SQLite этот lock отсутствует; он **не является глобальной блокировкой всего планировщика**.
- `Ticket.client_id` всегда ссылается на технического клиента, независимо от того, показывать ли сотруднику реального автора.

При материализации создаётся `Ticket` с `status=unassigned`, `agent_visible=true`, `load_counted=true`, `is_frozen=false`. Сервис выдаёт `ticket_number`, пишет видимое system-сообщение вида «Внутренняя задача создана: …» и одно начальное сообщение `message_type=client`, автор `null`, с описанием. Если дедлайн задан, к описанию добавляется строка **«Дедлайн: ДД.ММ.ГГГГ ЧЧ:ММ»** с конвертацией из UTC в `settings.app_timezone`.

`display_author=true` меняет **показанное** имя заявителя в списке и карточке внутренней задачи на ФИО администратора-автора; `false` показывает «Система». Тест `test_internal_task_ticket_display_author_overrides_visible_requester_only_for_internal_tasks` проверяет оба варианта и то, что обычная заявка продолжает показывать обычного клиента. Это **не** изменение `Ticket.client_id` и **не** изменение прав доступа.

## 3. Три способа создания и состояния

| Способ | `schedule_kind` | Создаёт `Ticket` сразу? | Состояние определения после создания / запуска |
|---|---|---|---|
| «Создать сейчас» | `immediate` | Да, в транзакции POST | `active` → `finished` в той же транзакции |
| «Создать к дате» | `scheduled` | Нет; сначала только шаблон | `active` до успешного запуска → `finished` |
| «Повторять» | `recurring` | Нет; каждый подходящий момент даёт новый экземпляр | `active`, возможен `paused`; после исчерпания лимита/окончания — `finished`; при удалении — `disabled` |

**Статус `Definition` ≠ статус выполнения `Ticket`.** Например, одноразовое определение уже `finished`, хотя сотрудник ещё работает над `Ticket` со статусом `new/pending/unassigned`; повторяющееся определение может оставаться `active`, хотя один или многие его экземпляры уже `closed`.

Немедленный запрос `POST /api/v1/management/internal-tasks` создаёт `Definition` и вызывает материализацию в **одной транзакции**. Если материализация падает, обработчик откатывает определение, `Occurrence` и `Ticket`; этот сценарий отдельно описан тестом `test_create_now_rolls_back_definition_when_materialization_fails`. Внешнего request-idempotency-key нет: **два одинаковых POST создают две разные внутренние задачи** (`test_create_now_has_no_external_idempotency`).

Отложенный POST только сохраняет `Definition` с будущим `scheduled_for_utc`; тесты прямо проверяют отсутствие новых `Occurrence`/`Ticket` в момент сохранения. Повторяющийся POST аналогично создаёт расписание, а не немедленное задание.

### 3.1. Два режима назначения

| Настройка `Definition` | Проверки при сохранении API | Поведение в момент **материализации** |
|---|---|---|
| `direct` | Обязателен `assignee_user_id` сотрудника **той же компании** с ролью `agent` или `trainee`; API не отвергает его лишь за `is_active=false`/offline | Если сотрудник существует, активен, роль и компания подходят — назначить напрямую **даже offline**. Иначе экземпляр переключается на `distribution`, **исходный `Definition` остаётся `direct`** |
| `distribution` | `assignee_user_id` должен быть `null` | `choose_online_agent()` выбирает доступного online-агента по существующей логике назначения; если никого нет, задание остаётся `unassigned`, добавляется system-сообщение «На распределении» |

При автоматическом распределении значение `Occurrence.effective_assignee_user_id` в данном коде остаётся `null`, даже если `Ticket.assignee_id` уже получил online-агента: `effective_assignee_user_id` отражает принятую при старте **прямую** кандидатуру, а не все последующие назначения. Для актуального адресата использовать `Ticket.assignee_id`/`current_assignee` из overview. Сервис распределяет **только вновь созданный** Ticket; он не запускает здесь массовую раздачу старой очереди (`test_distribution_assigns_only_new_internal_ticket_and_leaves_existing_queue_untouched`).

`creator_admin_id` — создатель определения, не меняется при редактировании другим администратором. `responsible_admin_id` — адресат завершения, по умолчанию создатель; API разрешает другого администратора своей компании, в том числе неактивного. Это не делает его гарантированно получающим уведомления: при доставке действуют дополнительные условия активности и привязки.

## 4. Административный API и обзор

Общий префикс — `/api/v1/management/internal-tasks`. Все маршруты вызывают `_require_admin`, получают текущую запись администратора и ограничивают поиск компании `company_id`. Это **не** публичный API для агентов/стажёров.

| Метод и путь от префикса | Назначение и существенные условия |
|---|---|
| `POST /` (у роутера — пустой суффикс) | Немедленно создаёт `Definition` + `Occurrence` + `Ticket`; возвращает их ID, флаг `created`, исходный и эффективный режим назначения; без клиентского ключа идемпотентности |
| `GET /options` | Списки `assignees` (`agent`, `trainee`) и `admins` **своей компании**, включая неактивных с атрибутами `is_active/availability_status`; `current_admin_id`, `app_timezone` |
| `GET /overview?scope=all\|mine&limit=…` | Четыре независимых массива `active`, `scheduled`, `completed`, `recurring`; `scope` только `all/mine`, `limit` 1–300, по умолчанию 100 |
| `POST /scheduled` | Сохранить будущий одноразовый запуск, без немедленного Ticket |
| `PATCH /scheduled/{definition_id}` | Изменить **только активное ещё не материализованное** расписание; дата запуска должна остаться в будущем; creator сохраняется |
| `DELETE /scheduled/{definition_id}` | Только активное не материализованное определение; переводит его в `disabled` — **не физическое удаление** |
| `POST /recurring` | Создать повторяющееся расписание и вернуть следующую дату, если она доступна для расчёта |
| `PATCH /recurring/{definition_id}` | Изменить настройки, включая `finished/paused`; не изменяет уже сделанные occurrence-снимки; активному расписанию поднимает границу генерации |
| `POST /recurring/{definition_id}/pause` | Только `active` → `paused`, выставляет границу генерации `now` |
| `POST /recurring/{definition_id}/skip-next` | Только `active`; пропускает **один ближайший будущий кандидат**, сдвигает границу за него; без будущего кандидата — 409 |
| `POST /recurring/{definition_id}/resume` | Только `paused/finished` → `active`, если ещё есть допустимые будущие срабатывания/лимит; граница `now` |
| `DELETE /recurring/{definition_id}` | Переводит расписание в `disabled`; ранее созданные экземпляры сохраняются |
| `DELETE /materialized/{ticket_id}` | Администратор **физически удаляет Ticket** с зависимыми данными через `_delete_ticket_hard`; `Occurrence` остаётся. Возвращает `file_delete_warnings` |

`overview` разделяет данные **по сущности, а не по одной взаимоисключающей вкладке**:

- `scheduled`: активные одноразовые определения без `Occurrence`, сортировка по времени запуска.
- `recurring`: активные, приостановленные и завершённые **определения**; `disabled` скрыты.
- `active`: материализованные экземпляры, если `Ticket.status != closed` (включая `unassigned`).
- `completed`: материализованные экземпляры, если `Ticket.status == closed`. Сам по себе `Definition.state=finished` не помещает запись сюда.
- Одна recurring-Definition может присутствовать в `recurring`, а её конкретные экземпляры — одновременно в `active` и `completed`.
- `scope=mine` означает, что администратор **создатель или ответственный**, а **не** обязательно текущий исполнитель Ticket. Для materialized применяется снимок creator/responsible из `Occurrence`.
- Materialized-список формируется `JOIN` `Definition`–`Occurrence`–`Ticket`, сортируется по `materialized_at_utc` от новых к старым; запрос забирает максимум `limit*2`, затем разделяет результаты и обрезает каждую вкладку до `limit`. Поэтому большой объём одной категории потенциально может вытеснить более старые элементы другой из данной выборки — **не заявлять полную пагинацию**.
- Если `Ticket` физически удалён, `Occurrence`-маркер остаётся, но результат `JOIN` в `active/completed` уже не появится.

## 5. Проверка полей и часы

Все три варианта POST имеют Pydantic `extra="forbid"`: неожиданные поля, включая поля отложенного/циклического создания в «создать сейчас», отклоняются. `title/description` обрезаются по краям; `title` обязателен и ограничен 255 символами, `description` не может быть пустым после `strip`. `direct` требует корректного сотрудника; `distribution` запрещает его ID. Ответственный — admin своей компании, по умолчанию текущий актор.

`deadline_enabled=true` требует `deadline_at`; при `false` дата должна быть `null`. Дедлайн сохраняется в `Definition` и копируется в `Occurrence`; для recurring это **значение определения**, автоматически «сдвигающегося на N дней от каждого экземпляра» алгоритма в исследованном коде нет. Время дедлайна добавляется к начальному описанию при материализации.

**Критическое различие для входа без UTC-offset:**

| Поле | Пример входа | Как код понимает «наивное» время при `app_timezone=Europe/Moscow` | Сохранение в UTC |
|---|---|---|---|
| `POST /` → `deadline_at` | `2026-09-17T13:30:00` | **13:30 UTC**, а не МСК | `13:30Z` |
| `/scheduled` → `scheduled_for`, `deadline_at` | `2026-09-17T13:00:00` | **13:00 Москва** | `10:00Z` |
| `/recurring` → `cycle_start_at`, `cycle_end_at`, `deadline_at` | `2026-09-17T13:00:00` | **13:00 Москва** | `10:00Z` |
| Любое из этих полей с offset | `2026-09-17T13:00:00+05:00` | Offset определён явно | `08:00Z` |

Это не абстрактное «везде локальное время»: источник — две разные функции `_normalize_datetime` (наивное = UTC, используется немедленным дедлайном) и `_normalize_app_local_datetime` (наивное = `settings.app_timezone`, используется планированием). Различие проверяется `test_create_now_keeps_naive_deadline_semantics_as_utc`, `test_scheduled_create_interprets_naive_datetime_in_app_timezone`, `test_recurring_timezone_naive_and_aware_datetime_normalization`.

Отложенная дата `scheduled_for` при создании и редактировании **строго больше** текущего `datetime.utcnow()`. Дата начала recurring не обязана быть будущей: если оставлена исторической, scheduler при первом проходе может материализовать прошедшие кандидаты (catch-up). Подтверждённые UTC-даты в коде чаще представлены naive `datetime`, но обработчики планировщика умеют нормализовать aware timestamps из PostgreSQL к UTC-naive. В документации не считать timezone naive равнозначным «время неизвестно»: здесь это договорённость хранения/расчёта.

## 6. Пять режимов повторения

Расписание строится от `cycle_start_at_utc`, `timezone_name` (при создании — `settings.app_timezone`) и строго нормализованного `recurrence_config`. Модуль `internal_task_recurrence.py` независим от БД и runtime.

| `recurrence_mode` | Конфигурация после нормализации | Правило |
|---|---|---|
| `daily` | `{"times":["10:00","16:00"]}` | В **каждый локальный день** в каждое время; строку `"16:00,10:00,10.00"` сортирует/убирает дубли |
| `selected_weekdays` | `{"weekdays":[1,5],"time":"09:05"}` | Выбранные дни недели по ISO, **1=понедельник, 7=воскресенье**; список нормализуется и сортируется |
| `weekly` | `{"time":"10:00"}` | Раз в 7 локальных календарных дней от локальной даты `cycle_start_at`; API принимает необязательный legacy `weekday` и пересчитывает начальный anchor на первую подходящую дату **не раньше** введённого старта |
| `monthly` | `{"day":31,"time":"10:00"}` или `{"day":"last","time":"10:00"}` | В выбранный день месяца. Если день 31 не существует, используется **последний фактический** день месяца; учитывается високосный февраль |
| `every_n_days` | `{"interval_days":3,"time":"10:00"}` | Каждые N **локальных календарных** дней от даты начала, N — положительное целое |

При вводе времени принимается `9:05` и `9.05`, сохраняется `09:05`; часы 0–23, минуты 0–59. Для daily разрешены строка с запятыми или массив; **один ошибочный элемент отклоняет весь ввод**, а не тихо пропускается. `weekdays` содержит только целые 1–7; `monthly.day` — 1–31 или `"last"`; `interval_days` и `cycle_max_occurrences` — положительные целые, `bool` не считается числом. В `recurrence_config` неизвестные или недостающие ключи отклоняются.

Генератор перебирает локальные календарные даты, затем переводит кандидатов в UTC. Возвращает **отсортированные уникальные UTC-наивные** даты внутри пересечения границ **включительно**: `cycle_start_at_utc`, `window_start_utc`, `window_end_utc`; дополнительно действует `cycle_end_at` для режима `at`. Тесты отдельно проверяют часовой пояс, месяцы, локальные границы и UTC-конвертацию.

### 6.1. Три способа окончания цикла

| `cycle_end_mode` | Правило | Когда завершение считается исчерпанным |
|---|---|---|
| `never` | Нет даты окончания и счётчика | По этому правилу автоматически не заканчивается |
| `at` | `cycle_end_at` обязателен, значение лимита — `null` | Кандидат **точно в момент конца** допускается; после достижения конца и успешной обработки всех разрешённых кандидатов определение переводится в `finished`. Если разрешённых кандидатов нет — может завершиться без созданного экземпляра |
| `count` | `cycle_max_occurrences > 0`; дата конца — `null` | Количество **сохранённых `Occurrence`** достигло лимита, тогда `finished` |

«Число повторений» здесь — число строк `Occurrence` конкретного определения, **не** число закрытых `Ticket`, не число доставленных уведомлений и не счётчик использованных `skip-next`. После hard delete Ticket маркер остаётся и **продолжает учитываться в `count`**.

### 6.2. Изменение, пауза, пропуск, возобновление

`generation_not_before_utc` — монотонная нижняя граница генерации, применяемая вместе с `cycle_start_at_utc` как `max(start, generation_not_before)`. Это **не** дата последнего успешного запуска.

1. **Новый recurring**: `active`, граница `null`, кандидатам разрешён catch-up от начала расписания.
2. **Редактирование ACTIVE**: сохраняет `creator` и историю; граница поднимается до `max(old_boundary, now)`. Изменённое расписание не «досоздаёт» задним числом новые кандидаты из интервала до правки. `PATCH` допустим и для `paused/finished`, но в этих состояниях он не активирует расписание сам.
3. **Pause**: только `active` → `paused`, граница ставится в момент паузы. Scheduler не обрабатывает paused.
4. **Resume**: только `paused/finished` при наличии допустимой ёмкости/будущих дат; становится `active`, граница ставится в момент возобновления. Пропущенный интервал паузы **не догоняется**. Если `count` исчерпан или нет будущего кандидата до даты `at`, ответ 409; после корректного `PATCH` законченный цикл может быть возобновлён.
5. **Skip-next**: только `active`, сервер ищет ближайший **будущий** кандидат и ставит `generation_not_before_utc = candidate + 1 микросекунда`; этот единственный запуск не создаёт `Occurrence` и не расходует `count`. При нескольких временах за день пропускается ближайшее время, а не весь день.
6. **Disable**: `DELETE /recurring/{id}` переводит в `disabled`; дальнейшие запуски этого определения не выбираются; ранее материализованные задания не исчезают.

**Нюанс `resume`:** `finished` не означает окончательное удаление. Можно отредактировать лимит/конечную дату и возобновить, но код требует будущей возможности запуска. Повторно использовать старые `Occurrence` как новые запуски нельзя — ключ времени уже занят.

Для поля `next_occurrence_at` обзор использует `_next_recurring_at()`, который ищет вперёд **не дальше `366*5` дней** от выбранной нижней границы. Поэтому `null` в UI — не доказательство невозможности какой-либо даты во всей бесконечности (кроме явно исчерпанного/истёкшего end-condition). Результат `next_occurrence_at` — предварительный расчёт API, не самостоятельный cron/job.

## 7. Планировщик: порядок, периодичность и восстановление после простоя

Точка цикла — `async internal_task_scheduler_loop()` в `api/app/services/internal_task_scheduler.py`. Внутри бесконечного цикла шесть последовательных вызовов через `asyncio.to_thread()`:

1. `run_internal_task_scheduler_once()` — отложенные одноразовые задачи.
2. `run_internal_task_recurring_once()` — повторяющиеся задачи.
3. `run_avatar_cleanup_once()` — nightly-очистка Telegram-аватаров.
4. `run_telegram_after_hours_cleanup_once()` — очистка Telegram-черновиков вне часов приёма.
5. `run_employee_auto_offline_once()` — автоматический offline сотрудников.
6. `run_employee_notification_backlog_once()` — накопитель/выдача сотруднических Telegram-уведомлений.

После завершения **всех** шести попыток — `asyncio.sleep(30)`. Следовательно, «каждые 30 секунд» — это **30 секунд сна плюс длительность самого прохода**, не точный cron по часам. Каждая ветвь обёрнута независимым `try/except`: ошибка задачи одного типа логируется, остальные ветви всё равно вызываются; `CancelledError` повторно выбрасывается. Очередность и продолжение после исключения проверены текстом scheduler-loop тестов. Семантика остальных четырёх фоновых служб подробнее рассмотрена в `TELEGRAM.md` и предшествующих шагах журнала; здесь они приведены как **соседи по общему циклу**, а не как часть внутреннего расписания.

### 7.1. Отложенные одноразовые задания

`run_internal_task_scheduler_once()` выбирает только `scheduled + active + scheduled_for_utc <= now`, по возрастанию даты и ID. Исторические просроченные задания **не отрезаются lookback-периодом**. После простоя сервиса задание создаётся при ближайшем успешном проходе, причём `Occurrence.occurrence_at_utc` — **исходное плановое время**, не `scan now`. После успешного commit определение становится `finished`.

Каждое выбранное определение перепроверяется перед материализацией. Для каждого работает собственная сессия и commit; сбой откатывает конкретную попытку, логируется и не мешает следующему определению. Оно остаётся кандидатом для следующего прохода. Повторный проход после успеха не создаёт дубль.

### 7.2. Повторяющиеся задания

`run_internal_task_recurring_once()` выбирает `recurring + active`; для каждого определения формирует все подлежащие исполнению даты между эффективной нижней границей и текущим `now`. Уже существующие `Occurrence` исключаются по точному времени. Если приложение было выключено несколько дней, без паузы/редактирования/skip и без исчерпанного end-condition оно **догоняет все пропущенные кандидаты**, а не только один «последний».

Кандидаты одного определения обрабатываются **по времени** и **отдельными транзакциями**. При ошибке очередного кандидата:

- уже созданные более ранние экземпляры этого определения остаются в БД;
- ошибочный запуск не увеличивает число сохранённых `Occurrence`;
- более поздние даты **того же определения** прекращают обработку в данном проходе, чтобы не обгонять неуспешную дату;
- другие определения продолжают обрабатываться;
- следующий проход повторяет неуспешный момент.

Валидатор испорченного config одного расписания не блокирует другие. Если `cycle_end_mode=at`, завершение откладывается, пока все допустимые даты не обработаны; если `count`, окончание привязано к сохранённому количеству строк. Тесты описывают частичный успех, отказ в середине, идемпотентный повтор и включительность крайней даты.

### 7.3. Размер партий — не общий потолок 50

Константы `INTERNAL_TASK_SCHEDULER_BATCH_LIMIT=50`, `INTERNAL_TASK_SCHEDULER_INTERVAL_SECONDS=30`. Лимит 50 относится к **одной DB-выборке определений**. В пределах прохода код берёт начальное количество и повторяет выборки, исключая уже attempted ID; поздние определения не должны бесконечно голодать из-за первых 50. Это тестируется с уменьшенным размером партии 2. Не формулировать «за проход обрабатывается максимум 50 задач»: это неверно. Отдельного бизнес-ограничения на число catch-up-экземпляров одного recurring-definition в исследованном коде нет — длительный простой потенциально создаёт большую работу и увеличивает время цикла.

## 8. Идемпотентность и границы конкурентности

`materialize_internal_task()`:

1. Проверяет существование компании, допустимость режима назначения и вида расписания, наличие `occurrence_at_utc`.
2. Ищет запись по **паре** `(definition_id, occurrence_at_utc)` до изменений.
3. В `db.begin_nested()` (SAVEPOINT) повторно ищет запись, создаёт клиента/Occurrence/Ticket/сообщения и назначение.
4. При `IntegrityError` повторяет поиск существующего запуска и может вернуть его как `created=false`.

Объявленная уникальность `Occurrence` по этой паре — главная DB-защита от повторной материализации **того же определения в тот же момент**, а не от двух администраторских POST «создать сейчас». В тестах есть повторный вызов с ожиданием одного Ticket и одних сообщений.

Что **не доказано** и чего эта схема сама не гарантирует:

- **Глобальный singleton scheduler** при нескольких API workers/репликах: в просмотренном цикле нет распределённого lease на проход, claim-очереди или глобального scheduler-lock. DB-уникальность помогает при дублях, но не доказывает весь многопроцессный сценарий без race/lost-update.
- **Exactly-once внешних уведомлений**: отдельная система отправки Telegram с best-effort/after-commit, потенциальными потерями/повторами; полный outbox и сквозной exactly-once не подтверждены.
- **Гарантированная обработка всех due к фиксированному дедлайну**: 30-секундный сон, долгий catch-up, отключённые сервисы и сетевые/DB-ошибки вносят задержку.
- **Восстановление вручную удалённого Ticket по оставшемуся `Occurrence`**: повторяемый момент считается занятым, планировщик его не создаёт повторно. Прямой вызов `_existing_result()` при маркере без Ticket вообще выбрасывает `RuntimeError`.
- **DST-политика** для несуществующего/двойного локального времени в зоне перехода: `_local_candidate()` использует `datetime.combine(..., tzinfo=ZoneInfo)` и конвертацию в UTC, но отдельного бизнес-правила выбора fold/gap и живых тестов на такие дни нет.

Эти пункты — **границы обследованного контракта и темы для отдельного решения**, не диагноз неисправности сервиса.

## 9. Закрытие, уведомление и передача результата

Внутреннее происхождение определяется `is_internal_task_ticket()` по существующей записи `InternalTaskOccurrence.ticket_id`, **не** по тому, что `workflow_type=task`: обычные задачи `task/normal` могут иметь тот же базовый тип Ticket. Общий staff lifecycle описан в `WORKFLOWS.md`.

| Сценарий | Что происходит |
|---|---|
| Исполнитель пишет промежуточный ответ / прикладывает файл | Это **не** событие уведомления ответственному о выполнении; ожидание результата связано с закрытием |
| Штатное закрытие с последним актуальным `agent`-ответом | `Ticket` становится `closed`; при разрешённых настройках планируется уведомление ответственному администратору с итогом |
| Итог только вложением, без текста | В уведомлении присутствует имя файла, **файл как отдельный Telegram-document не отправляется** |
| Итог с текстом и несколькими версиями вложений | Берутся **последний** agent-ответ и только относящиеся к нему имена файлов; старые agent-сообщения и внутренние комментарии не попадают в результат |
| Штатное закрытие администратором после результата сотрудника | `closed_by_user_id` — администратор, `completed_by_user_id` и имя в уведомлении — сотрудник-автор итогового ответа |
| Принудительное закрытие без ответа сотрудника | Уведомление о выполнении **не формируется** |
| Обычная задача, не созданная внутренним модулем | Внутреннее уведомление не планируется; её клиентская доставка действует по общим правилам |

Для внутренней задачи клиентская доставка текста/результата в Telegram или WEB **подавляется** по признаку `Occurrence`, чтобы не посылать рабочий результат техническому «клиенту». Тест `test_internal_task_close_suppresses_client_telegram_but_normal_task_still_sends` сравнивает с обычной задачей.

Получатель уведомления — `Occurrence.responsible_admin_id`, то есть **снимок на момент создания экземпляра**. Учитываются одновременно:

- `Occurrence.notify_on_completion`;
- запись администратора, роль/активность по правилам сотруднической доставки;
- его `EmployeeNotificationPreference`, флаги получения, персональный/базовый шаблон;
- доступная одобренная Telegram-привязка и настройки отправки;
- рабочий график / накопитель сотруднических уведомлений (Пн–сб 08:00–19:00 МСК по `8439b32`, воскресенье закрыто); время фактического Telegram-сообщения может отличаться от момента close.

В тексте используются **название из `Occurrence.title_snapshot`** (а не возможная новая тема Ticket/Definition), имя автора результата, последний итоговый текст и названия итоговых файлов. Поддерживаются персональный шаблон и базовый `internal_task_completion`; даже включённый базовый шаблон не отменяет персональный **delivery gate**. Отсутствие отдельной строки настроек тестом трактуется как default-enabled. При недоступном ответственном/Telegram-канале уведомление пропускается; ошибка отправки **не откатывает закрытие Ticket**. Изолированные тесты проверяют ровно одно текстовое уведомление на штатное закрытие в исследованном сценарии, но это не глобальная exactly-once гарантия.

## 10. Разное «удаление»: определение и выполненный запуск

| Действие | `Definition` | `Occurrence` | `Ticket`, сообщения, вложения |
|---|---|---|---|
| Удалить ещё не запущенное `scheduled` | Состояние → `disabled`; строка остаётся | Ещё нет | Не создавались |
| Удалить `recurring` | Состояние → `disabled`; строка остаётся | Прежние остаются | Прежние экземпляры остаются |
| Удалить конкретное материализованное задание | Определение сохраняется | **Маркер конкретного запуска остаётся** | **Hard delete** через общий сервис, включая доступные связанные данные/физические файлы; возможны предупреждения удаления файлов |

После удаления конкретного экземпляра recurring-definition соответствующее время **уже считается использованным** и не будет воссоздано повторным проходом планировщика. Это отдельно проверяет `test_delete_materialized_recurring_task_keeps_occurrence_marker_and_scheduler_does_not_recreate`. Историческая запись `Occurrence` сохраняется, но `overview` соединяет её с существующим Ticket и не показывает удалённый экземпляр в материальных вкладках. Для `count` оставшийся маркер продолжает учитываться в лимите.

Hard delete — существенно более сильная операция, чем `disable` расписания. Не смешивать её с обычным close Ticket и не рекомендовать без решения о сохранении истории. Полная матрица admin hard delete, транзакций и файлов — в `WORKFLOWS.md` и `INVARIANTS.md`.

## 12. Реестр вопросов перед будущими изменениями

| ID | Граница / возможное продуктовое решение | Почему важно |
|---|---|---|
| IT-01 | Единый scheduler при 2+ API-процессах или серверных репликах | Есть локальный цикл и DB-уникальность, но не доказан единый claim/lease на определение |
| IT-02 | Дата без offset у немедленного дедлайна | Сейчас UTC, хотя scheduled/recurring naive = app local; возможна неоднозначность UI/контракта |
| IT-03 | Дедлайн recurring — фиксированный timestamp или срок **от каждого запуска** | В `Occurrence` копируется дата определения, относительного пересчёта нет |
| IT-04 | Поведение после простоя с большим числом пропущенных запусков | Catch-up не ограничен общим числом экземпляров и может задержать остальные циклы |
| IT-05 | Политика hard delete и сохранённый orphan-маркер | Повтор не создаётся; `count` сохраняется; явный `_existing_result()` на маркере без Ticket выдаёт ошибку |
| IT-06 | Сезонный перевод часов в региональных timezone | Специальный выбор DST gap/fold не определён бизнес-правилом и не проверен |
| IT-07 | Идемпотентность внешнего немедленного POST и доставок | Два POST создают два Ticket; after-commit/Telegram не является exactly-once |
| IT-08 | Ограничение выборки overview `limit*2` и полнота истории | Вкладки активных/завершённых могут иметь несимметричные окна данных |
| IT-09 | Допуск inactive assignee/responsible в сохранённый шаблон | Runtime делает fallback, а уведомления inactive ответственному не гарантированы |
| IT-10 | Возобновление `finished` и изменение расписания с historical occurrences | Нужна договорённость, какую историю считать использованной, что сохраняет `count` и что делает новая граница |

**Это не перечень подтверждённых дефектов.** Для каждого изменения сначала согласовать ожидаемый продуктовый контракт, затем адресно извлечь соответствующий код/тест, предложить минимальный diff и отдельно получить разрешение на live smoke/DDL-аудит, если он необходим. Не изменять PROD/DB из задачи документирования.
