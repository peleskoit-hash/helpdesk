## 2. Объект Ticket и независимые измерения состояния

`Ticket` — общая сущность; разговорное «тикет» не равно `workflow_type=ticket`. Нельзя делать выводы о клиентском канале или правилах закрытия по одной колонке.

| Измерение | Важные значения | Смысл |
|---|---|---|
| `channel` | `telegram`, `web` | Куда пришёл клиент и как отдавать результат. Не синоним `workflow_type` |
| `workflow_type` | `ticket`, `task`, `auto` | Обычная переписка, задача с итогом, автоматическое обращение |
| `task_kind` | `normal`, `group_parent`, `group_child` | Вариант задачи; дочерний объект указывает на родителя через `parent_ticket_id` без DB-FK |
| `intake_state` | прежде всего `collecting`, `ready`, `cancelled` | Создание ещё не завершено, полностью оформлено либо отменено; **не** равно `status` |
| `status` | `unassigned`, `new`, `pending`, `closed` | Очередь/исполнитель/закрытие |
| `is_frozen` / `freeze_until` | флаг и срок | Поперечное состояние паузы; `new` и `pending` могут оставаться теми же |
| `is_special` / `special_assignee_id` | флаг и администратор | Особый административный контур поверх status/workflow; отдельная вкладка |
| `agent_visible` | bool | Ограничивает видимость для агента/стажёра в рабочей очереди |
| `assignee_id` | пользователь/null | Текущий ответственный, **не** обязательно автор фактического результата |
| `closed_by_user_id` / `completed_by_user_id` | пользователь/null | Кто выполнил действие закрытия / кому засчитано выполнение — **разные** поля |

Общие инварианты для чтения документа: **`new` — не «непрочитано»**, `pending` — не «закрыто», `is_frozen=true` — не новый статус, `collecting` — не самостоятельная очередь и наличие `ticket_number` — не маркер успешной доставки. Состояние вложений и отложенных уведомлений ведётся другими таблицами/полями.

## 3. Как объекты появляются: общая входная развилка

| Источник | Что создаётся / ключевой шаг | Что происходит дальше |
|---|---|---|
| Telegram, обычное обращение | Меню, контакт, профиль и допустимость создания → предварительный `Ticket`/сбор данных → `ready` | Нумерация, исполнитель, отдельные клиентские сообщения/кнопки. В рабочей переписке возможны быстрые действия и 20-минутное автозакрытие |
| Telegram, `task/normal` | Выбор DB-only кнопки и задача на основе текста/вложений клиента | Назначение → ответ сотрудника → закрытие с отправкой итогового ответа и приложений |
| Telegram, `task/group_parent` | Общее обращение с правилами групповой автоматизации | При назначении вызывается hook создания дочерних задач; их ответы могут агрегироваться в parent. Детали построения группы — `TELEGRAM.md` |
| WEB, `task/normal` | WEB-сессия → меню → серверный черновик → создаваемая задача; файлы проходят отдельную предзагрузку | Сотрудник готовит ответ; после закрытия опубликованный `WebTaskResult` становится клиентским итогом |
| WEB, обычный `ticket` | Общая модель и staff API допускают тип | В актуальном клиентском WEB UI путь **создания обычной заявки не реализован**; не описывать его как работающий |
| Внутренняя задача | `InternalTaskDefinition`/`InternalTaskOccurrence`, технический клиент | Плановый или разовый выпуск на сотрудника; ответ остаётся внутренним, итог клиенту в Telegram не отправляется |
| `auto` | Автоматизация из Telegram/системного обработчика | Не включать в обычную очередь auto-assignment и не приписывать ему правила обычного `ticket` |

Подробный клиентский intake, проверки 19:00, меню и DB-only конфигурация относятся к `TELEGRAM.md` §§ 1–21; WEB авторизация, черновики, вкладки и клиентские файлы — `WEB.md`. Здесь сохраняется **общий переход между каналами и сотруднической обработкой**. Веб-черновик/предзагрузка, `TicketMessage`, `WebChatMessage` и `WebTaskResult` — **разные** объекты. Не считать техническое WEB-событие чата последним агентским ответом.

### 3.1. Граница между сбором и рабочей заявкой

Состояние `collecting` может иметь физическую запись `tickets`, но она ещё не обязательно «готова» к распределению. Для штатных очередей auto-assignment проверяет `ready`; номер может выделяться позже функцией `ensure_ticket_number`. В `list_tickets_paginated` и карточке ready-объект без номера получает номер при чтении — это **запись в БД**, а не гарантированно чистый GET. Поэтому реальный момент нумерации не следует жёстко приравнивать только к Telegram callback.

Неоформленная Telegram-заявка, неоформленная обычная Telegram/WEB-задача и неоформленный Telegram group-parent имеют **узкие отдельные предикаты** в `ticket_admin_actions.py`. Их принудительное закрытие или отмена может означать **физическое удаление записи**, а не `status=closed`. Не распространять это правило на все `collecting` и не считать удаление безвозвратного объекта обычным закрытием.

## 4. Аутентификация и права на жизненном цикле

`get_current_user` читает активного пользователя по server session, проверяет роль из `{admin, agent, trainee, chiki_piki}` и обновляет время активности. Обычный idle timeout — **12 часов**; для реального администратора может отключаться настройкой `disable_admin_idle_timeout`. Тестовый admin override/effective-user переключатель **в данном коде отключён** (`_resolve_effective_user` возвращает реального пользователя). Код хранит в `CurrentUser` реальную и эффективную идентичность, но сейчас они совпадают.

| Роль | Реальные границы в исследованных маршрутах |
|---|---|
| `admin` | Списки, все карточки, bulk assign/close/freeze/unfreeze/delete, перевод в особые, операции над доступными объектами; не означает обход всех бизнес-ограничений обычного `POST /close` |
| `agent`, `trainee` | В активной работе видят назначенные им `agent_visible=true` объекты; могут отвечать, комментировать, закрывать и пользоваться разрешёнными быстрыми действиями в доступной карточке. **Закрытые объекты — особое исключение для просмотра** |
| `chiki_piki` | Read-only: выдачи ограничены направлением «Колл Центр» по ключам и реестру; карточка проверяет destination/ключи; управлять/отвечать нельзя |

**Важная тонкость закрытых:** в `list_tickets_paginated(... include_support_all_closed=True)` вкладка `/closed` для agent/trainee *не использует* обычный фильтр «назначено мне», а `_get_ticket_or_404` при `status=closed` пропускает проверку assignee/agent_visible. Это фактическая особенность **текущего кода**, которую нельзя заменять ожидаемой политикой «сотрудник всегда видит только свои». Она не предоставляет права на изменение закрытого содержимого: соответствующие действия отдельно проверяют статус/роль. Позже проверить намеренность видимости как политический/безопасностный инвариант.

Parent групповой задачи скрыт для не-admin в `apply_group_parent_visibility_filter`, включая карточку. `chiki_piki` получает дополнительный фильтр своего подразделения, который в list и card реализован **не идентичным набором признаков**; отсутствие ложных расхождений на реальных данных ещё не проверено.

## 5. Списки, счётчики, поиск и факт прочтения

| Роут | Отбор по состоянию | Существенное исключение |
|---|---|---|
| `GET /active` | `new`, `pending`, `is_frozen=false` | Открытые особые исключены, кроме специфических read-only условий |
| `GET /frozen` | `new`, `pending`, `is_frozen=true` | Открытые особые исключены |
| `GET /unassigned` | `unassigned`, не заморожена | Только admin/`chiki_piki`; не фильтруется по admin assignee |
| `GET /closed` | `closed`, любой `is_frozen` | Support может видеть все закрытые; админский фильтр assignee здесь выключен |
| `GET /special` | `is_special=true`, не `closed` | Только admin; отдельная реализация `list_special_tickets` |
| `GET /counts` | Отдельные агрегаты по очередям; admin `by_assignee` | Не механически равно `len(items)` одной страницы |
| `GET /task-panel` | Просмотренные ранее агентом, назначенные ему незакрытые видимые неособые | Основывается на `TicketView` и последнем сообщении |

Параметры листинга: `sort=created_at|updated_at`, порядок asc/desc, страницы, лимит **1–100** (`20` по умолчанию), строковый поиск и для части admin-списков фильтр `assignee_ids`. Поиск выполняется SQL-предикатами по теме, полям кнопок, реестру, имени заявителя (со специальной Unicode casefold-логикой) и тексту сообщений. Списки вычисляют имя заявителя со специальным приоритетом call-center snapshot/профиля/Telegram и отдельно атрибуцию внутренней задачи («Система»/создатель); отображаемое имя не обязательно равно `Client.display_name`.

Прочтение устроено в два этапа:

1. `GET /{id}` создаёт/обновляет `TicketView` и `first_opened_at`, **не равен** подтверждению всех новых сообщений. При первом открытии граница `last_opened_at` устанавливается перед созданием заявки, чтобы старые сообщения не считались автоматически прочитанными.
2. `POST /{id}/read` доступен назначенному support-пользователю, принимает граничное `message_id` и множество реально показанных `message_ids`. Проверяет допустимость границы, наличие всех видимых сообщений до неё, использует блокировку строки и не сдвигает `last_opened_at` назад из другой вкладки.

`unread_count` считается по видимым/допустимым для чтения сообщениям после `last_opened_at`, а не по `Ticket.status`. Получение карточки может также запускать восстановление загрузок и инициализацию таймера автозакрытия подходящей заявки — **GET может менять служебное состояние**.

## 6. Назначение и передача исполнителю

### 6.1. Обычное автоматическое назначение

`choose_online_agent` рассматривает **активных** пользователей роли `agent` со статусом доступности **online**. Выбирает минимальную текущую нагрузку по активным `new/pending` и `load_counted`, при равенстве — более раннее `last_assigned_at`, затем имя. Стажёр не включён в этот выбор. `assign_ticket_to_agent` дополнительно требует, чтобы заявка была **ready**, имела статус `unassigned`, не была `auto`, и назначаемый агент принадлежал нужной компании и был online. Успех переводит объект в `new`, заполняет исполнителя/время, пишет системное сообщение, запускает учёт рабочего интервала и уведомления.

Если при распределении свободного агента нет, заявка остаётся в очереди; существование очереди не означает, что её автоматически обработает кто угодно. `assign_unassigned_to_agent` и `assign_unassigned_fairly` проходят готовые неособые незамороженные объекты без исполнителя, исключая `auto`, ограничивая компанию и видимость; при групповых parent действует отдельное допущение. Выбор очереди упорядочен по времени создания.

### 6.2. Фиксированное и административное назначение

- Настройка принудительного исполнителя (`resolve_forced_assignee`, `assign_ticket_to_forced_user`) может выбрать активного `agent`/`trainee` по ID/логину, **без обязательного online**, если выполнены прочие условия соответствующего пути. Это другой механизм, не tie-break в обычной online-очереди.
- `POST /assign` — **только admin**; целевой пользователь активен и имеет роль `admin`, `agent` или `trainee`. `null` означает снять назначение, **кроме особой заявки** (она должна оставаться у администратора). Bulk-запрос проверяет наличие всех выбранных ID до обработки и делает commit после цикла.
- Сервис синхронизирует `StatsWorkInterval` при смене исполнителя, пишет системную историю, создаёт сотрудническое уведомление; при назначении parent может вызвать hook формирования группы.
- Для Telegram обычной заявки предусмотрено уведомление клиента о назначении. Уведомление сотруднику планируется с учётом commit, расписания и backlog-механизма из `TELEGRAM.md`. Не считать успешное изменение `assignee_id` доказательством доставки любого из этих сообщений.

`/assign` и быстрые назначения при разных состояниях могут отличаться по допустимым входам; описание выше **не утверждает**, что принудительный/ручной путь проверяет online так же, как auto-путь.

## 7. Работа с карточкой до завершения

### 7.1. Обычные ответы и комментарии

- `POST /{id}/reply` — внешний ответ, делегирует `ticket_messages.reply_to_ticket`. Для обычной Telegram-заявки возможна фактическая отправка клиенту и обновление timers/состояния. Для WEB-задачи ответ сотрудника сохраняется как рабочий `TicketMessage`, **публикация клиентского результата происходит при закрытии**, а не от одного факта `/reply`.
- `POST /{id}/comment` — внутренняя запись `message_type=internal`, не подменяет `message_type=agent` при проверке возможности закрыть.
- `PATCH /{id}/messages/{message_id}` и `DELETE /{id}/messages/{message_id}` — отдельные правила редактирования и мягкого удаления агентских сообщений, делегированы `ticket_messages.py`. При поиске «последнего ответа» закрытие исключает `message_status=deleted`.
- `PATCH /{id}/draft` хранит черновик отдельно для режима `reply` или `comment`. Изменение черновика не считается сообщением клиента или агента и не публикует результат.
- `POST /{id}/greeting` — одноразовое быстрое приветствие применимо к обычной заявке при выполнении проверок. Может перевести `new` → `pending`, снять заморозку, отправить текст в Telegram и перезапустить таймер. Для WEB `_send_to_telegram_client` не отправляет клиентский Telegram-текст.

Прямая роль `agent`/`trainee` в общем коде *не означает* разрешение на любой API-метод: окончательное ограничение задаётся карточкой, workflow и статусом. Для дословной матрицы quick actions и полных ограничений edit/delete сообщения потребуется прочитать тела `ticket_messages.py`, которые шаг 41 получил только в виде индекса.

### 7.2. Файлы и предзагрузка

`POST /{id}/attachment-preloads`, `GET /{id}/attachment-preloads/{preload_id}`, `POST .../retry`, `DELETE ...` управляют предварительной загрузкой. `upload_id` и совпадение файла защищают от части повторов; конфликт несовпадающего содержимого должен вызывать ошибку, а не незаметную замену. Загрузка и отправка могут выполняться в `BackgroundTasks` после регистрации состояния в БД. Неопределённая Telegram-квитанция требует **явного подтверждения риска повторной отправки** (`confirm_uncertain`) — не слепого retry.

Перед закрытием **задачи** `ensure_task_uploads_finished` блокирует процесс при активной загрузке/отправке у задачи (и, где применимо, у дочерних). Это **не** универсальная гарантия, что все ранее завершённые с ошибкой вложения успешно доставлены. Разные ветви Telegram, WEB и архива используют свои квитанции; подробности — `TELEGRAM.md` §§ 18–21 и `WEB.md` (drafts, uploads, result).

### 7.3. Заморозка, разморозка, автозакрытие

`POST /{id}/freeze` устанавливает `is_frozen=true`/срок, закрывает текущий `StatsWorkInterval` причиной `freeze`, сбрасывает автотаймер; `POST /{id}/unfreeze` снимает флаг, открывает рабочий интервал подходящему исполнителю, перезапускает автотаймер. `status=new|pending` может сохраниться. Bulk `/admin/freeze` исключает `closed`, уже замороженные, `unassigned`, без исполнителя и **особые**; bulk `/admin/unfreeze` отдельно считает закрытые/уже размороженные. Не предполагать полного совпадения bulk-предикатов с индивидуальными endpoint без проверки.

`PATCH /{id}/auto-close` меняет доступность автозакрытия в допустимой обычной заявке. 20-минутный автотаймер — механизм `workflow_type=ticket`, а **не WEB task и не любое сообщение**. Срок зависит от клиентских/агентских сообщений, заморозки, состояния и других условий `auto_close.py`; цикл очистки запускается фоном, а не прямо в браузере. Подробные условия и слабые места отправки до DB commit зафиксированы в `TELEGRAM.md`.

### 7.4. «Неверно выбрана проблема» — именно подсказка

`GET /{id}/problem-menu` строит доступное DB-only дерево конечных пунктов из активной конфигурации соответствующего меню и исключает текущий пункт. `POST /{id}/wrong-problem` можно использовать **не более одного раза на объект** (`wrong_problem_used_at`), нельзя на закрытом объекте и group child; нельзя выбрать подменю. При этом:

| `workflow_type` | Реакция |
|---|---|
| `ticket` | Сразу пытается отправить подсказку клиенту в Telegram; после успешной операции пишет системные сообщения, может снять заморозку и перевести `new` → `pending` |
| `task` | Запоминает текст `wrong_problem_hint` и системную запись о будущей отправке; подсказку пытается отправить **при завершении** задачи. При неудаче флаг сохраняется для дальнейшего анализа/повтора по правилам существующего кода |

Это **не автоматическое перемещение текущего Ticket в другой тип проблемы**, не создание новой задачи и не замена `button_config_key` рабочей заявки. Для этого действия важно наличие конкретной конечной кнопки в выбранном menu.

### 7.5. Особые заявки

`POST /{id}/special` — admin, для незакрытой не-`auto` заявки/задачи. `_apply_move_to_special` устанавливает `is_special=true`, назначает текущего администратора (`special_assignee_id` и `assignee_id`), снимает авто-close timer, переводит `unassigned/new` → `new`, а прочее открытое состояние → `pending`, записывает служебную историю. Обычная **заявка** в особом списке может блокировать клиенту создание новой обычной заявки до закрытия — это прямо предупреждается системным сообщением.

При назначении особого объекта другому администратору особый статус сохраняется и меняется его ответственный. При назначении `agent`/`trainee` особый статус **снимается**, специальные поля очищаются и продолжается обычная обработка. Нельзя просто снять исполнителя особой заявки через admin bulk assign.

## 8. Закрытие: общий контракт и развилки

### 8.1. Нормальный `POST /{id}/close`

Обычный endpoint доступен пользователю с правом управления и доступом к карточке. Уже закрытая заявка возвращает `409 ticket_already_closed`. Центральная функция `close_ticket_by_actor` в общем случае требует **хотя бы одно действующее сообщение типа `agent`** (исключая soft-deleted) и выполняет `ensure_task_uploads_finished`; отсутствие агента — `409 close_not_allowed`.

Для задачи дополнительно требуется исходное клиентское сообщение; иначе без административного force — `409 task_client_message_required`. Проверка касается типа/наличия записи, а не оценки качества ответа. Работа в комментарии (`internal`) и несохранённый draft не заменяют ответ агента. Путь принудительного администратора отличается (§ 9).

При успехе обычно устанавливаются `status=closed`, `closed_at`, `closed_by_user_id`, `is_frozen=false`, очищается срок freeze, закрывается рабочий интервал, пишется системное сообщение. Объект **не обязательно удаляется**; его сообщения/результат имеют собственный контракт. Внутри сервиса существуют внешние вызовы Telegram **до** `db.commit()` endpoint — это не единая атомарная транзакция с Telegram API.

### 8.2. Обычная заявка (`workflow_type=ticket`)

После ответа сотрудника закрытие выключает автотаймер, записывает системное событие и, если отмечено `onsite_triggered`, создаёт служебное напоминание. Для Telegram готовится уведомление о закрытии с доступными post-close действиями (отзыв/замечание при соответствующих условиях); при неудаче необязательная отправка может фиксироваться отдельной системной ошибкой. Для WEB `_post_close_markup_for_ticket` возвращает `None` и Telegram-уведомление не посылается. Статистика выполнения может быть синхронизирована независимо от факта клиентского прочтения.

Клиентское закрытие Telegram через callback/кнопку — **отдельный маршрут**, а не просто вызов сотруднического `POST /close`; его условия и действия по неоформленной задаче/заявке описаны в `TELEGRAM.md` (из шага 41 доступен индекс `telegram_client_close.py`). Не утверждать, что обе ветви идентичны.

### 8.3. Обычная Telegram-задача (`task/normal`)

Последний **действующий** агентский `TicketMessage` и его `TicketAttachment` формируют итог. При закрытии клиенту отправляется форматированный текст с исходной задачей, ответом, при необходимости списком файлов, затем требуемые вложения. Подсказка «неверная проблема», если была отложена, может отправляться после итогового ответа. Отдельные сообщения могут быть *необязательными*, а необходимые вложения — вызывать ошибку; **невозможно приравнивать статус закрытия к факту полной Telegram-доставки**.

Внешние вызовы находятся на пути закрытия **до коммита** локального endpoint, поэтому при сбое БД уже отправленный Telegram-текст не откатывается. При неудаче отправки Telegram возможен фиксируемый отказ. Идемпотентность вложений и cleanup описаны в `TELEGRAM.md`; здесь не обещается exactly-once.

### 8.4. Обычная WEB-задача (`task/normal`, `channel=web`)

При штатном закрытии с ответом и без подавления публикации вызывается `web_task_results.publish_result(db, ticket, last_agent_message, final_attachments)`. **В одной DB-транзакции закрытия** подготавливается опубликованный итог (`WebTaskResult`) и прикреплённые снимки файлов (`WebTaskResultFile`). Клиент затем читает их через WEB API; рабочий `TicketMessage` и событие `WebChatMessage` не заменяют опубликованный результат.

WEB `reply` сам по себе не публикует итог. Admin force-close **без ответа** проходит ветвь без вызова `publish_result`, поэтому из одного `status=closed` нельзя выводить, что доступен полный клиентский WEB-результат. Ветка неоформленной WEB-задачи может вместо закрытия удалить её и записать событие отмены в WEB-чат. Клиентский UI/авторизация/история/скачивание подробно описаны в `WEB.md`.

### 8.5. Внутренняя задача

Тип `task` может быть внутренней задачей, что определяется не одним `channel`, а `InternalTaskOccurrence`/`is_internal_task_ticket`. Для обычного успешного закрытия **клиентская отправка подавлена**; вместо неё при штатной (не force) ветви планируется сотрудническое уведомление о завершении после коммита. Статистика и системная история закрытия ведутся независимо. Расписание materialization, создание technical client и периодичность scheduler из шага 41 известны **только по индексу функций**; подробные тела `internal_tasks.py` и `internal_task_scheduler.py` ещё не были прочитаны полностью.

### 8.6. Групповая задача и подзадачи

У `group_parent` есть дочерние `group_child` по `parent_ticket_id`. При закрытии дочерней задачи с действующим агентским ответом, если **`suppress_client_answer=false`**, сервис копирует на parent последнюю агентскую запись и метаданные её файлов. Если `suppress_client_answer=true`, ответ дочерней задачи в агрегированный клиентский ответ не попадает.

`finalize_group_parent_if_ready` делает `flush`, ищет **любого незакрытого ребёнка** и закрывает parent автоматически **только при отсутствии таких детей**. Проверяет незавершённые загрузки, берёт собранные ответы/файлы, при наличии первого клиентского сообщения и без skip уведомляет клиента, ставит `closed` и служебную запись. В функции нет прямого вызова `_mark_ticket_completed` для parent; **не следует считать каждое автоматическое закрытие parent зарегистрированным в `StatsCompletion` на основании этого кода**.

**Крайний случай:** прямой `POST /{parent_id}/close` имеет самостоятельную ветвь для `group_parent` и в показанном коде **не вызывает тот же предикат «все дети закрыты»**, который есть у `finalize_group_parent_if_ready`. Поэтому фразу «parent всегда может закрыться только после всех детей» нельзя записывать как универсальный инвариант. Проверить это отдельно в `INVARIANTS.md`/тестах, прежде чем делать продуктовый вывод или исправление.

При принудительном закрытии дочерней без ответа parent может завершиться с пометкой **«возможен неполный ответ»**, когда остальные дети завершены. При физическом удалении ребёнка в bulk-контуре также вызывается попытка завершения оставшегося parent; если parent одновременно удаляется, finalize специально пропускается для исключения дублированного уведомления/конфликта. Отправка результатов группы не гарантирует доставку всех файлов: клиентский Telegram — внешняя система.

## 9. Принудительное закрытие администратором

`POST /admin/close` — отдельная **bulk admin** операция; для всех найденных объектов вызывает `close_ticket_by_actor(... force_without_agent_reply_for_task=True, skip_client_notification=...)`, накапливает `closed`, `already_closed`, `not_found`, затем делает `db.commit()`. `skip_client_notification` действует на этом *административном force*-пути, а не становится глобальным флагом для обычного закрытия.

| Состояние | Действие admin force close |
|---|---|
| Уже `closed` | Ничего не закрывает повторно, возвращает счётчик `already_closed` |
| Неоформленный Telegram `ticket` с подходящим узким предикатом | Убирает клавиатуру/кнопку, при необходимости уведомляет, **физически удаляет предварительный Ticket** |
| Неоформленная обычная Telegram/WEB task или Telegram group-parent | При выполнении соответствующего предиката **физически удаляет**, для WEB task пишет событие `cancelled` |
| Оформленная задача без действующего агентского ответа | Закрывает с системной пометкой «без ответа», клиенту возможен шаблон закрытия без результата; для group child возможна неполная агрегированная группа |
| Оформленный обычный `ticket` без ответа | Может закрыть администраторским исключением, очистить timer, учесть статистику, подготовить доступные Telegram post-close действия |
| `auto` без ответа | Может закрыть с отдельной системной записью; не превращать в обычный ticket |
| Есть действующий агентский ответ | Пользуется общей ветвью закрытия с особенностями `force`/`skip_client_notification` |

Перед массовым закрытием идёт guard по активным предзагрузкам для большинства объектов. Это не транзакционное массовое закрытие *вместе с клиентскими Telegram-сообщениями*: сервисные отправки могут состояться до commit, а rollback не отменяет фактическую доставку. Bulk API не является основанием безопасно пропускать клиентское уведомление без явного выбора администратора.

## 10. Физическое удаление — не закрытие

`POST /admin/delete` — **admin-only**, необратимая с точки зрения обычного UI операция. Для каждого объекта используется `_delete_ticket_hard`, который удаляет сообщения, вложения, просмотры, дочерние записи, отзывы/обратную связь и сам Ticket; физическое удаление пользовательских/архивных файлов планируется отдельно с возможными предупреждениями. Существующие `IntegrationLog` сохраняются с обнулением ссылки `task_id` (там, где выполняется этот код), а не обязательно исчезают вместе с задачей.

**Критическое уточнение к схеме:** `_delete_ticket_hard` **явно удаляет** `WebTaskResult` и все соответствующие `WebTaskResultFile` по `task_id`. Отсутствие внешнего ключа от WEB-снимка к Ticket **не является контрактом сохранения публикации после административного hard delete**. Нормальная очистка/изменение рабочего `TicketMessage` и явное удаление всей заявки — разные операции; `DATABASE.md` v0.14 исправлен по этому пункту.

Для открытой Telegram-заявки / самостоятельной задачи (не group child) может быть подготовлено клиентское уведомление до удаления, **но фактически отправляется уже после успешного DB commit** с временного снимка удалённых сущностей. Ошибка последующей доставки логируется и не возвращает удалённый Ticket в БД. Для `channel=web` этот клиентский Telegram-уведомительный путь подавлен. Если родитель и ребёнок в одном bulk-пакете, повторные удаления/уведомления пропускаются; удаление одного ребёнка может привести к частичному завершению parent.

`AdminDeleteResult` показывает `deleted`, `not_found` и `file_delete_warnings`. Предупреждения об удалении файлов важны: удаление строк БД не доказывает удаление байтов из внешнего хранилища. Не смешивать это с отменой неоформленной задачи при `admin/close`, хотя обе ветви могут использовать физический delete.

## 11. Возврат закрытой заявки в работу

`POST /{id}/restore` допускается **только для `workflow_type=ticket` со `status=closed`**. Восстановление `task` и `auto` запрещено. Администратор может восстановить любую доступную закрытую обычную заявку, support — только если **сам закрыл** её (`closed_by_user_id`). До восстановления проверяется отсутствие другой активной *готовой обычной* заявки у того же клиента; `collecting`-объекты обрабатываются отдельно.

При наличии конкурирующих `collecting`-объектов восстановление отменяет их: для настоящей предварительной Telegram-заявки может выполнить hard delete, прочим ставит `intake_state=cancelled`, `status=closed` и закрывает рабочие интервалы. Затем основной объект получает `new` с исполнителем или `unassigned` без него; сбрасываются `closed_at`, `closed_by_user_id`, `completed_by_user_id`, `completed_counted_at`, `onsite_triggered`, freeze. `StatsCompletion` отмечается `is_completed=false`, рабочий интервал открывается по допустимому текущему исполнителю.

В системной истории фиксируются возврат и инициатор; текущие Telegram review/feedback flow очищаются, клиенту может быть отправлено уведомление о восстановлении с best-effort обработкой ошибки, авто-close timer переинициализируется. Восстановление не является «новым Ticket» и не означает повторную публикацию WEB task. Специальный объект остаётся в специальном контуре, если его соответствующий признак сохранился.

## 12. Статистика: кому засчитано выполнение и когда идёт время работы

**Три разных сущности нельзя склеивать:** `Ticket.closed_by_user_id` — актор, нажавший закрытие; `Ticket.completed_by_user_id` и `StatsCompletion` — атрибуция результата; `StatsWorkInterval` — промежутки работы конкретного сотрудника. Ещё отдельно существует история доступности `StatsUserStatusInterval`.

### 12.1. `StatsCompletion`

- `sync_completion_after_close` по идентичности объекта создаёт/обновляет строку `StatsCompletion` (`is_completed=true`, `completed_at`, `completed_by_user_id`, тип и `task_kind`). `_mark_ticket_completed` синхронизирует её для обычных ветвей завершения, где вызван.
- Если закрыл **agent/trainee**, выполнением обычно считается сам актор. Если закрывал **admin**, выполнение может быть засчитано текущему назначенному `agent/trainee`, **только если он оставил действующий клиентски видимый ответ (текст или файл)**; иначе `completed_by_user_id=null`. Это защищает метрику от автоматического присвоения администратору.
- `completed_counted_at` в Ticket отражает проведённую синхронизацию; **не** эквивалент `closed_at` и не гарантирует наличие client delivery receipt.
- `sync_completion_after_reopen` очищает атрибуцию/время завершения и отмечает `is_completed=false` без требования удалить историю целиком.
- В автоматическом `finalize_group_parent_if_ready` явного `_mark_ticket_completed` **нет**; прежде чем считать parent в статистике завершений, требуется проверка прочих вызовов/тестов.

### 12.2. `StatsWorkInterval`

Рабочий интервал открывается только если объект не закрыт и не заморожен, есть назначенный сотрудник роли `agent`/`trainee` и по этому объекту/сотруднику нет уже открытого такого интервала. Админ как исполнитель **не** создаёт обычный `StatsWorkInterval`. Сервис закрывает открытые интервалы при:

| Событие | `end_reason` | После события |
|---|---|---|
| Передача другому исполнителю | `reassignment` | Попытка открыть интервал нового подходящего исполнителя |
| Снятие исполнителя | `unassignment` | Новый интервал не открывается |
| Заморозка | `freeze` | Новый интервал только после разморозки, если условия подходят |
| Закрытие | `close` | Объект закрыт, новый интервал не открывается |
| Восстановление | — | `sync_work_interval_after_reopen` пытается открыть интервал без переписывания старых |

`StatsUserStatusInterval` — **не** рабочий интервал Ticket. Он фиксирует состояния доступности активного `agent`/`trainee`, их изменение и автора admin-смены, где передан. Создание/редактирование пользователя может открыть/закрыть историю доступности независимо от назначений. Это нельзя заменять подсчётом «сколько тикетов было у сотрудника».

## 13. Уведомления и транзакционные границы

| Событие | Внешний эффект | Что гарантирует исходный код и где граница |
|---|---|---|
| Назначение | Сообщение сотруднику, иногда Telegram клиенту | Назначение и запись истории — в DB-транзакции; employee notification планируется после commit. Реальная Telegram-доставка не следует автоматически из `assign_ticket_to_agent=True` |
| Ответ / вложения | Telegram API, upload archive, WEB client events | Вне SQL-атомарности; данные квитанций и неопределённые состояния — отдельный слой `TELEGRAM.md`/`WEB.md` |
| Обычное закрытие | Telegram client text/files/review; WEB result | Telegram-сеть вызывается до основного commit; WEB `publish_result` использует DB-сессию текущего закрытия. Сбой одной системы не откатывает другую |
| Удаление администратором | Возможное сообщение Telegram | Снимок сохраняется в памяти, hard delete commit, **потом** best-effort отправка, не восстанавливающая данные при ошибке |
| Восстановление | Уведомление клиенту, очистка callback | Best-effort; в БД может остаться статус восстановленной заявки при недоступном Telegram |
| Внутренняя задача | Уведомление сотруднику о завершении | Планируется только для штатной успешной внутренней задачи; не клиентское «закрыто» |
| 20-минутное автозакрытие, backlog, WEB cleanup | Фоновые циклы | Наличие цикла не доказывает exactly-once и не отменяет необходимости смотреть конкретное состояние доставки |

Нельзя обещать атомарность внешних отправок и DB commit, exactly-once, полное отсутствие дублирования Telegram при всех рестартах или «всякая закрытая задача доставлена клиенту». В `TELEGRAM.md` уже зафиксированы различия client/staff polling offset, backlog сотруднического бота, post-close feedback и клиентских альбомов; здесь их не переописываем без новой полной выгрузки.

## 14. Сводная таблица переходов

| Из | Событие / условие | Куда / эффект | Ограничение |
|---|---|---|---|
| `collecting` | Intake закончен | `ready`; далее номер/очередь | Канальные проверки Telegram/WEB, кнопки и файлы |
| `ready + unassigned` | Успешно выбран агент | `new + assignee` | Для auto: online `agent`, не `auto`; для admin/forced иные условия |
| `new` | Ответ/приветствие/обработка неверной проблемы | Может стать `pending` | Не любое внутреннее действие меняет статус |
| `new/pending` | Заморозка | Тот же `status`, `is_frozen=true` | Закрывается рабочий интервал, очищается timer |
| `new/pending + frozen` | Разморозка | Тот же `status`, `is_frozen=false` | Может открыться рабочий интервал, timer пересчитан |
| Открытый неособый | Перевод в особые admin | `is_special=true`, ответственный admin | Нельзя применять к закрытому/auto; клиентская блокировка возможна для ticket |
| Особый | Переназначен agent/trainee | `is_special=false`, обычное назначение | Особый admin-контур очищается |

Эта таблица — навигация по **путям кода**, а не исчерпывающий конечный автомат: есть клиентские Telegram callback, автоочистка, восстановление загрузок и системные задания, которые имеют собственные предусловия.

## 15. Контрольный список потенциальных инвариантов для следующего документа

В `INVARIANTS.md` следует **разделить** «доказано кодом», «ожидается продуктом» и «пока не проверено». Приоритеты:

1. **Group parent:** автоматическая финализация требует всех закрытых детей, но ручное закрытие parent в staff endpoint не показывает той же проверки; проверить желаемую политику и тесты.
2. **WEB result retention:** при обычном закрытии публикуется DB snapshot, при явном admin hard delete он **удаляется**; проверить политики retention и клиентские последствия, не гадать по отсутствию FK.
3. **Доступ к закрытым:** `agent`/`trainee` получает широкий просмотр `/closed` и карточки закрытого; сверить с задачей разграничения доступа, не объявляя автоматически уязвимостью.
4. **Разные ветви закрытия:** обычное, принудительное, клиентское, автозакрытие, группа и отмена intake имеют разные guards и delivery order; проверить тестами, что это осознанно.
5. **Кому засчитывается работа:** admin force без ответа даёт `completed_by=null`, а group parent auto-finalize не явно проводит completion; проверить фактические отчёты, не переписывая статистику по одному подсчёту ticket.status.
6. **Сетевые эффекты до commit:** идемпотентность, ошибки required attachments, partial publish, отказ уведомления после hard delete; искать точные записи receipts/retry.
7. **Роли/компания/видимость:** различие list/card для call-center, отдельная видимость parent, права close/restoration; проверить сквозную непротиворечивость.
8. **Состояния загрузок:** блокировка только активных upload/sending не гарантирует success; проверить обработку failed/uncertain в каждой ветви.
9. **Фоновые процессы:** конкурентные scheduler/materialization, auto-close, WEB cleanup, employee backlog и restart safety; не объявлять «выполнено один раз» без данных.
10. **DB-уровень:** фактические FK/index/unique DEV и PROD, ручные миграции — только отдельно разрешённым read-only аудитом, без запуска `ensure_*` ради документирования.

Эти пункты — **исследовательские вопросы и условия проверки**, а не список подтверждённых дефектов. Никаких патчей из них автоматически не следует.
