## 1. Назначение и точки входа

В backend работают **два независимых polling-цикла**:

| Поток | Цикл и обработчик | Особенности |
|---|---|---|
| Клиентский Telegram-бот | `api/app/services/telegram_polling.py:telegram_polling_loop()` → `routers/telegram.py:process_telegram_update()` | Использует обычный токен бота; открывает сессию БД на обработку update; выполняет очистку истёкших намерений задач и автозакрытие между запросами к Telegram |
| Сотруднический Telegram-бот | `api/app/services/employee_telegram_polling.py:employee_telegram_polling_loop()` → `services/employee_telegram_bot.py:process_employee_telegram_update()` | Использует `employee_telegram_bot_token`; собственные polling timeout и сессии обработки |

Оба цикла запускаются из `api/app/main.py` условно, в зависимости от соответствующих настроек и наличия токенов. Вызов Telegram Bot API идёт через `services/telegram_bot.py:get_updates()` и исполняется с помощью `asyncio.to_thread(...)`.

**Важная техническая деталь:** в клиентском цикле offset обновляется до вызова обработчика каждого update; в сотрудническом — после успешной обработки update. При ошибках циклы повторяют работу после паузы. Это необходимо учитывать при дальнейшем анализе повторной доставки и гарантий обработки. Нельзя утверждать, что все события обрабатываются *ровно один раз*.

## 2. Входящее клиентское событие

Подтверждённая последовательность:

```text
Telegram getUpdates
  → telegram_polling_loop()
    → _process_update_sync() / отдельная SessionLocal
      → process_telegram_update(db, payload, notify_client=True)
        → [для некоторых групповых автоматизаций: chat_lock + recover]
        → _process_telegram_update(...)
          → поиск TelegramUpdate по update_id
          → выбор ветки: callback_query / message / edited_message / иное
          → бизнес-операция, запись в БД, ответ клиенту при необходимости
```

`_process_telegram_update()` проверяет `TelegramUpdate.update_id` на повтор; для обработанных событий используется модель `TelegramUpdate`, содержащая идентификатор и сохранённый payload. Точные границы транзакций и поведение при сбое между внешним ответом Telegram и commit требуют отдельного аудита.

Для **callback_query** код извлекает `chat_id`, `from_user`, проверяет приватный чат, наличие компании и доступ контакта через `evaluate_incoming_telegram_access()`. Обрабатываются, в частности, действия кнопок меню, закрытие, специальные автоматизации, подтверждения. Для обычных сообщений/редактирований предусмотрены проверки типа чата и доступа, регистрация контакта, вложения, направления в действующие сценарии. Регистрация Telegram-группы — отдельное исключение из общего запрета обработки неприватных чатов.

`process_telegram_update()` до основной обработки может взять блокировку по чату (`telegram_group_automation.chat_lock()`), обновить состояние ORM и выполнить `telegram_group_automation.recover()` для сценариев групповых автоматизаций и связанных ожиданий. Полный контракт конкурентной обработки пока не проверен.

При получении результата со статусом `unassigned` и `ticket_id` клиентский polling ставит фоновую повторную проверку через **3 секунды**. Уведомление «На распределении» отправляется только если обращение всё ещё соответствует условиям: обычная незакрытая заявка, `READY`, `UNASSIGNED`, без ответственного, не специальная, не замороженная, уведомление ещё не отправлялось; контакт существует, не заблокирован и имеет `external_chat_id`. После успешной отправки заполняется `distribution_notice_sent_at`.

## 3. Типы и состояния обращений

Текущие значения перечислений в `api/app/models.py`:

| Поле | Значения | Что означает |
|---|---|---|
| `workflow_type` | `ticket`, `task`, `auto` | Тип рабочего сценария |
| `task_kind` | `normal`, `group_parent`, `group_child` | Разновидность задачи |
| `intake_state` | `collecting`, `ready`, `cancelled`, `telegram_group_copy` | Стадия оформления обращения |
| `status` | `unassigned`, `new`, `pending`, `closed` | Рабочий статус |

**Не смешивать `intake_state` и `status`.** Например, `ready + unassigned` — оформленное обращение без назначенного исполнителя. Это не то же самое, что предварительный `collecting + unassigned`.

### 3.1. Предварительное создание

`routers/telegram.py:_create_collecting_ticket()` создаёт запись `Ticket` с `intake_state=collecting`, `status=unassigned`, `assignee_id=None`, `channel=telegram` (по умолчанию), системной записью о начале оформления и постановкой обновления аватара. На этой стадии номер обращения ещё не присваивается указанной функцией.

`_prepare_collecting_ticket_for_button()` настраивает тип в зависимости от выбранной кнопки:

| Кнопка | `workflow_type` | `task_kind` | `agent_visible` | `load_counted` |
|---|---|---|---|---|
| `ticket` / обычная ветка | `ticket` | `normal` | `True` | `True` |
| `task` | `task` | `normal` | `True` | `True` |
| `group_task` | `task` | `group_parent` | `False` | `False` |
| `auto` | `auto` | `normal` | `True` | `False` |

Дополнительно сохраняются ключи кнопки и инструкция; в меню «колл центр» инициируется актуализация данных сотрудника КЦ.

### 3.2. Оформление и распределение

`_ready_ticket_for_distribution()` переводит обращение в `intake_state=ready`, вызывает `ensure_ticket_number()` и сохранение снимка данных сотрудника КЦ, после чего последовательно пробует:

1. Фиксированного ответственного из настроек кнопки (`_apply_fixed_assignee_from_setting()`; внутренние условия ещё предстоит изучить).
2. Принудительного ответственного из `ButtonSpec` (`_try_forced_assignment()` → `assign_ticket_to_forced_user()`).
3. Общий выбор доступного сотрудника (`choose_online_agent()` → `assign_ticket_to_agent()`).
4. Если назначить не удалось — обращение остаётся на распределении, добавляется системное сообщение.

На этапе создания применяются флаги кнопки. Для задач при определённых условиях убирается клиентская кнопка закрытия; подробные правила закрытия — отдельный будущий раздел.

**Отдельные пути:** `_ensure_ticket_for_incoming()` создаёт обычную заявку непосредственно в `ready` при отсутствии активной заявки. `_create_task_from_intent()` тоже создаёт задачу непосредственно в `ready`, однако в просмотренном `api/app` найдена только её декларация — использовать функцию как доказательство реально действующего пользовательского сценария нельзя без проверки вызовов. Наличие прямого пути не означает, что он используется при обычном выборе кнопки.

## 4. Автоматическое и принудительное назначение

Источник: `api/app/services/assignment.py`.

### 4.1. Обычный выбор агента

`choose_online_agent(db, company_id)` рассматривает пользователей **той же компании**, для которых выполняются все условия:

- `role == "agent"`;
- `is_active == True`;
- `availability_status == "online"`.

Из них выбирается минимум по кортежу:

1. `agent_active_load()` — число заявок с `assignee_id` выбранного агента, статусом `new` или `pending`, `is_frozen=False` и `load_counted=True`.
2. `last_assigned_at` — более раннее время выигрывает (`NULL` трактуется как `datetime.min`).
3. `full_name` — последний критерий сортировки.

`assign_ticket_to_agent()` разрешает назначение только для `status=unassigned`, `intake_state=ready`, не-`auto` и агента `agent`/активного/`online`. При успехе записывает ответственного, переводит статус в `new`, обновляет время последнего назначения, синхронизирует интервалы статистики, пишет системное сообщение, выполняет hook для `GROUP_PARENT` и планирует уведомление сотруднику. Уведомление клиенту о сотруднике включено не для всех типов обращений.

### 4.2. Принудительное назначение

`resolve_forced_assignee()` разрешает поиск по `login` или `user_id` и требует активного пользователя с ролью **`agent` или `trainee`**. Этот путь **не проверяет `availability_status=online`**. `assign_ticket_to_forced_user()` напрямую присваивает такого сотрудника и переводит обращение в `ready`/`new` (если не закрыто). Поэтому не смешивать его с обычным распределением; точные дополнительные ограничения фиксированного назначения из настроек кнопки ещё не изучены.

Если принудительный ответственный не найден, неактивен или имеет недопустимую роль, `_try_forced_assignment()` записывает объяснение в систему и возвращает управление общему распределению.

### 4.3. Очередь и назначение администратором

`assign_unassigned_fairly()` выбирает неназначенные, оформленные, незамороженные, неавтоматические обращения по времени создания и для каждого повторно выбирает наименее нагруженного онлайн-агента. В выборку входят видимые агентам обращения и отдельно `group_parent`.

`assign_unassigned_to_agent()` выбирает такую очередь для конкретного онлайн-агента и пытается назначить ей все подходящие обращения; из одного лишь определения функции неизвестно, где именно вызывается этот путь.

`assign_ticket_by_admin()` — отдельный путь административного назначения: обновляет ответственного и `intake_state`, записывает историю, запускает hook для `GROUP_PARENT` и уведомления. Не подменять административный процесс ограничениями автоматического выбора агента.

## 5. Нумерация

Источник: `api/app/services/ticket_numbering.py:ensure_ticket_number()`.

Если номер уже есть, возвращается текущий. Иначе в PostgreSQL берётся транзакционная advisory-блокировка (`pg_advisory_xact_lock`), атомарно увеличивается `TicketNumberCounter.last_number` через `UPDATE ... RETURNING`, записывается `ticket.ticket_number` и выполняется `flush`. Для инициализации счётчика предусмотрен путь на основе максимального существующего номера. Это защита от конкурентного выделения номеров в предусмотренном механизме; схемные уникальные ограничения и поведение всех сторонних путей записи ещё не проверены.

## 6. Групповые задачи: `GROUP_PARENT` и `GROUP_CHILD`

Выбор кнопки `group_task` помечает родителя как `workflow_type=task`, `task_kind=group_parent`, `agent_visible=False`, `load_counted=False`.

`_create_group_children_from_collecting(db, parent, button, client_body, assignee)`:

- сначала проверяет, есть ли у родителя хотя бы один `group_child`, и при наличии не создаёт детей повторно;
- обеспечивает номер родителя, пишет системную запись;
- для каждого `button.subtasks` создаёт отдельный `Ticket` с `task_kind=group_child`, `parent_ticket_id` и собственным номером;
- переносит текст клиента, настройки дочерней кнопки и флаг `suppress_client_answer`;
- выбирает индивидуально заданного принудительного исполнителя дочерней задачи, иначе использует назначенного родителю сотрудника; синхронизирует статистику и добавляет системные сообщения.

В обработке завершения задачи непосредственное создание детей происходит при наличии назначенного исполнителя родителя. Дополнительно `routers/telegram.py:_on_group_parent_assigned()` регистрируется через `set_group_parent_assigned_hook()` и вызывается из `assignment.py` при обычном либо административном назначении родителя. Это обеспечивает механизм **отложенного** создания дочерних задач после появления исполнителя.

**Подробнее о завершении, удалении и сохранности результатов — в разделе 10.**

**Граница проверки:** наличие первого ребёнка исключает повторный вызов полного создания, но вопрос восстановления частично созданного набора детей и всех транзакционных/аварийных сценариев не изучен. Также требуется проверить все фактические пути принудительного назначения родителя.

## 7. Рабочее время Telegram

Источник: `api/app/services/telegram_intake_hours.py:is_telegram_intake_open()`.

- **Пн–сб:** с **07:50 включительно** до **19:00 исключительно** по `Europe/Moscow`.
- **Воскресенье:** приём закрыт целиком.
- При передаче собственного времени функция ожидает timezone-aware `datetime` (для naive выбрасывает `ValueError`).

`_is_hours_limited_button()` ограничивает обычные `ticket`, `task`, `group_task`, исключая определённые специальные автоматизации (`telegram_group`, сценарии происхождения клиента/телефона Bitrix, `message_only`, `send_files`). Само выполнение исключённой автоматизации и **передача её сотруднику** — разные операции.

В `routers/telegram.py` предусмотрены повторные проверки времени при выборе кнопки, подтверждении и в нескольких точках завершения создания. При закрытом приёме `_block_button_after_hours()` выводит шаблон `telegram.after_hours.creation_blocked.client` и удаляет предварительный черновик **только если** он проходит дополнительные проверки безопасности. Нельзя считать это правилом удаления любых открытых обращений.

Для обычной задачи в состоянии `collecting` при получении описания после закрытия приёма вызывается блокировка. Также есть проверка таймаута отправки описания; его значение задаётся константой `TASK_DESCRIPTION_TIMEOUT_MINUTES` (значение не извлекалось в этом проходе).

### 7.1. Фоновая очистка

`api/app/services/telegram_after_hours_cleanup.py:run_telegram_after_hours_cleanup_once()`:

- работает только вне часов приёма;
- сканирует партии до 50 подходящих `collecting`, `unassigned` Telegram-обращений;
- перед удалением проверяет отсутствие ответственного, закрытия, номера, родителя, клиентских сообщений, дочерних задач, признаков автоматизации, специальной/внутренней задачи;
- удаляет только подтверждённые предварительные обычные заявки и ещё не созданные обычные задачи / `GROUP_PARENT` через специальные функции удаления;
- фиксирует удаление в БД **до** попытки отправить уведомление клиенту; ошибка Telegram при отправке уведомления не отменяет commit.

**Место запуска подтверждено шагом 38:** `internal_task_scheduler.py:internal_task_scheduler_loop()` вызывает `run_telegram_after_hours_cleanup_once()` в каждом цикле, затем после всех других операций спит 30 секунд. Это не обещание точного 30-секундного интервала: продолжительность остальных задач добавляется. Конкурентные пограничные случаи на границе 19:00 и живой прогон не проверены (раздел 21).

### 7.2. Передача автоматизации сотруднику

В `api/app/services/telegram_automation.py:_handoff_automation_task_to_agent()` перед передачей Telegram-задачи сотруднику выполняется отдельная проверка времени. Если приём закрыт, `_block_automation_handoff()` делает автоматическое обращение невидимым агенту, исключает из подсчёта нагрузки, завершает сценарий без передачи и использует сообщение `telegram.after_hours.automation_handoff_blocked.client`.

## 8. Клиентские команды, первое подключение и обработка сообщений

Источники: `api/app/routers/telegram.py` (`_process_telegram_update()`, `_active_ticket_for_client()`, `_collecting_ticket_for_client()`, `_append_client_message()`), `api/app/services/telegram_onboarding.py:process_first_connection_start()`.

### 8.1. Поиск активного обращения и предварительного черновика

- `_active_ticket_for_client()` выбирает по компании и клиенту **незакрытую обычную заявку** (`workflow_type` не `task` и не `auto`, либо `NULL`) с `intake_state=ready` либо `NULL`, сортируя по последнему `updated_at`. **Обычные задачи и автоматизации в этом запросе не считаются активной обычной заявкой.**
- `_collecting_ticket_for_client()` отдельно ищет Telegram-запись с `status=unassigned`, `assignee_id=NULL` и `intake_state=collecting`, также по последнему обновлению. Это не тот же запрос, что активная заявка.
- `_task_for_client_album()` — специальный путь поиска задачи для вложения из Telegram-альбома через `media_group_id`; полную защиту от смешивания альбомов ещё не проверяли.

### 8.2. `/start`

При наличии уже активной обычной заявки система не создаёт вторую; записывает попытку `/start` в системную историю и сообщает клиенту, что сообщения будут добавлены в текущую заявку. Кнопка закрытия показывается, только если её разрешает `client_can_close_ticket()`.

Если активной обычной заявки нет, код проверяет `ClientProfile`:

```python
has_destination = bool((profile.destination or "").strip()) if profile is not None else False
needs_onboarding = bool(profile is None or not profile.is_verified or not has_destination)
```

При `needs_onboarding=True` и отсутствии активной заявки запускается `process_first_connection_start()`; вне часов приёма этот путь блокируется. Сервис первого подключения вызывает `_ensure_ticket_for_incoming()` (обычная заявка `ready`, при отсутствии действующей — с назначением либо очередью), добавляет сообщение для сотрудника и отправляет клиенту первоначальный текст с кнопкой закрытия. Если сотрудник уже назначен, клиенту дополнительно отправляется уведомление об ответственном.

Если первый сценарий не требуется, создаётся или повторно используется черновик `collecting` и показывается соответствующее меню. Повторный `/start` обновляет меню и убирает старые клавиатуры. **Тонкость рабочего времени:** обычный черновик для уже проверенного клиента может создаться вне времени приёма; это не означает разрешения завершить создание полноценного обращения после 19:00 — соответствующие запреты проверяются отдельно.

**Бизнес-правило требует отдельного уточнения, без правок кода в рамках документирования.** Пользователь уточнил, что смысл флага «Верификация» (`is_verified`) — разрешить прекращение повторного первого подключения, а подразделение необходимо для выбора меню. Однако **текущий код** также требует непустого сырого `profile.destination`; поэтому `is_verified=True`, `destination=пусто` может вызвать первый сценарий повторно. При этом выбор меню использует `temporary_rop_destination(profile)` и `BotMenuDestinationBinding`, а не только прямое поле `profile.destination`: если нет подходящего связывания, используется базовое меню `BASIC_MENU_NAME`. **Нельзя без проверки отождествлять `destination` с полем `department`**: обе колонки существуют в `ClientProfile`. Предлагаемое бизнес-решение — отдельная валидация установки верификации при незаполненном обязательном подразделении в карточке клиента/API; точное поле и условия нужно исследовать отдельно. Не выполнять временный хардкод-обход в Telegram.

### 8.3. Обычное входящее сообщение

В обработчике до обычного добавления сообщений предусмотрены специальные ветки (в частности, ожидание телефона Bitrix, происхождение клиента, Telegram-группы, отзывы и обратная связь, обработка редактирования сообщений и запрещённых типов вложений). Нельзя утверждать, что любое сообщение сразу направляется в `TicketMessage` активной заявки.

Если клиент находится в черновике **обычной задачи** (`workflow_type=task`), текст описания обрабатывается как завершение создания задачи. Есть проверка часов приёма и таймаута `TASK_DESCRIPTION_TIMEOUT_MINUTES` с раздельной отменой или безопасным удалением ещё не оформленных задач, включая `GROUP_PARENT`. Перед оформлением могут обрабатываться автоматизации; затем клиентское сообщение и вложения, номер, распределение и при необходимости дочерние задачи.

В иных случаях поиск идёт через Telegram-альбом или `_active_ticket_for_client()`. Если активной обычной заявки нет, произвольный текст **не создаёт новую заявку**, а возвращает `problem_type_required` (с подсказкой выбрать тип проблемы). При существующей заявке `_append_client_message()` записывает `TicketMessage` с `message_type=client`, `telegram_message_id`, `replaced_message_id` при необходимости и временем; снимает заморозку **обычной** заявки, если она была заморожена, обновляет `updated_at` и при обычном сценарии планирует уведомление сотруднику. Вложения учитываются отдельно; для них может планироваться отдельное уведомление. Сообщение клиента также обновляет таймер автозакрытия.

### 8.4. Клиентское закрытие `/close` и кнопкой

Источник: `api/app/services/telegram_client_close.py`.

**Кнопка закрытия** проверяется через `client_can_close_ticket()` (при условии, что обращение не закрыто):

| Сценарий | Условие допуска callback закрытия |
|---|---|
| Обычная заявка `ticket`/`normal` | Пока не закрыта; даже при назначенном сотруднике |
| Обычная задача `task`/`normal` | Пока `intake_state=collecting` |
| Иные задачи, включая `group_parent` | Пока `assignee_id is None` |
| `workflow_type=auto` | Техническая проверка `assignee_id is None` (не означает, что автоматизация обычно имеет исполнителя) |
| Оставшиеся нестандартные сочетания | Если не было сообщения сотрудника (`has_agent_message()`) |

**Команда `/close`** вызывает `close_active_ticket_for_contact()` и использует поиск активной *обычной* заявки либо предварительного черновика; она не сводится полностью к условиям видимости inline-кнопки. Предварительные безопасные заявки и неоформленные задачи могут **удаляться**, а полноценные обращения переводятся в `status=closed`, получают `closed_at`, снимаются с заморозки, обновляют статистику и историю. Поэтому не описывать `/close` как универсальное закрытие любой обычной задачи или автоматизации.

При закрытии **неназначенной обычной заявки** отправляется отдельный шаблон `telegram.ticket.close.unassigned.client` **без запуска цикла оценки**. Для прочих подходящих обращений `send_client_close_notification()` может подготовить оценку и дополнительные действия после закрытия. Полные условия отзывов/feedback ещё не исследованы.

## 9. Ответ сотрудника клиенту, закрытие и восстановление

Источники: `api/app/routers/tickets.py`, `api/app/services/ticket_messages.py`, `api/app/services/ticket_lifecycle.py`, `api/app/services/telegram_client_close.py`.

### 9.1. Отправка ответа

Маршрут `POST /{ticket_id}/reply` (`routers/tickets.py:reply()`) делегирует обработку в `services/ticket_messages.py:reply_to_ticket()`; роутер передаёт функции отправки в Telegram, сохранения файлов, захвата preload, фоновой доставки и обновления таймеров. `can_reply()`/`can_comment()` проверяют разные разрешения; закрытая заявка недоступна для ответа (`ticket_closed_readonly`). Внутренний комментарий **не отправляется клиенту**.

**Обычная Telegram-заявка, текст без вложений:** при доступном Telegram-контакте текст отправляется через `_send_to_telegram_client()` **до** записи итогового `TicketMessage`; из ответа извлекается `telegram_message_id`, сохраняемый у сообщения сотрудника. Отправка использует подготовку Telegram HTML, а при ошибке разбора разметки повторяется без форматирования. Если обязательная отправка не удалась, возникает ошибка `telegram_send_failed`; сервис предусмотрел сохранение записи о сбое доставки. Точное поведение при отказе БД *после успешной внешней отправки* остаётся открытым вопросом.

**Обычная Telegram-заявка с вложением:** сначала создаётся сообщение сотрудника и сведения о файлах/preload, обновляется заявка, выполняется `db.commit()`, а затем ставится **отдельная фоновая доставка** через `deliver_ticket_attachment`. Ответ API `ok=True` **не подтверждает успешную доставку файлов клиенту**. Готовый preload и загружаемый файл могут находиться в разных состояниях (`sending` / `uploading`). На этом пути есть ограничения: для обычной заявки допускается один preload за ответ; нельзя в одном запросе сочетать preload и raw-файл; `quick_action` разрешает только обычный текст. Полную модель подтверждения/повтора отправки ещё не исследовали.

**Задача (`workflow_type=task`):** текстовый ответ сотрудника не отправляется клиенту по маршруту обычной заявки сразу: он сохраняется для дальнейшего формирования результата задачи при закрытии. Загрузка вложений для задач, включая Telegram-архив, имеет отдельную логику; статус `sent` в архивном пути сам по себе не равен подтверждению доставки конечному клиенту.

**Общие побочные эффекты ответа:** при обычном внешнем ответе `new` может перейти в `pending`, перезапускается таймер автозакрытия, может сниматься заморозка, очищаться черновик редактора. Для определённой «выездной» фразы у агента существует установка `onsite_triggered` и изменение статуса сотрудника на `on_ticket`. Сами фразы и бизнес-предикат `is_onsite_phrase` пока не проверяли.

**Редактирование:** в открытой Telegram-заявке сообщение сотрудника можно редактировать при наличии права `can_edit_messages`; обычный пользователь — только своё, администратор — чужие. Текст/подпись редактируется через Telegram API, **затем** обновляется запись БД. Закрытые, удалённые или не имеющие Telegram ID внешние сообщения нельзя менять по этому пути. Удаление сообщений требует отдельного анализа, не переносить на него без проверки правила редактирования.

### 9.2. Закрытие сотрудником / администратором

Маршрут `POST /{ticket_id}/close` требует `can_manage_ticket()`, вызывает `close_ticket_by_actor()` и затем `db.commit()`. Повторное закрытие отвергается. При обычном сценарии закрытие полноценного обращения **требует сообщения сотрудника**; при его отсутствии возвращается `close_not_allowed`. **Администратор** имеет отдельный путь принудительного закрытия без ответа через другие административные операции; его не следует путать с обычным маршрутом `close`.

Закрытие обычной заявки, задачи и дочерней групповой задачи — **разные бизнес-операции**. Для `task` результат может быть собран из последнего ответа и вложений; для `group_child` и `group_parent` применяются специальные процедуры закрытия/агрегации, включая `finalize_group_parent_if_ready()`. Есть защита от завершения задачи при незаконченной загрузке вложений (`ensure_task_uploads_finished()`). Порядок агрегации, завершения, принудительного закрытия и административного удаления описан в разделе 10.

### 9.3. Восстановление закрытой обычной заявки

Маршрут `POST /{ticket_id}/restore` (`routers/tickets.py:restore()`):

- требует `can_manage_ticket()`, исходный `status=closed` и **только обычный `workflow_type=ticket`**; для `task` и `auto` возвращает `restore_not_allowed`;
- для неадминистратора требует `closed_by_user_id == user.id`; администратор может восстановить закрытую заявку вне зависимости от автора закрытия;
- запрещает восстановление при другой действующей обычной заявке того же клиента (`client_has_active_ticket`), но не при всех вообще задачах/автоматизациях;
- предварительно удаляет допустимые предварительные черновики клиента и отменяет остальные `collecting` с соответствующим обновлением статистики;
- возвращает статус `new`, если ответственный есть, иначе `unassigned`, обнуляет поля закрытия/завершения, снимает заморозку, синхронизирует статистику, записывает системные события и отменяет/очищает текущие сценарии ввода отзывов и обратной связи **без удаления уже сохранённых оценок и замечаний**;
- пытается уведомить клиента (`telegram.ticket.restore.client`) и перезапускает таймер автозакрытия. Ошибка необязательного уведомления не отменяет восстановление.

**Подтверждённое бизнес-правило владельцем проекта:** восстановление **не должно менять ответственного, независимо от `online`/`offline`** и не запускает автоматического перераспределения. Если заявку восстановил закрывший её сотрудник — дальнейшая обработка его ответственность. Если восстановил администратор — он сам отвечает за ручную передачу другому сотруднику при необходимости. **Не добавлять автоматическое переназначение при восстановлении.**

**Технический нюанс:** для `is_special=True` в просмотренном коде предусмотрено заполнение *пустого* `assignee_id` из `special_assignee_id` при восстановлении. Это отдельное поведение **особых заявок**, не доказательство перераспределения обычных заявок. При документировании/проверке инварианта сохранения ответственного в будущем следует обсудить его отдельно; сейчас код не меняется.

## 10. Обычные и групповые задачи: ответ, завершение и административное удаление

Источники исследования (шаги 12–15): `api/app/services/ticket_lifecycle.py`, `api/app/routers/tickets.py`, `api/app/services/ticket_admin_actions.py`, `api/app/services/telegram_outbound_delivery.py`. Дополнительно **прочитан код**, но **не выполнен запуск** регрессионных тестов `tests/test_admin_delete_regression.py`, а также найдены проверки в `tests/test_task_upload_close_guard.py`, `tests/test_ticket_lifecycle_close.py` и смежных тестах.

### 10.1. Обычная задача `task / normal`

В отличие от обычной переписки по заявке, ответ сотрудника по задаче сохраняется для **итоговой выдачи клиенту при завершении**. В `close_ticket_by_actor()` берутся первое клиентское сообщение и последний актуальный `AGENT`-ответ; к последнему ответу привязаны итоговые вложения. Для задач канала `web` предусмотрен отдельный путь публикации результата (`web_task_results.publish_result`) — его детали в этом разделе не исследовались.

`_format_task_completion_text()` формирует текст из темы задачи, даты создания в `settings.app_timezone`, исходного клиентского сообщения и результата сотрудника. Для обычной задачи используются шаблоны автоматических сообщений:

- `telegram.task.completion.with_answer`, если итоговый ответ содержит текст (допускается перечень файлов в тексте);
- `telegram.task.completion.files_only`, если текст ответа пустой и результат оформляется файлами.

При отсутствии либо ошибке пользовательского шаблона предусмотрен fallback. Далее при закрытии через `close_ticket_by_actor()` итоговое уведомление и вложения направляются клиенту, если это допускают тип задачи, внутренний режим и административные флаги. **Наличие статуса `sent` при загрузке в Telegram-архив не следует без проверки приравнивать к доставке файла конечному клиенту.**

**Обычное закрытие задачи без ответа сотрудника запрещено** (`close_not_allowed`). Отдельный административный маршрут `POST /admin/close` вызывает `close_ticket_by_actor(..., force_without_agent_reply_for_task=True)` и может принудительно закрывать без ответа. Безопасные *ещё не созданные* черновики задач обрабатываются отдельно (вплоть до удаления), и их нельзя путать с полноценными задачами.

### 10.2. Сбор ответов `GROUP_CHILD` → `GROUP_PARENT`

При закрытии дочерней задачи с ответом `_close_group_child_if_ready()` находит родителя. Если у дочерней задачи `suppress_client_answer=False`, она:

1. Создаёт в **родителе** сообщение типа `AGENT` с текстом **последнего** ответа по ребёнку.
2. Создаёт в родителе записи вложений этого ответа, сохраняя метаданные Telegram/архива, имя, тип и путь файла; это **отдельные записи БД**, потенциально ссылающиеся на тот же физический файл/сообщение архива.
3. Вызывает проверку автоматического завершения родителя.

Если `suppress_client_answer=True`, результат конкретной дочерней задачи **не добавляется** в клиентскую сводку, но сама задача участвует в общей логике завершения.

`_group_parent_children_payload()` **предпочитает уже агрегированные сообщения `AGENT` на уровне родителя** и их вложения. Для старых данных, где агрегированных сообщений нет, предусмотрен fallback: прочитать дочерние задачи и взять последние ответы, пропуская `suppress_client_answer=True`. Поэтому механизм не зависит только от существования исходной дочерней переписки после корректной агрегации. Наличие fallback не означает восстановление всех частично/некорректно записанных данных.

### 10.3. Автоматическое завершение родителя

`finalize_group_parent_if_ready()` применима только к открытой задаче вида `group_parent`:

- выполняет `db.flush()`, затем проверяет, **не осталось ли у родителя дочерних задач со статусом, отличным от `closed`**;
- при наличии хотя бы одной открытой дочерней задачи **оставляет родителя открытым**;
- если все дети закрыты или удалены и открытых больше нет, вызывает `ensure_task_uploads_finished(db, parent)`;
- собирает текст и файлы, формирует `telegram.group_task.completion.with_answers` либо `telegram.group_task.completion.files_only` (с fallback), отправляет результат и допустимые вложения клиенту при разрешённом уведомлении;
- проставляет родителю `status=closed`, `closed_at`, сбрасывает заморозку, обновляет учёт времени и добавляет системное сообщение.

**Нужно различать:** отсутствие *открытых* дочерних задач — условие завершения, но не гарантия, что каждый исполнитель предоставил содержательный ответ. Проверка незаконченных загрузок распространяется на родителя и его дочерние задачи. Статусы `uploading`/`sending` для актуальных вложений и относящихся к ним preload блокируют обычное завершение с ошибкой `task_attachments_uploading`.

### 10.4. Принудительное закрытие и удаление

`_close_task_without_reply()` используется для **принудительного закрытия администратором**, а не как обычное действие сотрудника. При принудительном закрытии `group_child` родитель проверяется на возможность завершения; при отсутствии других открытых детей возможна итоговая отправка с пометкой в системном сообщении «возможен неполный ответ». Это предусмотренная административная ветка.

Административное **удаление** в `routers/tickets.py:admin_delete_tickets()` использует `_delete_ticket_hard()` из `ticket_admin_actions.py`:

- удаление **одного `GROUP_CHILD`** удаляет выбранную дочернюю задачу и её переписку/записи вложений, но **не удаляет `GROUP_PARENT` и соседние дочерние задачи**; после удаления запускается проверка завершения родителя;
- удаление **самого `GROUP_PARENT`** через `_delete_ticket_hard()` удаляет родителя и все найденные непосредственные дочерние задачи вместе с относящимися записями;
- при массовом удалении родителя и его детей одновременно предусмотрен пропуск повторной финализации и защита от дублирующихся уведомлений;
- подготовка уведомлений идёт внутри транзакции, **отправка после успешного `db.commit()`**; ошибка Telegram после commit не возвращает удалённые записи, а логируется.

**Кодовые тесты, прочитанные на шаге 15:** `test_active_group_child_defers_parent_text_and_attachment` проверяет сохранность агрегированного ответа/файла родителя при удалении ребёнка, `test_closed_child_with_open_sibling_keeps_parent_open` — сохранение открытого родителя и соседней задачи; `test_parent_and_child_bulk_does_not_double_notify` — отсутствие дублирования уведомлений. Это **ожидаемое поведение по тестам**, а не результат их запуска в нашем сеансе.

### 10.5. Очистка файлов и защита общих ресурсов

`telegram_outbound_delivery.py:schedule_ticket_upload_delete()` собирает локальные пути и ID сообщений технического Telegram-архива для удаляемых обращений, удаляет относящиеся `TicketAttachmentPreload` в текущей транзакции и регистрирует отложенную физическую очистку.

Обработчик SQLAlchemy `after_commit` удаляет внешние ресурсы **только после фиксации удаления**, проверяя оставшиеся ссылки: `_archive_message_referenced(...)` для сообщений архива и `_safe_unlink(..., db=...)` для локальных файлов. При `after_rollback` план очистки сбрасывается. Это особенно важно, если копия вложения уже находится в родителе и ссылается на тот же ресурс. При ошибках очистка записывает предупреждения/лог; **это не абсолютная гарантия** удаления всех внешних ресурсов.

### 10.6. Подтверждённая бизнес-логика и нецелевой крайний случай

**Правило, подтверждённое владельцем ES DESK:** удаление или принудительное закрытие дочерней задачи **не должно ломать родительскую задачу** или уничтожать уже собранный итог. Обычный сотрудник не закрывает задачу без ответа — это отдельное право администратора. Если администратор удалил или принудительно завершил абсолютно все подзадачи без полезных ответов, это исключительная ситуация; обычно рассматривается административное удаление также и родителя. **Не проектировать ради неё новую ветку обработки без отдельного запроса.**

**Наблюдение по коду (без задачи на исправление):** при `answers=[]` форматтер групповой задачи выбирает шаблон «Получены файлы от сотрудников» независимо от фактического числа файлов. В крайне редком случае отсутствия **и** ответов, **и** файлов сообщение может быть смыслово неточным. Зафиксировано только как возможный крайний случай, не как подтверждённый эксплуатационный дефект.

**Остаётся вне границ этого прохода:** фактический запуск тестов на текущем Git HEAD; полные конкурентные гарантии, все состояния доставки и повторов вложений, инициализация всех групповых задач и дополнительные административные сценарии.

## 11. Автоматизации: граница бизнес-сценария

`workflow_type=auto` означает, что обращение обрабатывает система, **не обычный исполнитель и не очередь распределения**. Из кода назначения известно, что `assign_ticket_to_agent()` отвергает `auto`. Технический предикат `client_can_close_ticket(... auto ...)` проверяет отсутствие ответственного, но **не подразумевает, что системе нужен ответственный**.

Если автоматизация должна передать процесс человеку, код может преобразовать обращение в `workflow_type=task`, `task_kind=normal`, `agent_visible=True`, `load_counted=True` и вызвать распределение (`_fallback_auto_to_support()` в `routers/telegram.py`). Отдельные пути `_handoff_automation_task_to_agent()` накладывают ограничение рабочего времени на саму передачу. Все условия переходов и исключения ещё не проверены по полной карте автоматизаций.

### 14.1. Независимые клиентские действия

В `post_close_actions_markup()` доступны две независимые кнопки, формируемые на основании `available_post_close_actions()`:

| Кнопка | Назначение | Условия доступности | Данные |
|---|---|---|---|
| «Оставить отзыв» | Оценить конкретного сотрудника | Обычная закрытая заявка `workflow_type=ticket`, `task_kind=normal`; действующий цикл в `offered`, принадлежащий данному клиенту/заявке; оценка по циклу ещё не завершена | `TicketReviewCycle` + `TicketReview` |
| «Предложения и замечания» | Сообщить замечание/предложение по обращению, **без оценки сотрудника** | Закрытое обращение `workflow_type=ticket` или `task`, подходящий Telegram-контакт; для данного `ticket_id` ещё нет сохранённого `TicketFeedback` | `TicketFeedbackInput` + `TicketFeedback` |

`workflow_type=auto` ни в одном из этих маршрутов не указан как допустимый тип. Для задач отдельная оценка сотрудника **не предлагается** по просмотренной логике, но предложения/замечания допустимы. Тексты системных кнопок могут переопределяться через `BotButtonSetting` (`__system__|review|*`, `__system__|feedback|*`); поэтому строки выше — базовые наименования, не неизменяемый текст интерфейса.

**Подтверждённое бизнес-решение владельца:** оценки относятся к агентам/стажёрам, но не к администраторам; предложения и замечания относятся к заявке и клиенту и **не привязываются к конкретному ответственному сотруднику**. Не добавлять для этого механизма привязку к сотруднику.

### 14.2. Кому может быть назначена оценка

`valid_review_agent()` допускает только `User.role in {"agent", "trainee"}`. Функции подбора (`attributable_review_agent_id_for_actor`, `attributable_review_agent_id_for_client_close`) действуют так:

- если обычную заявку закрывает `agent` или `trainee`, используется пользователь, выполнивший закрытие; по уточнению владельца проекта, такой сотрудник и является ответственным к моменту закрытия;
- при закрытии администратором берётся `ticket.assignee_id` **только если** это агент/стажёр;
- при клиентском закрытии берётся `ticket.assignee_id` **только если** это агент/стажёр;
- если подходящего ID нет, `prepare_review_offer_cycle()` возвращает `None`, и кнопка оценки **не формируется**;
- цикл создаётся только при наличии Telegram-контакта; неудачная доставка завершающего Telegram-сообщения приводит к отмене предложенного цикла, а не к доступной кнопке.

**Особый список:** `_apply_move_to_special()` устанавливает `ticket.is_special=True`, `ticket.assignee_id=admin_user.id` и `ticket.special_assignee_id=admin_user.id`. При последующем закрытии администратором подходящего `agent/trainee` в `ticket.assignee_id` нет, поэтому кнопка **оценки сотрудника не показывается**. При этом «Предложения и замечания» остаются доступными по обычным условиям (если обращение закрыто и замечание ещё не сохранено).

**Решение владельца — оставить без изменений:** не искать предыдущего агента/стажёра по статистике назначений или истории, не добавлять новую логику атрибуции оценки для «Особых»; редкий сценарий не требует усложнения. Администратор никогда не получает оценку. Это **штатное принятое поведение**, не зарегистрированный дефект.

### 14.3. Оценка: цикл, текст, история версий

`TicketReviewCycle` хранит состояния `offered`, `awaiting_rating`, `awaiting_text`, `awaiting_text_after_caption`, `completed`, `cancelled`. Кнопки используют callback-префиксы `review:start:`, `review:back:`, `review:rate:`, `review:finish:`. Выбор **1–5 звёзд** сразу вызывает `save_review_rating()` — запись `TicketReview` появляется **до** необязательного текстового комментария. Это подтверждают реализация и тесты.

- После выбора рейтинга система предлагает текст; обычное текстовое сообщение сохраняет `review_text` и завершает цикл. Подпись к вложению может использоваться как **текст отзыва**; само вложение **не добавляется** к отзыву. Вложение без подписи вызывает подсказку о необходимости текста.
- При новом `/start`, когда рейтинг уже выбран, а текст ещё ожидается, `cleanup_review_flow_for_contact(..., reason="start")` завершает сценарий; сохранённая оценка **остаётся**. Если клиент ушёл на более ранней стадии без оценки, незавершённый цикл отменяется.
- Повторный цикл для **той же пары** `ticket_id + agent_id` может создать новую версию оценки: предыдущая запись получает `is_current=False`, новая — увеличенный `version_number`, `previous_version_id` на старую запись и `is_current=True`. Старый комментарий не переносится автоматически; прежний отзыв остаётся в истории.
- У другого агента по той же заявке может быть собственная независимая актуальная оценка (отдельная пара ticket+agent).
- Повторный вызов сохранения оценки **в том же цикле** возвращает существующую запись и не создаёт дубликат. Уровень БД ограничивает рейтинг 1–5 и уникальность текущей оценки в паре.
- `_valid_cycle_for_callback()` проверяет клиента, точный ID актуального Telegram-сообщения, ожидаемое состояние, последний цикл для пары, закрытый статус обычной заявки и допустимую роль оцениваемого сотрудника. Старые кнопки возвращают состояние `stale` и не должны создавать новую оценку.

По просмотренным запросам чтения `api/app/routers/reviews.py` отделяет текущие и исторические версии с помощью `is_current`. Полную статистику рейтингов и страницы интерфейса в этом проходе **не аудировали**.

### 14.4. Предложения и замечания: ввод и ограничения

Сценарий `feedback:start:<ticket_id>` → `TicketFeedbackInput(state=awaiting_text)` → одно текстовое сообщение → `TicketFeedback` → `completed` и благодарность. Кнопка `feedback:back:<input_id>` отменяет только ввод (`cancelled`) и возвращает постзакрывающие действия. Вложения и пустой текст **не принимаются**; отправляется просьба написать текст. Сохранение проверяет существование `TicketFeedback` и защищено уникальностью `ticket_id` и обработкой `IntegrityError` в savepoint: для одного обращения **одна сохранённая запись**. Отдельная оценка сотрудника после сохранения замечания по-прежнему может предлагаться, если для неё есть действующий цикл.

Одновременный активный ввод оценки и замечания предотвращается соответствующими проверками обработки кнопок. Устаревшие callback'и проверяются по клиенту, текущему сообщению, состоянию и наличию уже сохранённого замечания. `TicketFeedback` сохраняет снимок имени клиента и названия заявки, текст и момент отправки.

### 14.5. Восстановление заявки и повторное закрытие

`POST /{ticket_id}/restore` вызывает `cleanup_review_flow_for_ticket_reopen()` и `cleanup_feedback_flow_for_ticket_reopen()` **до** попытки отправить клиенту сообщение о восстановлении:

- активный цикл оценки в `offered` / `awaiting_rating` / `awaiting_text` / `awaiting_text_after_caption` **отменяется**, активное Telegram-сообщение удаляется, но уже сохранённые `TicketReview.rating` / `review_text` **не удаляются**; цикл в `completed` остаётся завершённым, очищается ID текущего Telegram-сообщения;
- незавершённый `TicketFeedbackInput` отменяется и его Telegram-сообщение удаляется; ранее сохранённый `TicketFeedback` **остаётся**;
- кнопки оценки на вновь открытой заявке невалидны, поскольку обработчик требует `ticket.status=closed`; также срабатывают проверки цикла и сообщения;
- при **повторном закрытии** доступен новый цикл оценки подходящего агента; новая оценка, если клиент её выставит, создаёт версию по той же паре `ticket_id + agent_id`;
- кнопка «Предложения и замечания» **не предлагается повторно**, если `TicketFeedback` уже сохранён для этой заявки. Это явно проверяет `test_reopen_and_second_close_does_not_offer_second_feedback()`.

Прочитаны тесты `test_restore_cleans_review_before_restore_notification`, `test_reopen_cleanup_handles_offered_rating_after_rating_and_completed_states`, `test_reopen_cleanup_without_telegram_contact_cancels_active_cycle_and_keeps_review_data`, `test_new_rating_for_same_pair_moves_current_to_history`, `test_reopen_and_second_close_does_not_offer_second_feedback`, `test_feedback_back_cancels_only_feedback_input_and_returns_actions` и смежные. **Чтение тестов не равно их запуску**.

### 14.6. Границы и дальнейшие проверки

Документированы условия показа постзакрывающих кнопок, атрибуция, основные callback'и, состояние ввода, версионирование, отмена при восстановлении и ограничения повторной обратной связи. **Не** проверены целиком административный UI просмотра оценок и замечаний (`routers/reviews.py`, `routers/management_feedback.py`), агрегирование рейтингов/фильтров, все случаи сбоя Telegram API, одновременные конкурирующие запросы и end-to-end поведение на работающем DEV. Отдельных доработок по этому блоку не запланировано.

## 15. Сотруднический Telegram-бот: доступ, уведомления и внутренние задачи (шаги 24–34)

Этот раздел фиксирует фактически прочитанный код `employee_telegram_polling.py`, `employee_telegram_bot.py`, `telegram_employee_binding.py`, `employee_telegram_access.py`, `employee_telegram_notifications.py`, `telegram_bot.py`, `ticket_lifecycle.py`, `internal_tasks.py` и фрагменты релевантных тестов. **Тесты не запускались**, боевые Telegram-запросы не выполнялись, код не менялся. Понятия «штатно предусмотрено» и «гарантированно доставлено» не тождественны.

### 15.1. Отдельный бот и входящие update

Сотруднический бот использует `settings.employee_telegram_bot_token` и `settings.employee_telegram_polling_enabled`; `api/app/main.py` запускает `employee_telegram_polling_loop()` отдельно от клиентского polling. `get_updates()` получает Telegram update, `_process_employee_update_sync()` создаёт `SessionLocal` и передаёт его в `process_employee_telegram_update()`.

- Цикл сотруднического polling начинает с `offset=None`, после **успешного** выполнения обработчика устанавливает `offset=update_id+1`; при ошибке обработчика пишет исключение и продолжает цикл, при общей ошибке polling делает паузу 3 секунды. **Не утверждать** гарантированную обработку каждого update: если после сбойного update успешно обработается более поздний, offset продвинется дальше.
- Обработчик поддерживает `callback_query`, `/start` и штатную кнопку открытия меню; произвольные сообщения и неизвестные команды игнорируются (`unsupported_command`). В просмотренных обработчиках **нет действий по ответу на заявку или закрытию заявки через бот сотрудника**: это бот уведомлений и управления Telegram-привязками.
- `/start` и кнопка меню принимаются **только в личном чате**. При обновлении аккаунта по Telegram user ID синхронизируются доступные metadata: `chat_id`, `username`, отображаемое имя.

### 15.2. Привязка сотрудника и состояние аккаунта

Таблица `TelegramNotificationAccount` (`telegram_notification_accounts`) содержит уникальный `telegram_user_id`, nullable уникальный `bound_user_id`, `telegram_chat_id`, `telegram_username`, `telegram_display_name`, `request_status`, `delivery_available`, `is_blocked`, `is_notification_bot_admin`. Уникальность двух идентификаторов не позволяет создать две записи для одного Telegram-пользователя и одновременно привязать одного сотрудника ES DESK к двум Telegram-аккаунтам.

`/start` нового посетителя создаёт **непривязанный запрос** `pending`, с `delivery_available=False`. Повторный `/start` с существующим запросом не создаёт дубль; подтверждённая привязка не сбрасывается. Для одобрения выбирается **конкретный активный `User` ES DESK**, запрос должен быть `pending`, непривязанным и незаблокированным, а выбранный сотрудник — без иной привязки. Одобрение устанавливает `bound_user_id`, статус `approved` и доступность доставки при наличии Chat ID. Отклонение **удаляет запись pending-запроса**, не блокирует Telegram user ID навсегда.

Разграничение операций:

| Операция | Изменения в БД |
|---|---|
| Отвязка (включая самостоятельную) | Удаляет запись подтверждённой привязки |
| Блокировка | Оставляет привязку, `is_blocked=True`, `delivery_available=False` |
| Разблокировка | `is_blocked=False`, `delivery_available=bool(telegram_chat_id)` |
| Обычное взаимодействие с ботом | Обновляет metadata; у активной, одобренной, незаблокированной привязки с Chat ID может вернуть `delivery_available=True` |
| Выдача/отзыв прав администратора бота | Изменяет `is_notification_bot_admin`, не отвязывая сотрудника |

Блокировка **не равна** отвязке. Повторное взаимодействие с заблокированным подтверждённым аккаунтом не снимает блокировку. Административное управление привязками также существует через API в `routers/settings_users.py`.

### 15.3. Роли бота и авторизация callback

В `employee_telegram_access.py` роли бота: `owner`, `admin`, `user`, `none`. Владелец задаётся `settings.telegram_notification_bot_owner_id` и определяется по Telegram user ID **без обязательной обычной привязки**. Дополнительный администратор — активный привязанный пользователь с `approved`, `is_blocked=False` и `is_notification_bot_admin=True`. Роль администратора **бота** не равнозначна административной роли пользователя **ES DESK**.

| Возможность | `owner` | `admin` бота | `user` бота |
|---|:---:|:---:|:---:|
| Запросы привязки, список подключённых, блокировка/разблокировка/отвязка | Да | Да | Нет |
| Назначение и отзыв дополнительных администраторов бота | Да | Нет | Нет |
| «Моя привязка», самостоятельная отвязка | Не предусмотрено в меню владельца | Да | Да |

Для каждого callback действие разбирается и **текущие права вычисляются заново**; скрытие кнопки само по себе не является единственной защитой. Опасные действия имеют отдельные экраны подтверждения. Некорректные callback не должны менять данные (прочитаны названия/часть тестов). У неактивного привязанного пользователя с сохранённым флагом дополнительного администратора эффективная роль понижается до `user`; после реактивации админские полномочия могут вернуться. Это следует из текущего кода и профильных тестов; не объявлять автоматически дефектом.

### 15.4. Какие уведомления и кому планируются

В `employee_telegram_notifications.py` поддерживаются события `new_assignment`, `transfer_between_agents`, `removed_from_agent`, `new_message`, `internal_task_completion`. Для обычных назначений и сообщений целевые бизнес-получатели ограничены **активными `agent`/`trainee`** (`BUSINESS_RECIPIENT_ROLES`). Администраторы ES DESK не получают обычное уведомление «назначено агенту» только по факту назначения себе технической «Особой» заявки; для уведомления о завершении внутренней задачи — отдельные правила (ниже).

| Смена ответственного | Кому планируется уведомление |
|---|---|
| Нет → агент | Новому агенту (`new_assignment`) |
| Агент А → агент Б | А (`transfer_from_agent`) и Б (`transfer_to_agent`) |
| Агент → без ответственного | Предыдущему агенту (`transfer_from_agent`) |
| Агент А → «Особые» | Агенту А (`transfer_from_agent`), адресат — «Административный контроль» |
| «Особые» → агент Б | Агенту Б (`transfer_to_agent`), источник — «Административный контроль» |
| «Особые» → «Особые» | Событие передачи отсутствует |

Из кода `build_assignment_notification_event()` следует, что отсутствие реального изменения обычного ответственного/флага special возвращает `None`. Для групповой **дочерней** задачи первоначальное назначение подавляется, но передача между сотрудниками поддерживается. Интеграционный тест `test_special_transfers_send_no_duplicates_and_use_administrative_control_label()` проверяет по одному уведомлению при переводе агент → «Особые» → другой агент; в проверенном сценарии администратор не получает третьего уведомления.

Перед отправкой выполняются **глобальная проверка разрешения типа уведомления**, проверка активной бизнес-роли получателя, персональный переключатель и наличие одобренной незаблокированной доступной привязки с Chat ID. Для `new_assignment`, `new_message` и `internal_task_completion` доступны общие/персональные шаблоны, HTML-режим, предпросмотр ссылок, тихая отправка. Для передач предусмотрены отдельные `receive_transfer_to_agent` / `receive_transfer_from_agent`; для сообщения — `receive_new_message`. Персональный шаблон определяется независимо от персональных переключателей доставки.

### 15.5. Граница транзакции и фактическая надёжность

`schedule_assignment_notification()`, `schedule_new_message_notification()` и `schedule_internal_task_completion_notification()` добавляют данные **в `Session.info`**. Обработчик SQLAlchemy `after_commit` извлекает списки, открывает новую `SessionLocal`, заново проверяет получателя и параметры и вызывает отправку. `after_rollback` и `after_soft_rollback` очищают списки.

**Для обычного немедленного маршрута это не долговременная очередь:** в данном механизме нет отдельной persisted outbox-записи для неотправленного уведомления. **Исключение после коммита `8439b32`:** уведомления, попавшие в нерабочие часы, накапливаются в отдельных таблицах PostgreSQL (раздел 17); это не универсальный outbox для всех ошибок отправки. Если процесс падает после commit, либо Telegram API не отвечает, штатного автоматического восстановления/повтора соответствующего уведомления здесь не выявлено. Исключения доставки логируются, но не откатывают уже сохранённое закрытие/назначение. При накоплении нескольких событий в одной транзакции они добавляются в список по отдельности; **не доказано**, что имеется общее устранение дублей для всех последовательностей переназначений — не обещать его.

`telegram_bot.py:telegram_request()` выполняет один HTTP-запрос через `urlopen`, переводит `HTTPError`/`URLError` в `TelegramApiError`, скрывая токен в тексте исключения. **Внутри `telegram_request()` retry нет.** `send_message()` при `parse_mode='HTML'` может повторить отправку как plain text; по умолчанию это происходит при **любой** `TelegramApiError`, а не только ошибке HTML. Значит, это fallback форматирования, **не гарантия exactly-once**; при неопределённом исходе первой попытки возможны риски повторной внешней отправки. В исследованном сервисе не найдено автоматического `delivery_available=False` на ошибку Telegram. Функции прямой отправки `notify_user()`/`notify_users()` объявлены, но `rg` по `api/app` не показал внешних вызовов; не приписывать им действующий основной поток без новых доказательств.

### 15.6. Новые сообщения и Telegram-альбомы

Для обычного входящего сообщения `schedule_new_message_notification()` фиксирует **`recipient_user_id=ticket.assignee_id` в момент планирования**. Не планирует уведомления, если нет ответственного, это `GROUP_CHILD`, системное или невидимое сотруднику сообщение, либо отредактированная замена (`replaced_message_id`). На этапе разрешения также отбрасывается сообщение **самого получателя** (`message.author_user_id == recipient_user_id`). Допускаются видимые внутренние комментарии другого сотрудника. Глобальный и персональный переключатели, роли и привязка перепроверяются при разрешении.

Если вложение принадлежит Telegram-медиагруппе, вместо обычного уведомления используется ключ **`(ticket_id, telegram_media_group_id)`** и process-local debounce: **10 секунд без новой части**, таймер сбрасывается при продолжении альбома; при **10 вложениях** отправка планируется без ожидания. Поколения `generation` защищают от исполнения устаревшего таймера, после завершения запись удаляется из локального реестра. Независимые медиагруппы разделяются, отдельный файл без `media_group_id` не ждёт таймера. При перезапуске процесса/в нескольких workers активные таймеры не сохраняются и не образуют кластерно-устойчивой очереди — это прямо отмечено в комментарии к коду.

**Тонкое отличие:** для альбома адресат читается заново из **текущего** `ticket.assignee_id` при разрешении после debounce, тогда как для обычного сообщения ID адресата фиксируется при schedule. Изменившийся ответственный может повлиять на адресата альбома. Название файла, текст и подпись собираются в единый текст уведомления; проверено в соответствующих тестах, но не реальной отправкой Telegram.

### 15.7. Завершение внутренних задач: уведомление ответственному администратору

`is_internal_task_ticket(db,ticket)` возвращает `True` **только по существованию записи `InternalTaskOccurrence` с данным `ticket_id`**. Поэтому название задачи, тип `task` сам по себе или канал не делают задачу «внутренней». В `ticket_lifecycle.py` такая задача подавляет обычную клиентскую отправку результата. В ветке **обычной задачи** (`task_kind=normal`) при штатном закрытии с итоговым ответом планируется `schedule_internal_task_completion_notification()`. При **принудительном закрытии администратором** (`is_admin_action and force_without_agent_reply_for_task`) это событие не планируется.

`resolve_internal_task_completion_telegram_delivery()` требует `InternalTaskOccurrence.notify_on_completion=True`, `responsible_admin_id`, активного пользователя именно с ролью **`admin`**, разрешения в настройках и подтверждённой доступной Telegram-привязки. Отправка идёт именно **ответственному администратору задачи**, а не произвольному администратору или агенту.

- В уведомление включается **последний итоговый `MessageType.AGENT` ответ**: его текст и имена только его вложений; предыдущие ответы, прежние файлы и вложения внутренних комментариев не включаются.
- Если итог — только файл, Telegram-бот присылает **текст с названием файла**; сами PDF/фото/прочие файлы отдельными Telegram-вложениями в этом уведомлении **не передаются** (в прочитанных тестах `sent_files=[]`).
- Если администратор **обычно** закрывает внутреннюю задачу, где сотрудник уже дал итоговый ответ, `closed_by_user_id` — администратор, `completed_by_user_id` — сотрудник-автор ответа, а Telegram-текст сообщает о выполнении **этим сотрудником**. Это прямо проверено `test_admin_normal_internal_task_close_notifies_with_agent_result_author()`.
- Если администратор **принудительно** закрывает задачу без результата сотрудника, задача закрывается, но отдельного уведомления о выполнении **нет** (`test_admin_forced_internal_task_close_without_employee_result_does_not_notify()`). Обычная не-внутренняя задача также не создаёт такого уведомления; результат доставляется обычным маршрутом клиента.
- `notify_on_completion=False`, персональное `notify_internal_task_completion=False`, отсутствие активного ответственного/доступной привязки или пустой/удалённый итог исключают уведомление. Персональный шаблон и общий шаблон работают раздельно: если используется базовый, действует его `enabled`; выбранные личные настройки могут использовать персональный шаблон. Тест с искусственной ошибкой `send_message()` подтверждает, что **ошибка уведомления не мешает перевести задачу в `closed`**.

Опора: `tests/test_internal_task_completion_notification.py` (прочитаны проверки текстового ответа, файла, текста+файла, последнего сообщения, включения/выключения, персонального шаблона, штатного админского закрытия и принудительного закрытия); `tests/test_employee_telegram_runtime_integration.py`, `tests/test_employee_telegram_bot.py`, `tests/test_telegram_employee_binding.py`, `tests/test_employee_telegram_access.py` и прочие. **Это анализ текста тестов, не их запуск.**

### 15.8. Что ещё не подтверждено этим проходом

- Фактическая отправка и журналы на живом DEV/PROD; конкурентные транзакции, рестарты и гарантии повторной доставки.
- Полные клиентские шаблоны, UI настроек уведомлений и их маршруты сохранения, административные страницы просмотра отзывов/замечаний.
- Все сценарии немедленных/плановых/повторяющихся внутренних задач от определения до materialization scheduler; в этом разделе рассмотрен **именно канал уведомлений при закрытии**.
- Иные внешние источники уведомлений за пределами просмотренных модулей.

**Решение текущей контрольной точки:** зафиксировать существующее поведение без изменений кода. Исследование сотруднического Telegram-бота на уровне базовых команд, привязок, прав, уведомлений и завершения внутренних задач завершено; дальнейшее исследование можно вести по отдельным темам.

## 16. Клиентское Telegram-меню: жизненный цикл сообщений и callback (коммит `8aec22d`)

> **Статус:** реализованная и принятая после паузы доработка; это дополнение к исследованию, а не повтор шагов 1–34. Серверная защита и удаление старых меню проверялись в DEV; полное прохождение создания обычной клиентской заявки в рабочее время на контрольной точке ещё не проверялось.

В клиентском Telegram-боте согласован жизненный цикл интерактивного меню:

- Новый `/start` и переходы между меню должны очищать устаревшие интерактивные сообщения, включая предыдущее меню с inline-кнопками; при переходах «Назад» не должно оставаться набора действующих старых клавиатур.
- Проверка актуальности callback выполняется **на сервере**, а не только через визуальное удаление кнопок. Устаревшее сообщение или неактуальный сценарий не могут выполнять прежнее действие.
- Подтверждающие действия используют отдельные кнопки/ветви подтверждения; результат должен относиться к текущему состоянию меню.
- Операции Telegram API по удалению старого сообщения и серверная проверка stale callback — **разные меры защиты**: нельзя полагаться исключительно на успешное удаление Telegram-сообщения.

**Проверенные живые сценарии:** `/start`, обычные подменю, «Назад», автоматические подтверждения задач и блокировка приёма вне рабочих часов. **Осталось проверить:** обычное создание клиентской заявки в рабочее время после обновления меню.

Реализация распределена по существующему клиентскому Telegram-router/сервисам меню; точная карта всех веток и TXT/DB-совместимости остаётся в очереди последующего адресного исследования. Не приписывать коммиту `8aec22d` завершение полного аудита `BotButtonSetting`.

## 17. Сотруднический бот: накопление уведомлений вне рабочего времени (коммит `8439b32`)

### 17.1. Расписание и область действия

Автоматические уведомления **сотруднического Telegram-бота** накапливаются, если событие возникло вне графика: **понедельник–суббота, с 08:00 включительно до 19:00 исключительно, по Москве; воскресенье — выходной**. Уведомления субботнего вечера и воскресенья предлагаются в понедельник утром.

**Не путать** с часами *клиентского приёма Telegram*: Пн–сб, **07:50–19:00 МСК**. Это два разных правила.

Промежуточное хранение применяется к автоматическим уведомлениям, проходящим через штатный сервис сотруднических уведомлений: назначения, передачи, новые сообщения, завершения внутренних задач при соблюдении прежних правил получателя и персональных настроек. Оно **не** откладывает ответ бота на явную команду пользователя и не превращает бота сотрудника в чат для ответов по заявке.

Для обычных уведомлений получатели по-прежнему ограничены активными агентами/стажёрами; уведомление о завершении внутренней задачи может предназначаться её ответственному администратору. Условия доступности Telegram-привязки и переключателей типов уведомлений остаются обязательными.

### 17.2. Хранение и запуск периодических операций

Две модели, добавленные в `api/app/models.py`:

| Таблица | Назначение | Основные данные |
|---|---|---|
| `employee_notification_periods` | Период выдачи накопления для определённого пользователя и рабочего дня | `user_id`, `work_date`, `chat_id`, `message_id`, `offered`; уникальная пара `(user_id, work_date)` |
| `employee_notification_backlog` | Отдельные тексты автоматических уведомлений, ожидающих выдачи | `period_id`, `text`, `parse_mode`, `disable_link_preview`, `send_silently` |

Ключевой сервис — `api/app/services/employee_notification_backlog.py`; вызовы отправки согласованы с `employee_telegram_notifications.py`, callback-кнопки с `employee_telegram_bot.py`, периодическая проверка — с `internal_task_scheduler.py`. Сами уведомления после окончания исходной бизнес-транзакции идут по существующему механизму `after_commit` (раздел 15.5); **сохранение отложенного уведомления не является транзакционно единым с исходным событием**.

Новые таблицы **исключены из общего `Base.metadata.create_all`**. Их нужно создать явным вызовом `ensure_employee_notification_backlog_tables()` из `api/app/services/schema_evolution.py` **до запуска новой версии API** в соответствующей БД. В DEV процедура выполнена 2026-11-08: обе таблицы проверены; в PROD миграция **не выполнялась**. Не заявлять, что таблицы автоматически создаются при обычном старте приложения.

### 17.3. Утренний запрос, пакетная выдача, очистка

- В **08:00 ближайшего рабочего дня** штатный периодический процесс предлагает сотруднику накопившееся число уведомлений одним сообщением с кнопками «Да»/«Нет». Фактический момент срабатывания ограничен частотой scheduler и работой бота.
- При выборе «Да» отправляются **не более пяти исходных уведомлений отдельными сообщениями**. Если остаются записи, бот предлагает следующую пятёрку, сообщает сколько выдано/осталось.
- При выборе «Нет» оставшиеся записи накопителя очищаются. Это **не** удаляет сообщения заявок, комментарии и историю задач в ES DESK.
- Сообщение-предложение с inline-кнопками подлежит удалению при обработке ответа; для проверки актуальности учитываются принадлежность пользователю, период, рабочий день и связка `chat_id`/`message_id`. Устаревшие callback должны отклоняться на сервере даже при неудачном удалении Telegram-сообщения.
- Если сотрудник не нажал кнопки, накопившиеся записи и устаревшее предложение очищаются **в 19:00 рабочего дня**. Это правило не означает очистку в воскресенье.

### 17.4. Надёжность, тесты и эксплуатационный статус

Это **специализированный отложенный backlog вне рабочего времени**, а не общий надёжный outbox с гарантией повторов после любой ошибки Telegram API. Следует сохранять прежние оговорки раздела 15.5: возможны ошибки внешней отправки, короткое окно между исходным commit и отдельным сохранением накопителя, отсутствие полной гарантии exactly-once.

Коммит: `8439b32`. Целевые тесты накопителя и интеграций прошли при разработке (в одном из прогонов Codex сообщил 151 пройденный тест); это **не** подтверждение живого сценария следующего рабочего утра. DEV API собран и запущен после явной миграции, но полная цепочка «накопление после 19:00 → предложение утром → серии по пять → очистка» пока требует отдельного живого теста. PROD не изменяли, push не выполнялся.

**Примечание для будущих изменений:** персональные графики сотрудников ещё не реализованы — текущее расписание единое. При развитии механизма необходимо отдельно уточнять консистентность периодов и правила для выключенных/заблокированных привязок, не объявляя их уже реализованными.

## 18. Клиентское меню: источник данных, идентификаторы и проверка callback (исследовательский шаг 35)

> **Основание:** адресные read-only PowerShell-выгрузки из `api/app/services/button_config.py`, `api/app/models.py`, `api/app/routers/telegram.py` на локальном `HEAD=8439b32` (2026-11-08). Код и БД не менялись; тесты в рамках этого исследовательского прохода не запускались. Раздел уточняет раздел 16, а не повторяет исторические шаги 1–34.

### 18.1. Где хранится меню и как выбирается его вариант

- Действующий маршрут `_send_problem_menu_with_visibility()` напрямую вызывает `_send_problem_menu_db_only()`. Эта функция получает активные строки `BotButtonSetting` из PostgreSQL для выбранного `menu_type`, а размещение кнопок по рядам — из `BotMenuLevelLayout.layout_json`. Не найдено TXT-чтения **в данном маршруте формирования меню**.
- `available_menu_names()` собирает варианты меню из `BotButtonSetting`, `BotMenuDestinationBinding` и активных `BotMenuProfile`; неактивные профили и системные типы исключаются. `_menu_name_for_contact()` и `_menu_name_for_ticket_client()` используют подтверждённый `ClientProfile.is_verified` и `temporary_rop_destination(profile)`: сначала ищут привязку подразделения `BotMenuDestinationBinding`, затем допустимое прямое совпадение названия. Если условия не выполнены, выбирается `Базовое`.
- `BotButtonSetting` содержит `id`, `stable_button_id`, `button_key`, `legacy_button_key`, `menu_type`, `workflow_type`, путь/родителя, тип узла, переопределения подписи и видимости, подтверждения, назначения, автоматизации и файлов. **Telegram callback новых кнопок использует именно `row.id`**, не `stable_button_id`: `btnid:{id}` для действия, `menuid:{id}` для раздела. `group_task` отображается как действие даже при структурном типе, который в иных случаях означал бы раздел.
- Строки с `currently_present=False` или `is_archived=True` не попадают в актуальную разметку. Переопределённая видимость `visibility_overridden/is_enabled` управляет показом; пустой раздел без видимых потомков пропускается. Подпись может браться из `label_override`. Сначала применяется конфигурация рядов `BotMenuLevelLayout`; не включённые в неё видимые кнопки дополняются отдельными рядами.
- `button_config.py` оставляет `ButtonSpec`, `ButtonConfig` и построители исторических ключей. `resolve_button_row()` разрешает текущий ключ, `legacy_button_key` и допустимые варианты ключей обычных `ticket/task/auto` **через строки БД**; при строгом неоднозначном совпадении предусмотрен HTTP 409. `BUTTON_CONFIG_DIR` в просмотренных вызовах используется для ранее сохранённых вложений (`files`), а не как источник структуры меню. Это **не доказательство** полного отсутствия иных исторических TXT-механизмов во всём репозитории; за пределами проверенного маршрута их нужно оценивать отдельно.

### 18.2. Жизненный цикл сообщения меню и серверная защита

- `_send_problem_menu_for_contact()` сначала собирает ID старых меню, отправляет новую разметку, при успешном получении `message_id` сохраняет его у черновика и контакта, затем вызывает `_clear_client_menu_keyboards(..., keep_message_id=новый)`. Если Telegram не вернул ID нового сообщения, этот путь не объявляет его актуальным.
- У `TelegramContact` хранится `menu_message_ids_json` — нормализованный список до **20 последних уникальных положительных ID**, и `active_menu_message_id`. Очистка пытается **удалить старые сообщения**; неудачные удаления сохраняются для дальнейшей очистки. Сохранённая история удаления сама по себе не даёт права нажимать кнопки.
- `_is_current_menu_callback()` требует совпадения ID нажатого сообщения с `contact.active_menu_message_id` и отсутствия противоречия с `collecting_ticket.menu_message_id`. В `_process_telegram_update()` эта проверка вызывается **до маршрутизации каждого обычного callback с префиксом `btnid:`, `btn:`, `menuid:`, `menu:`**; при неуспехе возвращается `ignored: stale_menu`. Значит, невозможность удалить старое Telegram-сообщение не делает его callback действующим. Другие семейства callback (закрытие, отзыв, отдельные автоматизации) имеют собственные обработчики и сюда не входят.
- `_button_from_callback()` разрешает `btnid:` через первичный ID строки, а старый `btn:` — через DB-ключ/алиасы и актуальный тип меню. `_is_callback_button_enabled()` отдельно проверяет существование, актуальность, архивирование, видимость кнопки и родительских разделов. Для `menuid:` существует разрешение в ключ раздела; исторический `menuid:` групповой задачи преобразуется в `btnid:`, чтобы выполнить действие, а не открыть раздел.
- `process_telegram_update()` направляет переходы меню в блокировку клиентского Telegram-чата и при необходимости восстановление незаконченной групповой автоматизации; `_process_telegram_update()` проверяет `TelegramUpdate.update_id` на повтор, тип чата и блокировку контакта. Это не означает гарантии exactly-once для внешних Telegram-отправок.

### 18.3. Выбор действия, подтверждение и переход к заявке

1. Клиентский `/start`: при существующей активной обычной заявке новая не создаётся — выводится сообщение о текущей заявке, старые меню очищаются. Если клиента нужно впервые подключить (`profile` отсутствует, не верифицирован или нет `destination`), работает отдельный onboarding и проверка часов приёма. Иначе для клиента без активной заявки используется `collecting`-черновик и актуальное меню из БД.
2. Выбор конечной кнопки: после проверки актуальности callback и разрешений кнопки повторно ищется активная заявка. Для ограниченных видов кнопок проверяется `is_telegram_intake_open()`. При необходимости создаётся `collecting`, фиксируются ключи выбранной кнопки и инструкции.
3. При включённом подтверждении отправляется отдельное сообщение с кнопками; оно становится актуальным, а прежние меню очищаются. Callback подтверждения дополнительно сверяет наличие самой кнопки в `reply_markup` исходного сообщения, текущий `active_menu_message_id`, `collecting_ticket.menu_message_id`, `button_config_key` и отсутствие другой активной заявки. Невалидное состояние даёт `ignored: stale_confirmation`. «Нет» сбрасывает черновик и возвращает меню; «Да» снова проверяет часы для ограниченного действия.
4. При подтверждённом или не требующем подтверждения действии сначала учитываются специализированные ожидания `telegram_client_origin`, телефона Bitrix и группового сообщения. Для `auto` выполняется автоматизация/доставка предусмотренных материалов (при ошибке прямого файла возможен fallback в поддержку); для `task/group_task` — запрос клиентского описания одним сообщением; для обычного `ticket` — перевод черновика в готовую заявку и распределение через `_ready_ticket_for_distribution()`. На пути обычной заявки часы приёма проверяются повторно.
5. Если клиент не присылает описание задачи вовремя, отдельная ветка обработки сообщений использует `TASK_DESCRIPTION_TIMEOUT_MINUTES` и закрывает либо удаляет подходящий черновик по существующим предикатам. Точное значение тайм-аута и все его варианты этим шагом не исследовались.

### 18.4. Границы вывода и следующий проход

Серверные проверки актуальности меню и подтверждения **доказаны по коду для обычных клиентских callback**; это сильнее прежней общей фиксации функциональности в разделе 16. Для этого шага были только прочитаны исходники и найден перечень профильных тестовых файлов, включая `test_bot_button_db_only_runtime.py`, `test_db_only_blockers.py`, `test_bot_button_moves.py`, `test_telegram_button_intake_hours.py`, `test_telegram_group_copy.py`; **тексты этих тестов в рамках шага 35 не изучались, тесты не запускались**.

**Ещё открыто:** полный цикл редактирования меню в административном UI/API; точные границы старых совместимостей за пределами проверенного DB-only маршрута; все автоматизации и загрузки вложений; живое создание обычной клиентской заявки в рабочие часы после коммита `8aec22d`. Не объявлять непроверенное дефектом и не менять код ради документации.

|---|---|---|

| Восстановление | `POST /bot-buttons/menu-types/{menu_name}/restore` | Профиль вновь активен, с его кнопок снимается архивный флаг. **Удалённые при архивации привязки этим endpoint не восстанавливаются** — их при необходимости добавляют заново. |

**Выявленное расхождение UI и API:** модальное окно создания меню при отсутствии свободных типов говорит, что можно создать меню без привязки и назначить её позже. Однако фактический backend отвергает пустой `destinations` с HTTP 422 `destinations_required`. Поэтому обещание интерфейса сейчас неверно; это документированное наблюдение, не выполненная правка.

Восстановление меню и его маршрутизации — **две разные операции**: активировать `BotMenuProfile` недостаточно для автоматического возврата прежнего `BotMenuDestinationBinding`. Возврат в клиентское меню определяется действующей логикой раздела 18 и текущими привязками, а не самим фактом восстановления архива.

### 19.3. Создание элемента и иерархия

- API `GET /bot-buttons/menu-types/{menu_name}/structure` строит дерево из активных строк `BotButtonSetting`, группирует по `parent_path`, применяет раскладку уровня и добавляет активные кнопки, которых нет в сохранённых рядах. Структура отдельно содержит листы `tickets`, `tasks`, `autos`, `group_tasks` и `removed_items`.
- В модальном окне «Создание кнопки» доступны **раздел/подменю** (`section/submenu`), **заявка** (`ticket`), **задача** (`task`), **автоматическая задача** (`auto`), **групповая задача** (`group_task`); задаются название и флаг активности. На уровне групповой задачи интерфейс вместо этого предлагает создание **дочерней задачи** (`group_task_child`). Отправка: `POST /bot-buttons/item/create`.
- Для обычных `ticket/task/auto` новый технический ключ собирается с указанием workflow; для разделов, групповых родителей и дочерних элементов используется DB-ключ видимости. Заполняются UUID строки `id` и отдельный `stable_button_id`; это не одно и то же. Совпадение `menu_type` + полного пути активной кнопки запрещено; если по пути найден ровно один неактивный элемент, создание может **реактивировать** его. Коллизии технических ключей/алиасов отдельно проверяются.
- Важное разграничение: пользовательская подпись (`label_override`) **не равна** техническому `button_path`. Простое переименование видимой подписи не должно переносить кнопку и переписывать её исторические ссылки; редактор предупреждает о непустой подписи. Порядок существующих кнопок перед такими изменениями сохраняется через `_preserve_level_order()`.
- Backend-метод создания проверяет тип элемента, название, ключ и совпадение пути. Само ограничение «`group_task_child` создаётся только из экрана группового родителя» показано для **UI**; отдельную строгую проверку типа родителя в `create_bot_button_item()` в прочитанном коде не обнаружили — не приписывать её серверу.

### 19.4. Редактор существующей кнопки и сохранение

`GET /bot-buttons/item` возвращает сохранённые и вычисленные поля кнопки. Основной редактор держит рабочие и сохранённые значения отдельно, предупреждает об уходе при несохранённых изменениях. Из кода контроллера и отправляемого JSON подтверждены следующие группы параметров:

- название кнопки в Telegram и её цвет (`base`/`primary`/`success`/`danger`); текст клиенту, системный текст и внутренняя инструкция;
- фиксированный ответственный (доступный активный пользователь допустимой роли), заморозка обращения при создании и флаг подавления ответа клиенту для дочерней групповой задачи;
- необходимость подтверждения и текст подтверждения; видимость/активность кнопки;
- назначение автоматизации, прямая отправка файлов и условные наборы файлов по полям карточки; выбор проверенной Telegram-группы для соответствующей автоматизации.

Сохранение отправляет `PUT /bot-buttons/item/instruction` и затем обновляет структуру. Сервер нормализует и проверяет значения, известные файлы и правила условий, доступность фиксированного исполнителя и совместимость автоматизации с типом кнопки. Для условий проверяются существование поля, допустимые операторы и значения по типу поля, а также наличие файлов. Редактор отдельно блокирует сохранение, если сохранённые файловые условия не удалось без потерь восстановить в его модель (защита от затирки при неполном преобразовании). **Физическая доставка файлов, детали пикера и все обработчики автоматизаций не проверялись этим шагом**.

Уже созданный обычный элемент может менять тип только внутри триады `ticket ↔ task ↔ auto`; изменение `submenu`, `group_task`, `group_task_child`, системного элемента через этот путь не допускается. Редактор запрашивает подтверждение о возможной несовместимости полей. `change_button_workflow_key()` меняет текущий ключ и ссылки на него в раскладках, проверяет алиасы и их коллизии, сохраняя идентичность строки и исторические ссылки. Некоторые автоматизации допустимы только для `auto` (в том числе Bitrix, Client Origin, Telegram-group); несочетаемые комбинации отвергаются либо очищаются на контролируемом переходе. Точный перечень допустимых комбинаций определяют текущие backend-правила, а не только фильтр в JS.

Редактор не служит маршрутом переноса: если пока он открыт кто-то уже изменил `menu_type` или `button_path`, backend возвращает **409 `button_identity_changed`** с требованием обновить редактор. В обычном редактировании путь кнопки остаётся прежним.

### 19.5. Раскладка кнопок и межуровневый перенос

- В интерфейсе «Изменить структуру» кнопки перетаскиваются между рядами и внутри ряда; допускается **до трёх кнопок в строке**. Изменения локального порядка сохраняет `PUT /bot-buttons/layout?menu_type=...&level_key=...`; `BotMenuLevelLayout.layout_json` содержит последовательность объектов `{columns, button_keys}`. Backend исключает дубли, неизвестные ключи и слишком широкие ряды. Ряды без кнопок отбрасываются.
- Для переноса **между уровнями** выделен другой маршрут `POST /bot-buttons/item/move`. UI разрешает **один межуровневый перенос на сохранение**, блокирует одновременные локальные перестановки и ставит перенесённую кнопку отдельным рядом в конец выбранного уровня. Это интерфейсное ограничение; сервер умеет принимать параметры позиции `target_row`, `target_index`, `new_row`.
- Сервер разрешает межуровневый перенос **только активной терминальной `ticket/task/auto` без детей**. Родитель-назначение должен быть действующим обычным подменю (`section/submenu`), корень тоже допустим; перенос в прежний уровень, в несуществующего родителя, цикл и коллизия целевого пути отвергаются. Разделы и групповые задачи через этот API не перемещаются.
- При переносе меняются `parent_path` и `button_path`, но текущий `button_key`, `id`, `stable_button_id` и настройки остаются за той же строкой; оба затронутых layout сохраняются вместе с переносом в одной транзакции. Ошибка целостности ведёт к rollback. Это механизм перемещения, отдельный от смены workflow.
- Внутри группового родителя интерфейс не предлагает обычный режим редактирования layout, но предлагает редактирование материнской задачи и создание `child task`. В архиве редактирование структуры отключено.

### 19.6. Архив кнопок, восстановление и окончательное удаление

- Обычное `DELETE /bot-buttons/item?button_key=...` — **логическое удаление**: `currently_present=False`, `is_archived=True`, проставляются дата и автор. Для `section` или `group_parent` рекурсивно архивируются потомки по префиксу пути. Через `POST /bot-buttons/item/restore` восстанавливаются те же поля и потомки. Системное первое подключение запрещено удалять этим endpoint.
- `DELETE /bot-buttons/item?button_key=...&hard=true` удаляет **строку физически**, без описанной выше рекурсии в этом обработчике. UI вызывает его из «Архива удалённых» как отдельную команду. Возможные каскады схемы БД этим исследованием не проверены; не утверждать полное отсутствие связанных последствий.
- Архив в основном дереве формируется из `removed_items`, причём `_build_bot_menu_structure()` добавляет туда архивные **терминальные** типы `ticket/task/auto/group_task_child`. Архивные `section` и `group_parent` этот список напрямую не содержит. Поэтому **полнота UI-восстановления архивных разделов/групповых родителей не подтверждена**; backend API восстановления есть, но не следует обещать, что любой архивный родитель можно выбрать из текущего списка архива.
- **Архив кнопки и архив целого меню устроены по-разному:** удаление кнопки меняет также `currently_present`; архивирование меню в проверенном обработчике делает профиль неактивным и `is_archived=True` у его кнопок, не меняя `currently_present`; восстановление меню не восстанавливает его прежние привязки к типам клиентов (см. 19.2).

### 19.7. Системные события — отдельные редакторы

- Внизу списка меню отдельно отображаются **«Системные события»**: «Первое подключение к боту», «Отзывы», «Предложения и замечания». Это не обычные доступные для удаления варианты меню. Для первого подключения `GET/PUT /bot-buttons/system/first-connection` управляют названием системной заявки, системным текстом и инструкцией.
- Для отзывов и предложений/замечаний отдельные `GET/PUT /bot-buttons/system/review-buttons` и `/feedback-buttons` позволяют менять подписи соответствующих системных кнопок и цвет (`primary`, `success`, `danger`, либо базовый). Непустота текста проверяется в UI; backend валидирует набор полей и кнопок.
- Наблюдаемое ограничение интерфейса первого подключения: при сохранении его JS отправляет только **изменённые непустые** значения `subject`, `system_text`, `instruction_text`. Поэтому очистка поля до пустой строки через этот экран не подтверждается как поддерживаемая; это ограничение формируемого запроса, а не предположение о БД.

### 19.8. Границы проверки, тесты и следующие действия

Из выгрузки получены имена тестов в `test_bot_button_db_only_runtime.py`, `test_bot_button_label_display.py`, `test_bot_button_moves.py`, `test_bot_button_origin_removal.py`, `test_button_key_transitions.py`, `test_bot_button_text_priority.py`, `test_bot_settings_transfer.py` и `test_bot_button_saved_file_migration.py`. Они адресуют типы кнопок, смену ключей, рекурсивный архив, layout, переносы, файловые ссылки и интеграционные режимы. **Наличие названий не равно результату тестирования**: в шаге 36 тесты не выполнялись, живой UI не открывали.

**Текущий итог:** основной административный цикл «меню → привязка типа клиента → создание/редактор кнопок → раскладка/перенос → архив/восстановление» прослежен по API и координаторам UI. Не просмотрены полностью подробные рендереры `bot_buttons_editor_view.js`, `bot_buttons_files.js`, слой API-клиента и Telegram-group picker. Из-за этого точное расположение всех отдельных полей и работа модальных окон на живой странице остаются за границей вывода; результаты этих будущих проверок не выдумывать.

**Отложенные вопросы для отдельной задачи разработки (без правок сейчас):** несоответствие подсказки «можно без привязки» требованиям API; отсутствие автоматического возврата привязок при восстановлении меню (может быть задуманной политикой); покрытие архива разделов/групповых родителей в UI. Сначала уточнить требуемое поведение, затем только обсуждать патч. Следующий тематический проход документации: механизмы автоматизаций и сохранённых/условных файлов, затем фоновые операции, WEB и схема БД.

Прочитаны `services/button_automation_types.py`, `telegram_automation.py`, `telegram_group_automation.py`, `telegram_group_registry.py`, `telegram_bitrix_phone.py`, `telegram_client_origin.py`, `saved_files.py`, `bot_button_saved_file_migration.py`; `routers/telegram_groups.py`; `static/bot_buttons_files.js`, `bot_buttons_editor_view.js`, `bot_buttons_api.js`, `bot_telegram_groups.js`; адресные участки `routers/telegram.py`. Также получен **индекс тестовых функций**, но их тела в данном проходе не читались и тесты **не запускались**. `telegram_outbound_delivery.py` инвентаризирован по функциям, не изучен полностью; это отдельный широкий путь доставки вложений, не эквивалентный `send_files` кнопки. Рабочий код, БД, UI, PROD и конфигурация не изменялись.

### 20.1. Какие автоматизации допустимы

Источник перечня — `services/button_automation_types.py`; динамическую доступность интеграций уточняет `services/telegram_automation.py:get_automation_registry()`. `none` в UI означает отсутствие ключа автоматизации (`None`).

| Ключ | Название в настройках | Типы кнопок | Что делает |
|---|---|---|---|
| `none` | Не использовать | `ticket`, `task`, `auto` | Обработчик автоматизации не применяется |
| `send_files` | Отправка файлов | `ticket`, `task`, `auto` | Отправляет прямые и подходящие по условиям материалы |
| `message_only` | Только сообщение | **только `auto`** | Отправляет клиентский текст и завершает автоматику; при ошибке выдачи возможна передача сотруднику |
| `bitrix_deal_phone_lookup` | Расшифровка номера Bitrix | **только `auto`** | По ID сделок ищет телефоны через Bitrix |
| `bitrix_phone_deal_lookup` | Поиск сделки по номеру телефона | **только `auto`** | По одному телефону ищет связанные сделки и ответственных |
| `client_origin` | Откуда клиент | **только `auto`** | По ID сделки возвращает `UF_CRM_MARK` |
| `telegram_group` | Отправка в Telegram-группу | **только `auto`** | Ожидает одно сообщение и копирует его в выбранную зарегистрированную группу |

- Для `ticket`/`task` серверная проверка допускает только отсутствие автоматизации или `send_files`. Для `auto` действуют названные в таблице ключи. UI фильтрует выпадающий список по `workflow_types`, но серверная валидация также обязательна и уже разобрана в разделе 19.4. Разрешение `none` в отдельном вызове проверки зависит от аргумента `allow_auto_none`; не трактовать его как универсально полезный режим «авто без действия».
- Для Bitrix-поиска `available` зависит от заполненного `settings.bitrix_webhook_base`; для `client_origin` — от **другого** параметра `settings.bitrix_deal_mark_webhook_base`. Это индикатор наличия конфигурации, а не успешного соединения с Bitrix. `telegram_group` объявлена встроенной и доступной, но конкретную группу дополнительно проверяют.
- Фактический ключ берётся из актуальной записи `BotButtonSetting` для `Ticket`, а не безусловно из сохранённого в `ButtonSpec` снимка (`resolve_effective_automation_key`). При смене настроек между выбором кнопки и исполнением необходимо учитывать этот факт; стабильность поведения при одновременном редактировании отдельно не проверялась.

### 20.2. Где срабатывает исполнение

1. В `routers/telegram.py` кнопка выбирается через актуальный DB callback (раздел 18); клиент может сначала получить отдельное подтверждение с повторной проверкой его актуальности. Ветви ожидания **Origin**, двух видов **Bitrix** и **Telegram-группы** запускаются специализированными `_begin_*_wait()` до обычного цикла ввода/распределения.
2. Обычные встроенные операции проходят через `_dispatch_builtin_button_automation()`. Для `auto + send_files` отправляются клиентский текст, прямые файлы и файлы по условиям; при успешной прямой отправке вызывается `_complete_auto_ticket()`. Для `auto + message_only` клиентский текст и завершение происходят без набора файлов по механизму `send_files`.
3. Для `task` и связанных сценариев отправка `send_files` вызывается при формировании обращения из первого клиентского описания; для действующей обычной заявки — при **первом клиентском сообщении**, когда до него в заявке не было `TicketMessage` типа `client` (в просмотренном участке `3300–3444`). Это **не** отправка на каждое сообщение. Непосредственное создание по callback и ветви подтверждения также могут вызвать встроенный обработчик; не считать все типы одинаковыми по моменту отправки.
4. `telegram_automation.process_collecting_ticket_automation()` не подменяет обработчики Bitrix/группы: эти случаи пропускаются там как обслуживаемые раньше в `telegram.py`. При неизвестном/неподдерживаемом ключе предусмотрено системное сообщение, а часть дальнейшего пути выполняет обычный intake. Не выводить из наличия функции, что она сама проводит все автоматизации.
5. Отдельные callback результатов (`bitrix_phone:*`, `bitrix_phone_deals:*`, `origin_repeat:*`) проверяют идентичность текущего обращения/сообщения и собственную фазу. Устаревшие кнопки отклоняются. Это отдельные семейства от серверного guard меню (`btnid:/menuid:`).

### 20.3. Откуда берутся файлы и что такое `saved:<uuid>`

- В БД `SavedFile` хранит UUID, `display_filename`, случайный `storage_key`, MIME, размер и время создания; содержимое файла физически размещено под `settings.saved_file_storage_dir`. Путь строит `resolve_saved_file_path()`: он проверяет, что результат остаётся внутри корневого каталога и файл существует. Имя, видимое клиенту, может отличаться от физического имени.
- `services/saved_files.py` реализует создание, безопасное переименование отображаемого имени, замену содержимого, удаление. При замене создаётся **новый** физический файл, выполняется запись и `fsync`, затем commit нового ключа в БД и только после него удаляется старая копия. Это уменьшает риск потери замены, но **не является доказательством общей атомарности** операций с файловой системой и БД. Схема всех API-эндпоинтов управления файлами в шаге 37 не проверялась.
- Значения `BotButtonSetting.files_json` и элементов `conditional_files_json[].files` могут быть вида `saved:<uuid>`. `_resolve_button_file_path()` разрешает их через запись `SavedFile`. Поддерживается и путь **относительно** `BUTTON_CONFIG_DIR/files` для старых материалов, но абсолютные пути и выход за пределы каталога отвергаются. `BUTTON_CONFIG_DIR/files` здесь — источник **вложений**, не меню клиента.
- `bot_button_saved_file_migration.py` адресно переносит **четыре перечисленных в нём исторических PDF** (памятки обучающихся и руководства МПП) в `SavedFile`: использует детерминированные UUID5, копирует байты и переписывает ссылки в прямых и условных массивах на `saved:<id>`. Повторный вызов не должен создавать новые ID для того же имени; при отсутствии исходного файла и сохранённой копии миграция не обещает появление материала. **Уточнение шага 38:** `main.py:on_startup()` действительно вызывает `migrate_legacy_bot_button_pdf_saved_files(db)` после `ensure_saved_files_table()` при успешном запуске API, в одной сессии с `migrate_legacy_bitrix_passwords(db)` и последующим `db.commit()`. Фактический результат миграции в PROD и наличие всех исходных файлов **не проверялись**.

### 20.4. Прямые и условные файлы: проверка и отправка

| Настройка | Хранение | Выполнение в `telegram.py` | Что происходит при ошибке |
|---|---|---|---|
| Прямые файлы | `BotButtonSetting.files_json` | `_resolve_effective_direct_files()` → `_send_button_direct_file()` → `send_document()` последовательно по списку | Возвращает `False` при недопустимом пути, отсутствии файла или исключении Telegram; пишет видимую сотруднику системную запись |
| Файлы по условиям | `BotButtonSetting.conditional_files_json` | `_resolve_effective_conditional_rules()` → `_field_value_for_rule()`/`_match_condition()` → `_send_button_rule_files()` → `_send_file_items()` | Некорректная/недоступная ссылка или сбой Telegram протоколируются в системной записи; цикл продолжается, **общего `False` для fallback не возвращает** |

- Для каждого правила все его условия соединяются логическим **И**; если хотя бы одно не совпало или некорректно, файлы этого правила пропускаются. Между подходящими правилами файлы собираются в общий список; `_send_file_items()` убирает дубликаты **по строке ссылки внутри условного списка**. Прямой список обрабатывается отдельно. Проверены операции совпадения/булевы проверки и числовые `gt`, `lt`, `gte`, `lte`; набор операторов и доступность конкретного поля также контролирует сервер настройки (раздел 19.4).
- Важное различие поведения: у **`auto + send_files` сбой прямой отправки** вызывает `_fallback_auto_to_support()`; в рабочее время автообращение превращается в видимую задачу для распределения, в системную историю попадает причина и контекст автоматизации. **Ошибка только условного файла сама по себе этого fallback не вызывает**: код лишь добавляет запись и продолжает. Для `ticket/task` `_dispatch_builtin_button_automation()` не использует результат `_send_button_direct_file()` как основание для того же auto-fallback.
- В `bot_buttons_files.js` редактор представляет материал как прямой файл **или** набор условных правил для этого файла: при добавлении условия удаляет его из прямого списка; при удалении последнего условного правила файл может вернуться в прямой список. Доступны несколько условий на один файл; форма приводит их к payload для сохранения.
- `bot_buttons_files.js` сравнивает исходную файловую конфигурацию с её представлением в интерфейсе (`hasProjectionLoss()`). Если существующие правила нельзя безопасно восстановить в редакторе, UI защищает от **сохранения с потерей данных**, а не молча удаляет условия. Пикер получает список сохранённых материалов, не принимает произвольный абсолютный путь с компьютера как ссылку кнопки.

### 20.5. Bitrix: две самостоятельные автоматизации телефона

Модуль `telegram_bitrix_phone.py` обслуживает оба ключа; рабочее состояние хранится в `Ticket.quick_action_state_json` отдельно по ключу. При начале сценария `Ticket` остаётся в `collecting`, `load_counted=False`; состояние содержит фазу, `deadline=now()+600` (10 минут), записи об отправках. Истечение времени контролирует `cleanup()`, а не обычный тайм-аут описания задачи.

- **`bitrix_deal_phone_lookup`**: клиент присылает **1–30 уникальных ID сделок Bitrix**, допускаются строки с ID или поддерживаемые строгим разбором ссылки. Пустые строки и повторы не увеличивают лимит; каждая непустая строка обязана пройти `extract_deal_id()`. Данные каждой сделки ищет `get_deal_phone_lookup()`, результат связывает ID и телефон/причину отсутствия. Частичные результаты сохраняются; не найденное в Bitrix и `400 Not found` отделены от технической ошибки. При частичном результате возможно повторно прислать ID без создания новой заявки.
- **`bitrix_phone_deal_lookup`**: клиент присылает **один номер телефона**; `bitrix_phone_deals.normalize_phone()` проверяет формат, затем `lookup()` возвращает связанные сделки и ответственных. При наличии номера сделки в выдаче формируются ссылки на карточки в корпоративном Bitrix. Неизвестный номер не равен техническому отказу сервиса.
- Результат может формироваться как расширенное HTML-представление таблицы; при подтверждённом отказе отправки используется текстовое представление. Большие ответы разбиваются на части; перенос HTML-ссылок учитывается. Есть callback «Закрыть обращение», повторный запрос, при неполном результате/сбое — возможность обращения к сотруднику. Передача происходит **по отдельному действию клиента**, а не автоматически при каждом отсутствии данных.
- Для каждого этапа доставки `deliver()` записывает в БД маркеры `sending/confirmed/failed/uncertain`. При подтверждённом `message_id` повтор этапа не нужен; при **неоднозначном** результате Telegram отправка того же этапа **не повторяется вслепую**, поскольку Bot API не предоставляет используемого здесь idempotency key. Предварительная запись состояния происходит до внешнего HTTP-запроса. Технические обрывы могут оставить обращение ожидающим выбора клиента/восстановления, что принципиально отличается от «ошибка всегда закрывает задачу».
- `handoff()` записывает итоговую системную сводку, сохраняет исходный ввод, результаты и недостающие элементы; в часы приёма переводит `auto` в обычную `task` и запускает распределение. После часов приёма передача сотруднику запрещена, обращение завершается через `_block_automation_handoff()` с соответствующим клиентским ответом. Команды `/start`, `/close`, просроченные callback и повторный запрос имеют отдельные ветви; старый `message_id` не даёт повторно управлять текущим сценарием.

### 20.6. `client_origin`: отдельный webhook без передачи сотруднику

- `telegram_client_origin.py` запрашивает **один ID сделки** через `bitrix_get("crm.deal.get.json", {"ID": ...})`, используя **`bitrix_deal_mark_webhook_base`**, и извлекает `UF_CRM_MARK`. Это не поиск контактов по телефону. Отсутствующая сделка, пустая метка, ошибочный ID и техническая ошибка обслуживаются отдельными текстами/возможностью следующего ввода. `extract_deal_id()` принимает также поддерживаемый формат строгой ссылки Bitrix.
- Ожидание ввода устанавливает дедлайн 600 секунд; `touch()` продлевает его на клиентском действии, а после подтверждённого ответа с меткой можно выбрать «Запрос по другой сделке». До получения явного результата/закрытия у обращения сохраняется собственная фаза. `cleanup()` проверяет дедлайн независимо от общего срока создания обычной задачи.
- Для Telegram-ответа используется сохранение намерения/`message_id` перед завершением. Если результат отправки неоднозначен, автоматизация **не заявляет успешное закрытие** и не отправляет результат безусловно заново. Для повторного нажатия проверяется ID актуальной кнопки; прежние кнопки закрытия отслеживаются отдельно.
- **Принципиальный контракт:** `client_origin` не распределяет задачу сотрудникам ни при штатном результате, ни через общий Bitrix handoff. Это явно обозначено в реализации (`One deal lookup per client attempt; never hands an automation to staff`).

### 20.7. `telegram_group`: регистрация, копирование и восстановление

1. Администратор ES DESK запрашивает временную команду через `POST /api/v1/settings/telegram-groups/registration-code`; код действует **10 минут**, в БД хранится его SHA-256, он привязан к компании, окружению и конкретному Telegram-боту (`getMe`). Список и перепроверка доступны через `GET /api/v1/settings/telegram-groups` и `POST /{id}/check`; маршруты требуют действующего администратора.
2. Администратор Telegram-группы выполняет `/register_group@BotUsername <код>` в настоящей `group/supergroup`. Система исключает служебную группу-архив, проверяет права отправителя, присутствие бота, его возможность писать и отправляет тестовое сообщение. Неудача удаления **тестового** сообщения записывается как предупреждение, а не обязательно откатывает успешную проверку. Группа получает статус `verified` или при последующей проверке `unavailable`; привязка учитывает `environment`, `company_id`, `bot_id`, `chat_id`.
3. На кнопке с `telegram_group` хранится выбранный `telegram_group_id`. После выбора клиенту предлагается прислать **одно сообщение**, не создавая сразу распределённую заявку. `telegram_group_automation.process_message()` сохраняет исходный клиентский текст/вложение и `TelegramUpdate`, устанавливает `intake_state=telegram_group_copy` и **делает commit до** `copyMessage`.
4. Вызов Telegram `copyMessage()` должен подтвердить успешную отправку **положительным целочисленным** `message_id`. Полученная квитанция сохраняется **следующим commit до закрытия** обращения; после этого `finish_confirmed()` закрывает автообращение. Если закрытие прервалось, `recover()` читает сохранённую квитанцию и закрывает без новой пересылки. Клиентское сообщение об успешной передаче отправляется после закрытия; сбой этого уведомления не открывает обращение заново.
5. Если статус копирования **неизвестен** (например, обрыв между Telegram и записью квитанции), повторная пересылка запрещена; `recover()`/обработчик передают обращение на разбор сотрудникам. В этой ветви `auto` переводится в `ticket` — **не в `task`** как телефонный Bitrix handoff. Недоступность группы, неподдерживаемое/слишком большое вложение или ошибка сохранения тоже приводят к ветви handoff. После часов приёма действует общий запрет на передачу: обращение завершается с сообщением о невозможности handoff.
6. Синхронизация одного чата осуществляется `chat_lock()`: в PostgreSQL — session advisory lock на отдельном закреплённом соединении через несколько commit; для SQLite — локальный reentrant lock. Восстановление `recover()` умеет неблокирующую попытку. Это **не гарантия Exactly Once всего Telegram-сервиса**, а защита данного сценария от конкурирующих копирований в описанных ветвях.

### 21.1. Что именно поднимается на старте API

`main.py:on_startup()` вызывает `settings.validate_runtime_guards()`, делает до 20 повторов инициализации схемы при `OperationalError` с паузой 1 сек, запускает `Base.metadata.create_all` **кроме** таблиц `web_chat_messages`, `ticket_number_counter`, `web_client_drafts`, `employee_notification_periods` и `employee_notification_backlog`. Затем последовательно выполняет `ensure_*` для соответствующих колонок/таблиц, миграции старых паролей Bitrix и четырёх PDF кнопок, начальные системные данные, очистку старых integration logs и восстановление незавершённых групповых Telegram-автоматизаций. Это реальные **действия при запуске**, а не read-only диагностика; проверять конфигурацию/миграции перед будущим развёртыванием. Таблицы сотруднического backlog по-прежнему требуют **отдельной предварительной миграции**, они не создаются общей веткой startup.

| Процесс | Условие запуска и периодичность | Назначение |
|---|---|---|
| `telegram_polling_loop` | Только при включённом клиентском polling и наличии token; длинный `getUpdates`, после ошибки сон 3 сек | Клиентские Telegram update; в каждом цикле также cleanup intents и автозакрытие |
| `employee_telegram_polling_loop` | Только при включённом сотрудническом polling и token; после общей ошибки сон 3 сек | Update отдельного бота сотрудников |
| `internal_task_scheduler_loop` | Запускается без проверки Telegram token; после **всей серии** проходов сон 30 сек | Плановые/повторяющиеся внутренние задачи, avatar cleanup, after-hours, авто-offline сотрудников, backlog уведомлений |
| `web_task_cleanup_loop` | Запускается на старте API; сон 30 сек между проходами | Просроченные черновики описаний WEB-задач |
| `call_center_employee_refresh_loop` | Запускается потоком; без webhook обновление не выполняется; ожидание `max(30, BITRIX_KC_REFRESH_INTERVAL_SECONDS)` | Актуализация сотрудника КЦ по внутреннему номеру через Bitrix |

Завершение FastAPI отменяет четыре `asyncio.Task` и останавливает поток обновления КЦ. Задачи `FastAPI BackgroundTasks` для отправки вложений и отдельное трёхсекундное `asyncio.create_task` уведомления об очереди в этой четвёрке **не отслеживаются как постоянная очередь**. Сам факт старта одного loop не доказывает глобальную единственность фонового исполнителя при нескольких процессах API.

### 21.2. Планировщик: общая последовательность, окна и ограничения

`internal_task_scheduler_loop()` последовательно вызывает в отдельных `asyncio.to_thread`: `run_internal_task_scheduler_once`, `run_internal_task_recurring_once`, `run_avatar_cleanup_once`, `run_telegram_after_hours_cleanup_once`, `run_employee_auto_offline_once` и `run_employee_notification_backlog_once`. Каждый блок имеет собственный `try/except`: сбой одного прохода журналируется, следующие всё равно выполняются. После всех вызовов происходит `asyncio.sleep(30)`, поэтому реальные интервалы — **не строго 30 секунд**. Планировщик внутренних задач обрабатывает партии максимум по 50 определений: наступившие одноразовые и рассчитанные повторяющиеся экземпляры с правилами периода/завершения; полнота конкурентной защиты на уровне ограничений БД здесь не проверялась.

В `telegram_after_hours_cleanup.py` один проход берёт до 50 безопасных черновиков `collecting/unassigned` и работает лишь вне времени приёма. Удаление подходящего черновика **коммитится до** попытки Telegram-уведомления. Если уведомление не отправилось, исходное удаление не откатывается и отдельной долговечной очереди повторной отправки из просмотренного пути не следует. Конкретный вызов из scheduler **подтверждён**, что закрывает старый вопрос раздела 7.1; гонки на 19:00 остаются непроверенными.

`auto_close.py` — **другой** механизм: таймер обычной `ticket` на **20 минут после последнего ответа сотрудника**, если последнее видимое сообщение именно от агента, заявка `new/pending`, не `collecting`, не заморожена/особая и нет запрета автозакрытия. При ответе клиента таймер снимается. `cleanup_auto_close_tickets()` запускается из клиентского polling **до** `getUpdates`: закрывает наступившие обращения, пишет системное событие; Telegram-уведомление пытается отправить **до commit закрытия**, а его неудачу фиксирует системой. Для WEB клиентский Telegram-ответ не отправляется. Внешнее сообщение и коммит изменения статуса не составляют одну атомарную транзакцию.

### 21.3. Polling update и отложенное сообщение об очереди

- Клиентский polling хранит `offset` **только в памяти процесса** и ставит `update_id+1` **до вызова** `process_telegram_update`. Если обработчик упал, следующий long poll может подтвердить offset уже пройденного update. Внутреннее хранение `TelegramUpdate` позволяет обнаруживать отдельные повторы, но не доказывает exactly-once или гарантированную обработку каждого события.
- Сотруднический polling перемещает offset после успешного обработчика. Исключение отдельного update логируется и вызывает `continue`; при успешной обработке последующих update курсор может продвинуться дальше пропущенного. Поэтому он тоже не гарантирует автоматическую доставку/обработку каждого сбойного события.
- Если клиентское событие создало обычную `ready/unassigned` заявку, планируется **неотслеживаемая** асинхронная задача с задержкой **3 секунды**. Перед сообщением она повторно проверяет отсутствие назначения, заморозки/закрытия, блокировки контакта и предыдущей отметки. Текст отправляется, затем в БД ставится `distribution_notice_sent_at`. При сбое задачи/процесса уведомление может не появиться, а при сбое фиксации после успешного Telegram-ответа возможна повторная попытка в ином пути; долговечной очереди в этом участке нет.

### 21.4. Низкоуровневый Telegram API: что считает подтверждением

`telegram_bot.py` отправляет запросы Bot API через `urlopen` и обёртки `send_message`, `send_document`, `send_document_by_file_id`, `copy_message`; универсального idempotency key или подтверждённого автоматического retry сетевой отправки нет. `TelegramApiError` маскирует token в ошибках. Для HTML-ответов некоторые обёртки по умолчанию пробуют упрощённый текст после **любой** ошибки, а вариант `retry_only_parse_errors=True` разрешает запасную отправку **только при ошибке разбора HTML**. Сетевой обрыв после фактической отправки остаётся неоднозначным; общий fallback нельзя автоматически считать защитой от дублей. Общая доставка вложений сознательно выбирает `retry_only_parse_errors=True`.

### 21.5. Два слоя: технический архив и доставка клиенту

| Слой | Основные записи/состояния | Где находится файл |
|---|---|---|
| Подготовка / технический архив | `TicketAttachmentPreload`: `status=uploading/ready/failed/cancelled`, `staging_attempt`, `receipt`, `telegram_file_id`, ID сообщения архива | Сначала локально, затем в `settings.telegram_staging_chat_id` через Telegram `sendDocument` |
| Итоговое вложение ответа | `TicketAttachment`: `telegram_delivery_status=uploading/sending/sent/failed`, `delivery_attempt`, `delivery_pending`, подтверждённые ID текстового и файлового сообщений | Архивный `telegram_file_id` повторно используется для отправки клиенту Telegram; в WEB остаётся ссылкой для истории, **без Telegram-отправки клиенту** |

Загрузка бинарного документа в архив защищена **локальным для процесса** семафором на одну одновременную отправку (ожидание по 30 сек, timeout HTTP **300 сек**); это не межпроцессный распределённый семафор. Для архивных групп/альбомов используются `archive_group_id`, отдельное информационное сообщение и временная метка резерва `pending:<preload_id>`. Резерв с проверкой/ожиданием снижает дубли внутри исследованных ветвей, но не доказывает глобальное exactly-once при падении между Telegram и БД.

В `ticket_messages.py` обычный **текстовый** ответ в Telegram отправляется внешне, а затем создаётся `TicketMessage`. Для ответа **с вложениями** сообщение и вложения сначала сохраняются в БД, затем роутер/сервис планирует `FastAPI BackgroundTasks`: `deliver_attachment_preload` либо `deliver_ticket_attachment`. Содержимое может быть caption одного файла при допустимой длине (до 1024 символов), иначе текст идёт отдельно. Для `task` результат/файлы связаны с завершением задачи; WEB-вложения для задачи готовятся в архиве, не высылаются Telegram-клиенту. Внутренний комментарий не является внешним ответом клиенту.

При доставке из архива в Telegram `_deliver_attachment_to_client()` перед **каждым внешним шагом** (текст или файл) сохраняет `delivery_pending=<kind>` и делает commit. Только после положительного `message_id` записывает `sent_text_message_id` / `sent_file_message_id` и очищает pending. Если pending остался без квитанции, следующий проход **не отправляет вслепую**, а фиксирует сбой с системной заметкой; успешную часть комбинированного ответа можно отличить по сохранённому ID. В WEB при наличии архивного `file_id` ставит статус `sent` без Telegram-пересылки клиенту. Это **отказ от автоматических дублей при неопределённости**, но не гарантия доставки каждого сообщения.

### 21.6. Перезапуск, квитанции, повторы и физическая очистка

- `telegram_upload_state.py` сохраняет `staging_attempt`/`delivery_attempt` с token, временем старта и heartbeat. `ATTEMPT_TIMEOUT=360` секунд. Протухший `uploading` может стать `failed`, а при достоверном сохранённом `sent_file_message_id` и отсутствии pending доставка может быть признана `sent`. Квитанция содержит ограниченный набор сведений (в частности, Telegram `file_id`/`message_id` и тип документа/видео); произвольный ответ Bot API не сериализуется как доказательство.
- `recover_ticket_uploads(db, ticket_id)` вызывается при **чтении карточки заявки** из `routers/tickets.py`: восстанавливает/помечает прерванные попытки, синхронизирует данные архива, освобождает уже выгруженные локальные источники, очищает допустимые устаревшие записи. Он **не запускает слепую повторную отправку** вложения или клиентского сообщения.
- `cleanup_stale_attachment_preloads()` удаляет подходящие бесхозные предзагрузки старше **24 часов**, если не привязаны к итоговому вложению/черновику, не защищены активной неистёкшей попыткой и не исключены состоянием ошибки. Вызовы есть в `routers/tickets.py` при операциях с файлами и в восстановлении карточки; это не доказательство независимой глобальной ночной очистки.
- Повтор `retry_preload()` — **явная операция**, а при `uncertain=True` требует дополнительного `confirm_uncertain=True`, поскольку копия уже может существовать в техническом архиве. Старые ID квитанций учитываются при последующей очистке; автоматическое «попробуем ещё раз» после неизвестного результата не предусмотрено.
- `schedule_ticket_upload_delete()` откладывает удаление локальных ресурсов и сообщений технического архива до `SQLAlchemy after_commit`; `after_rollback` сбрасывает список. Перед удалением проверяются ссылки других вложений/предзагрузок. Действия после commit best-effort и **не являются самостоятельным долговечным outbox**: ошибка удаления Telegram/файла не возвращает удалённую запись БД. Схожие хуки очищают ошибочные предзагрузки после закрытия.
- Уведомления сотрудников, регистрируемые через `after_commit` в `ticket_messages.py`, имеют отдельную логику/накопитель из разделов 15 и 17. Нельзя переносить гарантии его backlog на клиентские файлы, авто-close или трёхсекундный queue-notice.

### 21.7. Связанные WEB-задачи и обновление сотрудника КЦ

`web_tasks.py` создаёт WEB-задачи идемпотентно **в пределах своего ключа** (UUID5 из компании, клиента и request ID), использует транзакционную блокировку клиента (PostgreSQL advisory transaction lock или `BEGIN IMMEDIATE` в SQLite), хранит описание/дедлайн в `quick_action_state_json.web_task_intake`. `web_task_cleanup_loop` периодически убирает просроченные ожидания описания; архивы WEB-предзагрузок синхронизируются отдельно после commit. Это часть сквозного WEB-потока, **но не полный аудит WEB UI, auth, chat и history**.

`call_center_employee_resolver.py` поддерживает снимок соответствий «внутренний номер → сотрудник Bitrix» в `CallCenterEmployeeResolverState`, обновляется фоновым потоком и по запросу через single-flight **в пределах одного процесса**. Метод Bitrix — `im.department.employees.get`, список отделов задаётся `BITRIX_KC_DEPARTMENT_IDS` (fallback 60). HTTP 429/5xx и сетевые ошибки могут повторяться согласно `BITRIX_KC_RETRY_COUNT`; плохой JSON/API-ответ не считается повторяемой сетевой ошибкой. При просрочке снимка допускается `stale_fallback_used` только внутри `BITRIX_KC_MAX_STALE_SECONDS`, неоднозначный номер помечается отдельно, а `resolve()` может ждать до `BITRIX_KC_FINAL_WAIT_SECONDS`. **Нет доказанной межпроцессной координации refresh**. Это отдельный фоновой интеграционный механизм, не Telegram delivery.

### 21.8. Матрица реальных гарантий и открытые вопросы

| Операция | Что код фиксирует | Чего нельзя обещать без отдельной проверки |
|---|---|---|
| Клиентский и сотруднический update | Локальный offset, DB-обработка/логирование | Exactly-once; отсутствие пропусков после сбоев |
| Текстовый ответ агента | Telegram send, затем `TicketMessage` | Атомарность внешнего send и DB commit |
| Telegram-вложение | Стадии, попытки, квитанции и запрет слепого повтора | Гарантированную доставку при падении после send и до квитанции |
| Файл WEB | Архивный file ID и статус в БД | Что файл физически доступен в каждом окружении без отдельного smoke |
| Фоновый после-commit cleanup | Защита от удаления разделяемых источников и запуск после commit | Долговечный retry внешнего удаления/уведомления |
| Отложенный queue-notice / after-hours | Проверки текущего состояния, явные send/commit | Гарантированное повторное уведомление при сбое |
| Периодический scheduler / КЦ refresh | Локальные задачи/потоки, статусы и обработка исключений | Глобальный singleton или отсутствие гонок при нескольких воркерах |

**Граница шага 38:** тела тестов доставки, `telegram_attachments.py` с полным путём архивирования *входящих* Telegram-вложений/альбомов, весь WEB-клиент, схема таблиц/индексов и живые проверки не исследовались. Наличие `BackgroundTasks` и записей состояний не даёт права назвать отправку распределённой очередью с гарантированным retry. Следующий самостоятельный крупный проход — **WEB end-to-end**, затем **схема БД, миграции и инварианты**; повторно выгружать уже прочитанные файлы шага 38 не требуется.
