# ES DESK — актуальная архитектура

> **Версия:** 0.2 (обновлено 2026-11-08). **Основание:** первичный обзор исходного кода на ревизии DEV `5d95903`, дополненный проверенными изменениями коммитов `8aec22d` и `8439b32`. Исторические исходные разделы 1–8 сохранены.
>
> **Статус:** документ создаётся заново. Старые `docs/*.md`, `README.md` и `PROJECT_CONTEXT.md` **не являются источниками истины**. Источник — текущий код. Достоверно подтверждённое отделено от ещё не проверенного.

## 1. Назначение и контуры системы

ES DESK — система обработки обращений и внутренних задач с агентским web-интерфейсом, Telegram-каналом и отдельным WEB-клиентом. Код хранится в едином репозитории.

Первично подтверждены три Docker Compose-сервиса (`docker-compose.yml`):

| Сервис | Роль | Где смотреть |
|---|---|---|
| `db` | PostgreSQL 16 | `docker-compose.yml`, `api/app/db.py`, `api/app/models.py` |
| `api` | FastAPI: API, агентские HTML-страницы, статика и фоновые процессы | `api/app/main.py`, `api/app/routers/`, `api/app/services/` |
| `web_client` | Отдельный WEB-интерфейс, сервер на Node.js, проксирование разрешённых WEB-запросов к API | `web-client/`, `web-client/dev-server.mjs`, `web-client/Dockerfile` |

В конфигурации DEV API запускает Uvicorn с `--reload`; в `docker-compose.prod.yml` запуск без `--reload`. Это подтверждает различие команд, **не** подтверждает фактическую конфигурацию работающего PROD.

## 2. Схема взаимодействий (обзор)

```text
Клиенты Telegram ──> Telegram polling / обработка событий ─┐
                                                           │
Сотрудники ──> агентские HTML + JS ──> FastAPI / routers ──> services ──> PostgreSQL
                                                           │
Клиенты WEB ──> web-client (Node) ──> WEB API маршруты ─────┘

Параллельно в API: внутренний планировщик, очистка WEB-задач,
периодическое обновление данных сотрудников контакт-центра.
```

Это логическая схема, а не полное описание сетевых потоков. Подробные пути Telegram-уведомлений, обработку авторизации и внешние интеграции следует отдельно проверить по исходникам.

## 3. Backend: организация и точки входа

- `api/app/main.py` — `FastAPI(...)`, подключение маршрутов (`include_router`), HTTP-страницы, `/static`, запуск/остановка фоновых задач.
- `api/app/routers/` — отдельные маршрутизаторы для заявок, Telegram, WEB, настроек, статистики, управления, уведомлений и интеграций. В инвентаре 33 Python-файла **включая** `__init__.py`.
- `api/app/services/` — сервисная логика, 97 отслеживаемых файлов в первичной инвентаризации.
- `api/app/models.py` — SQLAlchemy-модели; `api/app/db.py` — `Base`, `engine`, `SessionLocal`, `get_db`.
- `api/app/config.py` — настройки; конкретные значения окружений и секреты в документацию не копируем.
- `api/app/static/`, `api/app/templates/` — агентский HTML/CSS/JS-интерфейс.

### Инициализация на старте

В просмотренном `api/app/main.py:on_startup()`:

1. Проверяются runtime guards.
2. `Base.metadata.create_all` вызывается **с выбранным списком таблиц**: на исходной ревизии из него исключены `web_chat_messages`, `ticket_number_counter`, `web_client_drafts`; после коммита `8439b32` дополнительно исключены `employee_notification_periods` и `employee_notification_backlog` (см. раздел 9.2).
3. Выполняется набор `ensure_*` для эволюции схемы и зависимых подсистем.
4. Выполняются адресные миграции старых данных, `ensure_system_seed_data`, очистка журналов интеграций и восстановление незавершённых групповых Telegram-автоматизаций.
5. Условно запускаются polling клиентского и сотруднического Telegram-ботов; запускаются внутренний scheduler и WEB task cleanup; отдельный периодический цикл обновляет данные сотрудников контакт-центра.
6. При shutdown запущенные задачи отменяются/останавливаются.

**Архитектурный риск:** при старте API выполняются операции изменения структуры БД. Полную политику schema evolution ещё не исследовали; не делать вывод о её безопасности или идемпотентности без отдельной проверки.

## 4. Агентский интерфейс и App Shell

HTML-страницы отдаются FastAPI через `FileResponse` из `api/app/templates/` (см. HTML-обработчики в `api/app/main.py`). Статические ресурсы монтируются по `/static`.

`api/app/static/app_shell.js` содержит таблицу внутренних маршрутов, позволяющую переходить между зарегистрированными страницами с частичной заменой `#appContent`. **Подтверждено кодом:** в таблице присутствует `/tickets`, а `dynamicShellRoutes` включает `/tickets/{id}`. Также есть настройки, профиль, статусы, отзывы и management-страницы. При неподходящем маршруте или сбое загрузки до монтажа предусмотрен обычный переход.

Нельзя считать документированный ранее список shell-страниц актуальным. При изменении навигации смотреть непосредственно `app_shell.js`, регистрацию страницы и её cleanup.

## 5. Telegram-канал

В `api/app/routers/telegram.py` и `api/app/services/button_config.py` обнаружены запросы к `BotButtonSetting`, обработка DB-профилей меню, `btnid:` и функции с DB-only-реализацией. Путь `BUTTON_CONFIG_DIR / "files"` используется для файлов.

**Пока не доказано полностью:** отсутствие любых TXT-fallback по всем путям исполнения. Упоминания `legacy`/`fallback` сами по себе не являются доказательством использования TXT-конфигурации. Нужна отдельная адресная проверка runtime.

По ранее рассмотренному и закоммиченному коду (`e9e8852`) внутренний планировщик вызывает `run_employee_auto_offline_once`; это не подтверждает остальные правила Telegram без отдельного исследования.

## 6. Отдельный WEB-клиент

В `web-client/` присутствуют `index.html`, `app.js`, `workspace.js`, `api.js`, файлы оформления, загрузки, истории и черновиков; сервер — `dev-server.mjs`.

Подтверждены реализацией API и allowlist WEB-прокси следующие группы операций:

- WEB-авторизация и меню (`web_auth.py`, `web_menu.py`).
- Создание/продолжение обычной WEB-задачи (`web_tasks.py`), включая предварительную загрузку вложений.
- История обращений (`web_history.py`).
- WEB-чат (`web_chat.py`).
- Результаты задач (`web_task_results.py`).
- Черновики и предварительная загрузка вложений (`web_composer_draft.py`).

**Ограничение вывода:** наличие endpoint и прокси-маршрута не гарантирует полноценную реализацию каждого пользовательского сценария. Эти сценарии документируются отдельно с проверкой сервиса, интерфейса и тестов.

## 7. Хранение данных

`api/app/db.py` использует SQLAlchemy и `settings.database_url`. В `api/app/models.py` обнаружены группы моделей: пользователи/клиенты, заявки/сообщения/вложения, WEB-сессии/чат/черновики/результаты, Telegram-контакты и настройки, внутренние задачи, статистика, отзывы и обратная связь, интеграции и сохранённые файлы.

Связи, внешние ключи, каскады, ограничения и жизненный цикл каждой сущности **пока не документированы**. Их вынесем в `DATABASE.md` после отдельного анализа.

## 9. Изменения, принятые после исходного обзора (локальные коммиты `8aec22d`, `8439b32`)

> **Дата актуализации:** 2026-11-08. Исходные разделы 1–8 являются обзором на ревизии `5d95903`; этот раздел описывает дополнительные механизмы из двух последующих принятых коммитов, не выдавая обзор за полный аудит системы. DEV API пересобран и запущен; PROD не изменялся.

### 9.1. Клиентский Telegram-бот: актуальность меню

Коммит `8aec22d` добавил управление жизненным циклом клиентских inline-меню: удаление предыдущих сообщений с кнопками, проверки устаревших callback на сервере и явные подтверждения. Физическое удаление сообщения Telegram и проверка актуальности callback — независимые защитные механизмы. Основные переходы и блокировку вне часов проверяли на DEV; обычное создание заявки в рабочее время остаётся отдельным сценарием живой проверки. См. `TELEGRAM.md`, раздел 16.

### 9.2. Отложенная доставка сотруднических Telegram-уведомлений

Коммит `8439b32` добавил `api/app/services/employee_notification_backlog.py` и связал его с `employee_telegram_notifications.py`, обработкой callback `employee_telegram_bot.py` и периодическим `internal_task_scheduler.py`. Рабочие часы **этого** механизма — Пн–сб 08:00–19:00 (МСК), воскресенье выходной; клиентский Telegram-приём имеет другой порог открытия (07:50). Вне часов автоматические уведомления накапливаются в PostgreSQL и на следующий рабочий день предлагаются сотруднику; выдача — партиями до пяти с повторным запросом «Да»/«Нет», игнорированные записи очищаются в 19:00 рабочего дня.

Две таблицы:

- `employee_notification_periods` — периоды `(user_id, work_date)`, Chat ID, ID Telegram-сообщения предложения и флаг `offered`.
- `employee_notification_backlog` — записи уведомлений, привязанные к периоду (`period_id`), текст и параметры отправки.

**Особое правило развёртывания:** новые таблицы исключены из общего `Base.metadata.create_all`; вызвать `ensure_employee_notification_backlog_tables()` из `api/app/services/schema_evolution.py` **до старта новой версии API в каждой БД отдельно**. Для DEV миграция выполнена 2026-11-08, обе таблицы проверены. Для PROD — **не выполнена**. Накопитель — специальная очередь для внерабочих уведомлений, **не** транзакционный outbox для всех событий/сбоев Telegram API. Исходный post-commit-поток остаётся отдельным и не гарантирует exactly-once. См. `TELEGRAM.md`, раздел 17.

### 9.3. Счётчик непрочитанных и подтверждение чтения

Система использует существующий `TicketView.last_opened_at` как индивидуальную серверную границу прочтения ответственного сотрудника (роль `agent`/`trainee`). `api/app/services/ticket_reading.py` задаёт единые фильтры допустимых сообщений (клиентские, сотруднические и внутренние комментарии; видимые, не собственные, не системные и не удалённые).

- `api/app/services/ticket_list.py` одним групповым запросом для текущей страницы вычисляет `TicketListItem.unread_count`; общий `list.js` показывает `+N` рядом с заголовком только ответственному агенту/стажёру и обновляет его штатным поллингом списка. Плашка `MAIN` групповой задачи сохраняется.
- `GET /api/v1/tickets/{ticket_id}` отдаёт `unread_message_ids`; **не** продвигает границу прочтения при каждом опросе. При первом просмотре создаётся `TicketView`, но `last_opened_at` инициализируется перед началом истории. Отдельное `first_opened_at` сохраняет факт первого открытия.
- `POST /api/v1/tickets/{ticket_id}/read` принимает ID границы и список показанных сообщений, проверяет ответственное назначение, права и допустимость сообщений на сервере, не допускает пропуска более ранних непрочитанных сообщений и отката границы назад. Администратор своим просмотром не обновляет прочитанность агента.
- `ticket_message_view.js` определяет видимые части сообщений с учётом DOM, длинных блоков, разбитых частей задачи и незагруженных изображений. Чат при открытии показывает короткий непрочитанный блок целиком внизу, а длинный — с первого непрочитанного. Поллинг и чужие сообщения сохраняют позицию; успешная локальная отправка сотрудником переводит чат вниз.

Это изменение затрагивает модель прочтения и клиентский интерфейс, но **не требует новых таблиц/миграций**. `+N` проверен визуально в DEV, API пересобран и работает; целевые Python/UI-тесты прошли. Полный набор регрессий не был полностью зелёным из-за ранее воспроизводимых ошибок тестового окружения/ожиданий, отдельно отмеченных в `DOCUMENTATION_PROGRESS.md`.
