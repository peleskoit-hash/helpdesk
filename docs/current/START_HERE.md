## 1. Как пользоваться — главное правило экономии времени и токенов

1. **Открой этот файл.** Определи область задачи по таблице ниже.
2. **Прочитай один подходящий технический MD** и, только если задача затрагивает соседний контур, второй. Не загружай весь комплект документов «на всякий случай».
3. По указанным исходникам **точечно сверь актуальный код**. Документ описывает состояние на момент исследования, но после новых коммитов может устареть.
4. Валера определяет изменения и ограничения, готовит короткое задание; **Codex выполняет точечный патч**. Codex не должен заново проводить широкий аудит без отдельной задачи.
5. После реализации проверь **реальный `git diff`**, затем разрешённые DEV-проверки; при изменении архитектуры, состояния или важных гарантий обнови соответствующий технический MD.

**Не путать документы:** `START_HERE.md` отвечает **«куда смотреть?»**, тематические MD — **«как устроено?»**, `DOCUMENTATION_PROGRESS.md` — **«что уже исследовано и что осталось?»**, рабочие правила — **«как мы выполняем задачи?»**.

## 4. Правила доверия к документации

- **Источник истины — актуальный код и поведение, подтверждённое разрешёнными проверками.** Наши MD были составлены статическим чтением исходников на отдельных шагах; это не полный live-аудит и не гарантия отсутствия ошибок.
- **Интерфейс ≠ серверные права.** `admin-only`, скрытая кнопка, запрет отправки в JS не доказывают API-авторизацию. Особенно важно для ролей, reset-data, внешних HTTP-источников, saved-files и массовых оповещений (`ADMIN_UI.md`, реестр `AUI-01…AUI-12`).
- **Фоновая операция ≠ exactly-once.** Для scheduler, Telegram delivery, WEB-архивов и внешних POST отдельно учитывать идемпотентность, повтор, commit и конкурентность (`INVARIANTS.md`, `INTERNAL_TASKS.md`).
- **Разные удаления — разные последствия.** Закрытие, архивирование кнопки, hard delete Ticket, удаление recurring definition, замена содержимого файла по ID — самостоятельные контракты.
- Реестры `I-*`, `IT-*`, `UI-*`, `AUI-*` содержат **открытые вопросы**, а не подтверждённый перечень дефектов. Не поручать Codex автоматически исправлять все пункты.
- `ARCHITECTURE.md` и `MODULE_MAP.md` могут помогать как дополнительные исторические указатели, но без адресной сверки с текущим кодом не заменяют перечисленные профильные документы.

## 5. Практический порядок новой разработки

**Валера:** (1) выясняет ожидаемое поведение и границы задачи; (2) выбирает по этой карте 1–2 MD; (3) при необходимости получает **адресные read-only** фрагменты текущих исходников и проверяет `HEAD/status`; (4) описывает риск для соседних механизмов; (5) выдаёт небольшой Codex-промпт с конкретными файлами и запретом побочного рефакторинга.

**Codex:** вносит минимальный патч в согласованную DEV-копию. Не поручать ему широкое повторное discovery, если необходимые факты уже доступны в исходниках/нашей карте; не просить читать `ES_DESK_WORK_RULES_*.md` как обязательный baseline Codex. Технический тематический MD можно назвать **дополнительным контекстом**, но не требовать чтения всех документов.

**После Codex:** проверяем настоящий `git diff` и фактические изменённые файлы; затем — соответствующие разрешённые DEV-тесты, rebuild и smoke по рабочему регламенту; **только после проверки** решаем вопрос коммита. Не считать текстовое резюме Codex доказательством результата. Никаких автоматических изменений PROD.

**PowerShell-регламент:** команды в нашем процессе — одной физической строкой; read-only поиск/диагностика выводятся **в буфер**, а не в консоль. Рабочие правила живут отдельно и имеют приоритет над этим кратким указателем.

## 6. Как начать новый чат, не загружая все MD

| Новый чат | Минимально достаточный набор |
|---|---|
| **Новая задача по коду** | Актуальные правила работы (если не закреплены проектом) + **этот `START_HERE.md`** + конкретная задача. Валера сам выберет нужный профильный документ. |
| Продолжение незаконченного патча | Правила + `START_HERE.md` + **короткая точка остановки**: что изменено, `HEAD/status`, какие проверки уже прошли, что осталось. При необходимости приложить фактический diff. |
| Продолжение документирования | Правила + `START_HERE.md` + **`DOCUMENTATION_PROGRESS.md`**. Он нужен для истории этапов и незаконченных вопросов, **не для каждой обычной правки кода**. |
| Новый чат по узкой сложной области | Правила + `START_HERE.md` + **один** профильный документ (или Валера попросит его после выбора маршрута). |

**Готовая начальная фраза для обычной задачи:**

> Валера, продолжаем ES DESK. Применяй наши рабочие правила и `START_HERE.md` как карту. Задача: [что хотим изменить и какой результат ожидаем]. Сначала определи минимальные исходники и возможные зависимости, потом предложи следующий точечный шаг. Не запускай Codex, сборки или PROD без согласования.

Если чат находится в проекте ChatGPT с уже подключёнными рабочими правилами, не прикладывай тот же файл второй раз. Если в новом чате нет доступа к Windows `docs/current/`, дай нужные файлы вложением или разреши получить их по имени; **само существование пути в документе не означает, что ChatGPT видит твой локальный диск**.
