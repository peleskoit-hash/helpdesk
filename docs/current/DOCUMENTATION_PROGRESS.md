## 1. Принятое решение — важно не потерять

**ВСЯ прежняя проектная документация считается устаревшей по умолчанию.** В ней могут содержаться действующие базовые механизмы, но старые MD-файлы не служат основанием для новых архитектурных утверждений. **Создаём собственную документацию с нуля на основании текущего кода.** Не тратим время на систематическую сверку старых документов; обращаемся к ним лишь как к историческим подсказкам, если необходимо. Старые файлы не удалять и не переписывать.

**Место новой документации в целевом репозитории:** `docs/current/` (новый каталог, старые `docs/*.md` остаются отдельно).

## 3.1. Telegram: пройденные шаги (2026-11-07/08)

На основе шести адресных PowerShell-выгрузок проверено:

1. **Карта модулей:** клиентский и сотруднический polling, основной Telegram-router, onboarding, меню, клиентское закрытие, автоматизации, группы и after-hours сервисы.
2. **Приём update:** `telegram_polling_loop` → `process_telegram_update` → `_process_telegram_update`; SQLAlchemy-сессия на событие; `TelegramUpdate` для обнаружения повторов; отдельные события группы и групповые блокировки. В клиентском polling offset сдвигается до обработки; в сотрудническом после успешной обработки. Гарантии exactly-once не доказаны.
3. **Часы:** `is_telegram_intake_open`: Пн–сб 07:50 включительно–19:00 исключительно МСК, воскресенье закрыто. Повторные проверки на разных стадиях. Исключённые виды автоматизаций не означают разрешения передачи сотруднику после 19:00.
4. **After-hours:** `telegram_after_hours_cleanup.py` выбирает и безопасно удаляет только подходящие незавершённые черновики (партии 50); защитные проверки клиентских сообщений, детей, специальности, автоматизации; commit перед Telegram-уведомлением. Передача автоматизации сотруднику вне часов приёма блокируется отдельно. **Уточнение шага 38:** вызов найден в `internal_task_scheduler_loop()`, серия проходов повторяется после 30-секундного сна, а не по точному cron.
5. **Создание:** `_create_collecting_ticket` создаёт `collecting + unassigned`; `_prepare_collecting_ticket_for_button` выбирает `ticket/task/group_parent/auto`; `_ready_ticket_for_distribution` устанавливает `ready`, номер, данные КЦ и запускает назначение. Отдельный прямой `_ensure_ticket_for_incoming` создаёт `ready` сразу; `_create_task_from_intent` объявлена, но вызовы в просмотренном `api/app` не найдены.
6. **Распределение:** фиксированный из кнопки → forced по `login`/`user_id` → онлайн-agent с минимальной активной нагрузкой, старейшим `last_assigned_at`, затем по ФИО → очередь `unassigned`. Обычный авто-путь требует `role=agent`, `is_active`, `online`; forced допускает активного `agent` или `trainee` без проверки `online` в исследованном сервисе. `GROUP_PARENT` имеет hook при назначении и создаёт нумерованные дочерние `GROUP_CHILD`; источники `assignment.py`, `ticket_numbering.py`, `routers/telegram.py`. Нумерация использует `TicketNumberCounter` и `pg_advisory_xact_lock` в PostgreSQL.

**Подробности и ограничения документированы в `TELEGRAM.md`** (часть 1, не весь Telegram). На текущем шаге `ARCHITECTURE.md` не изменён.

### 3.2. Telegram: шаги 7–11 (2026-11-07/08), контрольная точка v0.3

7. **Клиентский `/start` и обычные сообщения:** `_active_ticket_for_client()` ищет действующую *обычную* заявку, исключая задачи/авто; `_collecting_ticket_for_client()` — отдельный Telegram-черновик. Повторный `/start` с действующей заявкой не создаёт другую; меню для проверенного клиента формируется из профиля, при отсутствии заявки и обязательного выбора типа произвольный текст возвращает `problem_type_required`. Первое подключение использует `process_first_connection_start()` → `_ensure_ticket_for_incoming()` (сразу `ready`). Клиентские сообщения создаются через `_append_client_message()`, с Telegram ID, возможным снятием заморозки и уведомлениями сотрудника.
8. **Первое подключение и `/close`:** подтверждено буквальное условие `needs_onboarding = profile is None or not is_verified or not has_destination`. Показ меню использует `temporary_rop_destination(profile)`, `BotMenuDestinationBinding` и запасное базовое меню; это не просто прямой доступ к `destination`. `client_can_close_ticket()` определяет допуск callback закрытия; команда `/close` обслуживается отдельно. Безопасные черновики могут удаляться, полноценные заявки закрываются с обновлением статистики. Для неназначенных обычных заявок отдельное уведомление без оценки; другие подходящие случаи могут предлагать отзыв.
9. **API ответа и завершения:** `routers/tickets.py:reply()` делегирует в `services/ticket_messages.py:reply_to_ticket()`, а не содержит бизнес-логику целиком. `_send_to_telegram_client()` обрабатывает Telegram HTML с fallback в простой текст. `ticket_lifecycle.py:close_ticket_by_actor()` разделяет обычные заявки, задачи, групповые задачи и админское принудительное закрытие.
10. **Последовательность доставки:** для простого текстового ответа обычной Telegram-заявки сначала внешняя отправка, затем запись `TicketMessage` с `telegram_message_id`; при вложениях сначала запись БД/commit, затем отдельная доставка. Для `task` текст результата обычно сохраняется, а отправка клиенту связана с закрытием. `can_reply`/`can_comment` различаются, `closed` read-only. При ошибке отправки есть отдельная фиксация неудачной доставки. Не заявлять exactly-once или гарантии успеха фоновой доставки.
11. **Закрытие/restore:** сотруднический `POST /{ticket_id}/close` вызывает `close_ticket_by_actor()` и по обычному сценарию требует ответа сотрудника; принудительное закрытие администратором — отдельный маршрут. `POST /{ticket_id}/restore` применим только к закрытой обычной заявке, доступен администратору либо сотруднику, который её закрыл, и запрещён при другой активной обычной заявке этого клиента. Очищаются collecting-черновики, состояния закрытия, отзывов и статистики; клиенту отправляется необязательное уведомление. **Бизнес-правило владельца проекта:** восстановление сохраняет ответственного независимо от online/offline; если восстановил сотрудник — ответственность его, если администратор — он вручную решает вопрос переназначения. Автораспределение при restore не добавлять. У особых заявок есть узкое кодовое исключение: пустой `assignee_id` может быть заполнен из `special_assignee_id`; не подменять этим бизнес-правило обычной заявки.

**Отдельный нерешённый бизнес-вопрос (не исправлять сейчас):** пользователь считает, что галка «Верификация» должна быть допустима только при заполненном подразделении; сначала проверить соответствие полей `destination` / `department` и работу `temporary_rop_destination()`, затем спроектировать проверку на уровне карточки и API. Не добавлять временные хардкодные обходы в Telegram. **Второе уточнение:** `workflow_type=auto` не является обычной заявкой с ответственным; автоматизация обрабатывается системой, а при выполнении условий может перейти в `task` и быть распределена. Не трактовать технический предикат `assignee_id is None` как обязательность ответственного для автоматики.

**Для v0.3 обновлены только `TELEGRAM.md` и этот журнал.** Старые разделы `ARCHITECTURE.md`, `MODULE_MAP.md` не менялись; не считать всю Telegram-подсистему завершённой.

### 3.3. Telegram: шаги 12–15 (2026-11-08), контрольная точка v0.4

12. **Агрегация `GROUP_CHILD` → `GROUP_PARENT`:** при закрытии ребёнка с ответом `_close_group_child_if_ready()` копирует в родителя последний агентский текст и метаданные связанных вложений, если `suppress_client_answer=False`. `_group_parent_children_payload()` предпочитает агрегированные записи родителя; fallback по старым данным читает последние ответы дочерних задач. `finalize_group_parent_if_ready()` завершает родителя лишь при отсутствии открытых детей и с учётом ограничений загрузок.
13. **Формат выдачи клиенту:** обычная задача при закрытии направляет исходное сообщение и последний итоговый ответ/файлы (`telegram.task.completion.with_answer` / `.files_only`); групповая — сводные ответы/файлы (`telegram.group_task.completion.with_answers` / `.files_only`). `ensure_task_uploads_finished()` блокирует закрытие при `uploading`/`sending`, у родителя учитывает дочерние задачи. Наличие файлов в техническом Telegram-архиве не равнозначно доставке клиенту.
14. **Административные операции:** без ответа задачу может принудительно закрыть только администратор, а не обычный сотрудник. Удаление дочерней задачи не удаляет родителя; удаление родителя каскадно удаляет его прямых детей через `_delete_ticket_hard()`. Удаление последнего открытого ребёнка может запустить завершение родителя, если выполнены остальные условия. Массовое удаление родителя и ребёнка предотвращает повторную финализацию/уведомление.
15. **Тесты и cleanup:** в `tests/test_admin_delete_regression.py` прочитаны проверки сохранности агрегированного файла родителя после удаления ребёнка, сохранения открытого родителя при наличии открытого соседа и отсутствия двойных уведомлений; **тесты не запускались**. `schedule_ticket_upload_delete()` планирует физическое удаление локальных/архивных ресурсов на `after_commit`, прежде проверяя ссылки; на `after_rollback` сбрасывает план. Ошибки после commit не откатывают удаление БД.

**Подтверждённое бизнес-правило владельца:** закрытие/удаление подзадачи не должно ломать `GROUP_PARENT` и уничтожать уже агрегированные результаты. Безответное закрытие доступно только администратору принудительно. Полное отсутствие ответов по всем детям — редкий крайний случай; отдельную ветку или новый клиентский текст **не проектировать**, пока не появится конкретная бизнес-потребность. Форматтер «файлы получены» при пустых ответах и пустых файлах отмечен как возможная смысловая неточность, **не дефект, требующий сейчас исправления**.

**Для v0.4 обновляются только `TELEGRAM.md` и `DOCUMENTATION_PROGRESS.md`.** Версии указываются **внутри** документов; имена файлов на скачивание всегда остаются неизменными. `ARCHITECTURE.md` и `MODULE_MAP.md` не меняются. Источник — присланные выдержки исходников и тестов; никаких изменений кода и запусков тестов не было.

### 3.4. Telegram: шаги 16–23 (2026-11-08), контрольная точка v0.5

16. **Структура постзакрывающих действий:** `telegram_post_close.py` содержит независимые механизмы «Оставить отзыв» (`TicketReviewCycle` + `TicketReview`) и «Предложения и замечания» (`TicketFeedbackInput` + `TicketFeedback`); доступность задаёт `available_post_close_actions()`. Оценка — только для обычной закрытой заявки `ticket/normal` с действующим `offered`-циклом; замечание — для закрытых `ticket` или `task`, если ещё нет `TicketFeedback`.
17. **Адресат рейтинга и версии:** сотрудник, который закрыл заявку как `agent/trainee`, либо действующий `ticket.assignee_id` при закрытии администратором/клиентом — и только при роли `agent/trainee`. Рейтинг 1–5 сохраняется уже при выборе звёзд, комментарий необязателен. Новая оценка той же пары `ticket_id+agent_id` переводит старую в историю (`is_current=False`) и увеличивает `version_number`, сохраняя `previous_version_id`. У другого агента своя история.
18. **Обрыв и устаревшие действия:** callback-валидация требует правильного клиента, актуального `review_current_message_id`, состояния цикла, последнего цикла пары и закрытого `ticket`. `/start` после выбранного рейтинга может завершить ожидающий текст цикл без удаления оценки; без выставленного рейтинга незавершённый сценарий отменяется.
19–20. **«Особые» и принятое бизнес-решение:** `_apply_move_to_special()` меняет и `assignee_id`, и `special_assignee_id` на администратора. При закрытии им без допустимого `agent/trainee` `prepare_review_offer_cycle()` не создаёт оценку — **кнопки «Оставить отзыв» нет**. Кнопка предложений/замечаний остаётся, если замечания ещё нет. **Владелец явно решил оставить существующую реализацию:** не искать предыдущего ответственного и не строить новую систему оценки; администраторам оценки не предназначены. Предложения/замечания связаны с заявкой и клиентом, а не сотрудником. Не считать этот случай дефектом и не отправлять Codex на изменения.

- **Три слоя:** `InternalTaskDefinition` хранит шаблон, тип и состояние расписания; `InternalTaskOccurrence` — факт запуска и снимок параметров с уникальным ключом `(definition_id, occurrence_at_utc)`; реальная работа идёт в обычном `Ticket(task/normal, ready)` с техническим клиентом **«Система»**. Технический ID клиента стабилен на компанию (`uuid5`); PostgreSQL advisory transaction lock защищает **его создание**, не весь scheduler. Настройка `display_author` меняет видимое имя заявителя только у внутренних задач, а не `Ticket.client_id`.
- **Способы создания:** `POST /api/v1/management/internal-tasks` создаёт немедленный Ticket/Occurrence и переводит one-off Definition в `finished` в одной транзакции. `POST /scheduled` и `POST /recurring` сохраняют только будущий/циклический шаблон до запуска. Два одинаковых немедленных POST **создают два Ticket**: внешнего idempotency-key нет. При ошибке немедленной материализации определение откатывается.
- **Назначение и права:** все management-маршруты — для администратора своей компании. `direct` допускает `agent/trainee` даже offline, но при материализации требует `is_active=true`; если исполнитель стал невалидным/неактивным/чужой — **только экземпляр** переходит к `distribution`, Definition не меняется. `distribution` использует существующий online-agent selection; без кандидата Ticket остаётся `unassigned`; старую очередь сервис сам массово не распределяет. `responsible_admin` может быть неактивным при выборе, но это не гарантия Telegram-доставки.
- **Даты — важное несовпадение:** при немедленном `POST /` `deadline_at` **без offset трактуется как UTC**, а для scheduled/recurring (`scheduled_for`, `cycle_start_at`, `cycle_end_at`, `deadline_at`) — как **локальное время `settings.app_timezone`**. Значения с offset конвертируются в UTC. Scheduled требует строго будущего времени; recurring допускает исторический старт и catch-up. Recurring-копия дедлайна хранит **фиксированную дату шаблона**; отдельного расчёта дедлайна «от каждого запуска» в изученном коде нет.
- **Календарь и окончания:** поддерживаются `daily`, `selected_weekdays` (ISO 1–7), `weekly`, `monthly` (31→последний реальный день), `every_n_days` (по локальным дням). Нормализация `9.05`→`09:05`, сортировка/дедупликация времени, строгие ключи config. `never` не заканчивается само; `at` включает кандидат точно в момент конца; `count` считает **сохранённые Occurrence**, а не закрытые Ticket. UI-предпросмотр `next_occurrence_at` ограничен горизонтом `366*5` дней.
- **Pause/edit/skip/resume:** `generation_not_before_utc` служит нижней границей: активное редактирование поднимает её до текущего момента, `pause` и `resume` отсекают паузу без ретроспективной генерации, `skip-next` поднимает границу до ближайшего кандидата плюс **1 микросекунда** и не расходует `count`. `finished` после допустимого изменения расписания/лимита может быть возобновлён, если есть будущие срабатывания. `delete scheduled/recurring` — перевод Definition в `disabled`, не hard delete истории.
- **Scheduler:** `internal_task_scheduler_loop` последовательно запускает scheduled → recurring → avatar cleanup → Telegram after-hours cleanup → employee auto-offline → notification backlog, потом **спит 30 секунд**; это период сна, не жёсткий cron. Выборка `batch_limit=50` — **размер одного chunk**, а не максимум за проход: список проходится по порциям с исключением attempted IDs. Отложенные просроченные создаются без lookback cutoff по исходному scheduled timestamp. Recurring после простоя создаёт **все разрешённые пропущенные кандидаты**; каждый в собственной транзакции; ошибка одного кандидата сохраняет прошлые успехи, откладывает следующие даты **той же Definition**, не блокирует другие и допускает retry.
- **Закрытие:** внутреннее происхождение определяется `Occurrence.ticket_id`; обычные `task/normal` без маркера не считаются внутренними. Клиентский Telegram/WEB outbound для внутреннего Ticket подавляется. При штатном закрытии с финальным ответом уведомляется **ответственный администратор из снимка** по сотрудническим настройкам/привязке/рабочим часам. Берутся последний agent-результат и **только имена** его файлов, без отдельной Telegram-пересылки файлов. Force close без ответа — без уведомления; admin normal close с результатом сохраняет автора-исполнителя; сбой уведомления не отменяет `closed`.
- **Разница удаления:** `DELETE /materialized/{ticket_id}` делает реальный hard delete Ticket и связанных данных, но **оставляет `Occurrence`-маркер**. Recurring scheduler **не воссоздаёт** ту же дату, `count` учитывает сохранённый маркер, а `overview JOIN Ticket` удалённый экземпляр не показывает. Прямой вызов материализации на orphan-маркере может выбросить ошибку отсутствия Ticket. Не путать это с `disable` расписания.
- **Гарантии и границы:** DB-уникальность пары Definition/time защищает от дублей **одного запуска** по объявленной модели, но многопроцессный singleton scheduler/глобальное exactly-once не доказаны. Не проверены реальная schema legacy PostgreSQL, DST-gap/fold, долгие массовые catch-up, внешняя идемпотентность POST, полнота overview `limit*2`, retention удалённых экземпляров. Это реестр для согласования, **не список подтверждённых дефектов**.
