# ES DESK — интерфейс сотрудника (STAFF UI)

> **Версия документации:** v0.17, 2026-11-08. **Исследовательский шаг:** 44. **Подтверждённый Windows Git HEAD:** `8439b32`; `git status`: только `?? docs/current/`. **Метод:** статическое чтение двух пользовательских PowerShell-выгрузок полных JS/HTML и вспомогательного CSS; без запуска браузера, тестов, API, БД и без изменения исходного кода. В этом документе слово «делает» означает «реализовано в изученном фронтенд-коде», не подтверждённый live-smoke.

## 1. Назначение и границы

Этот документ описывает **сотруднический** интерфейс ES DESK: переход из списка заявок в карточку, сессию и боковую навигацию, очереди, роль-зависимые действия, таблицу, панель задач, историю, чтение, ответ/комментарий, вложения, профиль клиента и состояние экранов. Это **не** WEB-интерфейс клиента (`WEB.md`), не бизнес-реализация Telegram (`TELEGRAM.md`), не спецификация серверных гарантий (`WORKFLOWS.md`, `INVARIANTS.md`) и не административный редактор настроек.

Получены **полные тексты** 21 файла: `api/app/static/{app_shell.js,app.js,sidebar.js,list.js,status_transitions.js,statuses.js,ticket_api.js,ticket_column_auto_width.js,desk_dialogs.js,error_dialog.js,ticket.js,ticket_controls.js,ticket_composer.js,ticket_message_view.js,ticket_attachments.js,ticket_client_card.js,task_panel_layout.js,ticket_client_card.css}` и `api/app/templates/{index.html,tickets.html,ticket.html}`. Адресно проанализированы реализации ключевых сценариев в shell/sidebar/list/ticket, Controls/Composer/MessageView/Attachments/ClientCard, API helper и шаблонах. Экспорты: `Вставленный текст(20261108-203640).txt` (44А, 12 файлов) и `Вставленный текст (2)(1).txt` (44Б, 9 файлов). Первичный inventory насчитывает **93** файла в `static/` и `templates/`; **72 остальных не предоставлены полностью на этом шаге**. Принимаем исходники и маршруты как свидетельства frontend; соседние API и тесты в рамках шага 44 не перечитывались, а отдельные backend-сведения взяты из задокументированного шага 41.

## 2. Архитектура страницы и входные маршруты

| Маршрут / объект | Роль на экране | Источники |
|---|---|---|
| `/tickets` | Список/очереди, таблица, фильтры, массовые действия, панель задач | `templates/tickets.html`, `list.js` |
| `/tickets/{ticket_id или ticket_number}` | Карточка: клиент, сообщения, композер, действия | `templates/ticket.html`, `ticket.js` |
| `HelpdeskAppShell` | Подгружает HTML следующей страницы, управляет history и жизненным циклом | `app_shell.js` |
| `HelpdeskSidebar` | Общая боковая панель, сессия, роль, счетчики, админ-фильтр, доступность, аватар | `sidebar.js` |
| `TicketApi`, `TicketControls`, `TicketComposer`, `TicketMessageView`, `TicketAttachments`, `TicketClientCard` | Независимые именованные фронтенд-модули карточки, доступные через `window` | соответствующие `.js` |

`app_shell.js` регистрирует `tickets-list` и `ticket-card`, перехватывает подходящие внутренние ссылки, запрашивает HTML через `fetch`, парсит через `DOMParser`, переносит `#appContent` и его `data-shell-page`, загружает нужные JS-модули, вызывает `destroy` прежней страницы и `init` новой, синхронизирует `history.pushState`/`replaceState`, слушает `popstate`. При невозможности частичной навигации предусмотрен переход на полный URL. Это **собственный shell с серверными HTML-шаблонами и обычным JS**, не подтверждённый SPA-фреймворк. Ссылки с иными origin, специальными действиями и скачиваниями не должны перехватываться как локальная навигация.

В карточке `canNavigateAway()` пытается закрыть инлайн-редактор клиента и может заблокировать переход при несохранённых изменениях; обработчик `beforeunload` использует браузерное подтверждение. Для текстового черновика параллельно используется фоновое сохранение, а не общий запрет навигации. Для карточки с HTTP `403/404` показывается ошибка («Нет доступа» / «Тикет не найден») с намерением вернуться к списку после её закрытия. `/tickets/{…}` открывается из строк таблицы по `ticket_number || id`.

`app.js` содержит более ранний компактный набор функций списка/карточки. Фактические изученные shell-маршруты и шаблоны подключают `list.js`/`ticket.js` с разделёнными модулями. **Не использовать `app.js` как доказательство текущего поведения вместо этих модулей**; отдельный legacy-entry в иных контекстах без дополнительного просмотра `main.py` исключать нельзя.

## 3. Общая боковая панель, роли и сессия

Общая панель инициализируется перед экраном (`await HelpdeskSidebar.init()`), читает сессию/пользователя, при необходимости список сотрудников и счётчики, показывает пункты «Нераспределённые», «Активные», «Замороженные», «Закрытые», «Особые», а для администратора также ссылки на настройки, управление, статусы и задачи/регулярки. Ссылка является **навигацией**, а не подтверждением возможности каждого API-действия. В роли `admin` виден выбор сотрудников для фильтрации очередей. Панель отображает статус присутствия `online`, `on_ticket`, `waiting`, `lunch`, `offline`; сохранение идёт через `POST /api/v1/users/me/status` с последующим чтением. Админский preview-переключатель роли и пользователя в `list.js`/`ticket.js` содержит явный `TODO` и ранний `return`; **переключения эффективной роли в этом UI нет**.

Ключевые наблюдения из фронтенда:

| Фактическая роль | Очереди/таблица | Карточка и действия |
|---|---|---|
| `admin` | Видит `unassigned`, `special`, фильтр ответственных, колонку назначения, одиночное/массовое назначение, bulk-действия | Выбор ответственного; принудительное закрытие, удаление, особый статус; прочие кнопки по условиям |
| `agent` | Основные очереди; отсутствие `unassigned`/`special` как вкладок; счётчик непрочитанных у своих заявок | Ответ/комментарий, доступные действия по статусу; подтверждение чтения только для собственных назначенных |
| `trainee` | Основные очереди, панель задач; без админских bulk-действий | Композер доступен фронтендом, однако кнопка обычного закрытия в `ticket_controls.js` видна только `admin/agent`; окончательные права — в API |
| `chiki_piki` | Read-only; `unassigned` виден, `special` скрыт; колонка исполнителя только текстом | Композер, файлы, редактирование клиента и основные действия отключаются/скрываются; детали доступа решает сервер |

**Важно:** элементы скрываются/disable в JS по роли и данным заявки. Это **не авторизационная граница**: API проверяет полномочия самостоятельно. Отдельные backend-правила `admin/agent/trainee/chiki_piki` и `agent_visible` ранее изучены в `WORKFLOWS.md`; не переносить сюда гипотезы о «полной изоляции» закрытых заявок.

`sidebar.js` хранит в памяти и `localStorage` некоторые данные для быстрой отрисовки (`hd_tab_counts`, кэш сотрудников, фильтр `hd_admin_assignee_ids`); периодически обновляет серверную сессию/списки/счётчики. Отложенная/кэшированная отрисовка не равна актуальному результату нового API-запроса.

## 4. Очереди и URL списка

В `list.js` есть ровно пять вкладок и соответствующих GET:

| Вкладка | API | Видимость на интерфейсе |
|---|---|---|
| `active` | `/api/v1/tickets/active` | Основная |
| `unassigned` | `/api/v1/tickets/unassigned` | `admin` и `chiki_piki` в просмотренном коде |
| `special` | `/api/v1/tickets/special` | `admin` |
| `frozen` | `/api/v1/tickets/frozen` | Основная |
| `closed` | `/api/v1/tickets/closed` | Основная |

Состояние адреса: `/tickets?tab=<key>&page=<n>&q=<поиск>`. Значения читаются при входе и `popstate`; переключение вкладки, поиск и сброс поиска возвращают на первую страницу; номер страницы проверяется на целое положительное значение, иначе `1`. Если URL не содержит допустимую вкладку, используется `hd_tab` из `localStorage`, затем `active`. При обнаружении вкладки, скрытой для текущей роли, `applyRoleUi` переключает на `active` и корректирует URL. Для сохранённого фильтра администраторов применяется отдельное состояние sidebar.

`loadTickets()` отправляет `sort=created_at&order=desc&page=N&limit=20`, опционально `query=<q>`, а для администратора на большинстве вкладок — повторяющиеся `assignee_ids`. **Особая очередь `special` глобальная для администраторов и игнорирует выбранных сотрудников**; для `unassigned` список ответственных не применяется. Тело JSON ожидается как `items`, `total`, `pages`, `page`. Поиск **серверный**; текст применяется по Enter в поле, очистка отдельно. Бизнес-состав результата (какие статусы и какие объекты допускаются) определяется API и разбирался в `WORKFLOWS.md`, а не в браузерной фильтрации.

## 5. Таблица заявок и пользовательские настройки

В таблице всегда есть канал (иконка), у администратора — чекбокс выбора. Конфигурируемые колонки: `subject` (обязательная), `requester`, `assignee`, `department`, `type`, `location`, `age`, `created_at`, `last_reply`. По умолчанию: тема, заявитель, исполнитель (если доступен), возраст, дата создания, последний ответ. Настройки колонок, автоширины, цветовых выделений и панели задач читаются/сохраняются через `GET/PATCH /api/v1/users/me/preferences`. Редактор колонок поддерживает добавление, удаление необязательных, перестановку, явную ширину и авторазмер с измерением DOM (`ticket_column_auto_width.js`). В режиме изменения ширин ссылка строки временно блокируется, чтобы не открывать карточку случайно.

**Важное ограничение сортировки.** `sortTickets(state.tickets)` сортирует **только полученные 20 (или меньше) элементов текущей страницы** по выбранному столбцу. API при любой сортировке таблицы всё равно вызывается с фиксированными `created_at/desc`, а не с текущим ключом UI. Следовательно сортировка по заявителю, исполнителю, последнему ответу и т. п. **не является глобальной сортировкой всех заявок** и не меняет распределение объектов между страницами. Ключ и направление сортировки сохраняются в `hd_table_sort_key`, `hd_table_sort_dir`.

Строка содержит ссылку `/tickets/{ticket_number || id}`, бейдж `MAIN` для `task_kind=group_parent`, иконку канала (Telegram/WEB/внутренний), отметку типа/статуса, цветовую схему (если включена), `ticket-row-seen/unseen`, имя заявителя и иногда бейдж `+N` непрочитанных **только** в назначенной текущему `agent/trainee` заявке. Тип/цвет строятся из нескольких измерений `workflow_type`, `task_kind`, `is_internal_task`, `is_special`, `is_frozen`, `status`, а не единого поля `type`. Отображаемая метка групповой задачи в одном UI-ответвлении имеет название «Увольнение»; это буквально наблюдаемый текст, **не универсальная бизнес-классификация** всех групповых задач.

Пагинация имеет Previous/Next и компактную модель номеров с многоточием. Выделение нескольких заявок сохраняется в `Set` до массового действия или смены вкладки; «выбрать все» выбирает **только ID на текущей видимой странице**, а не все найденные в базе.

## 6. Панель задач сотрудника

Для `agent` и `trainee` поддерживается компактная верхняя панель задач, если `task_panel_enabled` в пользовательских preferences. Данные: `GET /api/v1/tickets/task-panel`, с собственными состояниями `loading/ready/error`, ссылками на карточки и выпадающим «Ещё», если места мало. `HelpdeskTaskPanelLayout` распределяет слоты, рассчитывает переполнение/позицию dropdown, обновляется при размере окна и навигации. Панель появляется и в списке, и в карточке; при смене shell-страницы её layout размонтируется и создаётся заново. Не путать эту UI-панель с админским конструктором регулярных внутренних задач (`INTERNAL_TASKS.md`).

## 7. Массовые действия списка и назначения

Массовые элементы доступны **в UI только администратору** при наличии выбранных строк:

| Действие | Запрос фронтенда | Дополнительное поведение |
|---|---|---|
| Назначить / снять | `POST /api/v1/tickets/assign`, `{ticket_ids,assignee_id}` | Доступно также в селекте исполнителя одной строки; после успеха сбрасывает выбранные ID, перезагружает список/счётчики |
| Принудительно закрыть | `POST /api/v1/tickets/admin/close` | Подтверждение и опциональный `skip_client_notification` |
| Заморозить | `POST /api/v1/tickets/admin/freeze` | UI-кнопка активна только на вкладке `active`; показывает агрегаты `frozen/already_frozen/invalid/closed/not_found` |
| Разморозить | `POST /api/v1/tickets/admin/unfreeze` | UI-кнопка на `frozen`; считает пропуски/уже размороженные |
| Удалить | `POST /api/v1/tickets/admin/delete` | Подтверждение, `skip_client_notification`, возможный список `file_delete_warnings` |

После успешного bulk-действия UI очищает выделение и перечитывает список и счётчики. Опция «без ответа клиенту» применяется **только к закрытию/удалению** и очищается при закрытии модального окна. **Не интерпретировать UI-успех как полную атомарность по всем ticket ID, гарантированную Telegram-доставку или автоматическое отсутствие побочных эффектов**; семантика серверных ответов и hard delete описана в `WORKFLOWS.md`. `setStatus()` в `list.js` фактически пустая функция; поэтому текстовые вызовы `setStatus('Готово')` сами по себе **не доказывают видимый toast**.

## 8. Карточка заявки: загрузка и состав

`ticket.js` при входе сначала инициализирует sidebar и текущего пользователя, читает preferences композера, затем параллельно запрашивает:

1. `GET /api/v1/tickets/{id}` — базовая карточка, массив `messages`, `client_profile`, `draft_*`, статусы, назначения, тип/источник, unread IDs, флаги, active attachment preloads;
2. `GET /api/v1/tickets/{id}/client-card-view-config` (`cache: no-store`) — конфигурация блока клиента; при ошибке предусмотрен fallback-вид;
3. отдельно — счётчики вкладок, панель задач и другие пользовательские настройки.

По `templates/ticket.html` расположение — левая колонка «Клиент» с инлайн-редактором, центральная панель с заголовком, метками, сообщениями и композером, правая «Управление заявкой». У кнопки «Назад» используется shell history/back, либо `/tickets` при отсутствии истории. При незагруженной/битой карточке код не должен молча рисовать пустой результат. Полный рендер сообщений делегируется `TicketMessageView`, а при исключении есть упрощённый fallback с сохранением прежнего `scrollTop`. Следовательно продвинутые функции цитирования/вложений в fallback не гарантированы.

## 9. Переписка, чтение, цитаты, редактирование

История отображает `client`, `agent`, `internal` и `system`, автора и время, ссылки из текста, quote-preview, вложения и статусы `edited/deleted`. Удалённые внутренние комментарии **не отображаются**; удалённое обычное сообщение может остаться с пометкой об удалении. Исходное цитируемое сообщение из `internal` или с `message_status=deleted` замещается фразой «Исходное сообщение недоступно». Для первого сообщения о задаче с несколькими файлами отображение может **визуально разбивать** одну запись на отдельные части и переносить начальное описание/назначение в заданный порядок; это не означает создание дополнительных серверных `TicketMessage`.

Контекстное меню на сообщении: «Копировать», для не-`chiki_piki` и не-внутреннего — «Цитировать», для допускаемого к изменению agent/internal — «Редактировать» и «Удалить». UI допускает правку, если автор тот же `agent/trainee` либо роль `admin`, тип `agent/internal`, сообщение не deleted, карточка не closed. Запросы `PATCH/DELETE /api/v1/tickets/{ticket_id}/messages/{message_id}`. При удалении agent-сообщения UI формулирует Telegram-удаление **«если возможно»**, то есть не гарантирует внешнее удаление. Чужие сообщения через UI не редактируются обычным агентом; серверная проверка независима.

**Непрочитанные:** после первичной загрузки read-controller позиционирует ленту к первому непрочитанному, когда это возможно, учитывает догружаемые изображения/видео и скролл. `POST /api/v1/tickets/{ticket_id}/read` отправляется **только** когда текущий `agent`/`trainee` назначен ответственным, документ видим, текстовые/медийные части сообщения фактически вошли в область просмотра и достигнута монотонная последовательная граница unread IDs (при одинаковом timestamp подтверждается группа). Для длинного сообщения проверяется **нижняя граница**, а не просто показ верхушки. Debounce ~180 мс. Ошибка запроса оставляет границу для повтора при следующем реальном просмотре/скролле. **Открытие карточки само по себе не обязано прочитать все сообщения**; нет подтверждения «прочитано при открытии».

## 10. Композер, черновики и быстрые ответы

Два режима — **«Ответ»** (`POST /reply`) и **«Комментарий»** (`POST /comment`). Композер отключается в `closed` и для `chiki_piki`. Можно прикладывать файлы из input, drag-and-drop или paste, цитировать сообщение и использовать быстрые ответы. По умолчанию отправка с `Ctrl+Enter`; при включенной настройке `send_by_enter` — обычный Enter отправляет, Shift+Enter оставляет перенос строки. Preference загружается/сохраняется на сервере через user preferences.

Для текста и выбранного режима предусмотрен **серверный черновик** `PATCH /api/v1/tickets/{id}/draft`. Ввод помечает draft грязным и планирует сохранение через ~400 мс; смена режима запускает его сразу. `draft_revision` предотвращает применение старого серверного состояния поверх более нового известного; пока локальная версия dirty или идёт save, последующее `loadCard()` не перезаписывает композер. Перед отправкой ожидается завершение сохранения. На выходе вызывается best-effort `fetch(..., keepalive:true)`; **не гарантия доставки на всех типах закрытия вкладки**. Позиция курсора сохраняется локально отдельным ключом. После успешной отправки черновик и quote очищаются; при ошибке отправки должны остаться данные для повтора.

Панель «Быстрые ответы»: серверный поиск, навигация стрелками/Enter/Escape, вставка текста в позицию курсора, подкачка связанных сохранённых файлов, переход в редактор быстрых ответов; предусмотрено отложенное применение после перехода между экранами. Разрешения редактора зависят от роли, проверяется `canUseQuickRepliesEditor`. Полный CRUD быстрых ответов и права его API на шаге 44 не перечитаны; подтверждена **интеграция в карточку**, не весь редактор.

## 11. Вложения и путь отправки

`ticket_composer.js` использует предварительную загрузку `POST /api/v1/tickets/{id}/attachment-preloads` с `FormData(file,archive_group_id,upload_id)`, получение статуса через `GET /attachment-preloads/{preload_id}` с polling ~1,5 сек и отмену через `DELETE /attachment-preloads/{id}`. К состояниям UI относятся `browser_uploading`, `uploading`, `ready`, `sending`, `failed`, `cancelled`. При повторной загрузке карточки `active_attachment_preloads` восстанавливает видимые выбранные файлы и polling; `claimed` используется как сигнал уже использованной сервером предзагрузки. Карту предварительно выбранных файлов и сетевые controllers очищают при уходе со страницы. **Наличие объекта предзагрузки не равно успешной доставке вложения клиенту**.

Варианты отправки:

- **Обычная заявка, «Ответ» с файлами:** фронтенд идёт по файлам **последовательно**, в первом запросе передаёт текст/цитату, в последующих пустой текст; использует preloaded ID, если доступен, либо raw файл. На каждый файл выполняется отдельный `POST /reply`; после каждого карточка перечитывается. При частичном успехе несколько запросов могут иметь разные результаты — **нет frontend-атомарности пачки**.
- **Задача, «Ответ» с файлами:** все подготовленные файлы и текст отправляются одним `FormData` на `/reply` с несколькими `preloaded_attachment_id` / raw файлами по допустимому транспорту. UI сообщает, что клиент получит итог после **закрытия** задачи; это согласуется с серверной логикой в `WORKFLOWS.md` и `INTERNAL_TASKS.md`.
- **«Комментарий» с файлами:** FormData-ветка; для неё интерфейс требует готовой предзагрузки и отказывает, если её нет; `POST /comment`.
- **Только текст:** JSON `text`, `quote_message_id` в `POST /reply` или `/comment`.

Кнопка «Закрыть» при одновременной отправке откладывает действие до завершения текущей отправки (`pendingCloseAfterSend`), и UI отключает завершение задачи, пока выявляет активные стадии upload/sending. **Серверные guards `ensure_task_uploads_finished` остаются источником истины**; `ready` и `uploading` различаются и по пути данных, и по пользовательским подписям.

`ticket_attachments.js` создаёт изображения/превью/скачивание через `download_url`, распознаёт PNG/JPEG и стикеры Telegram (`.tgs`, `.webm`, `.webp`), загружает pako/lottie для анимированных `.tgs` по необходимости, поддерживает object URL cache и его очистку, фото клиента с thumbnail→full и таймаутом ~45 сек. Превью изображения можно увеличивать колесом; загрузка и открытие в новой вкладке предоставляются разными кнопками. Состояния внешней доставки (`uploading`, `sending`, `failed`) показываются как подписи у вложения. Внешние CDN-deps и медиа/архив вне проверенного фрагмента **не проходили live-проверку**.

## 12. Профиль клиента: чтение и инлайн-редактор

`TicketClientCard` отрисовывает динамические блоки, их поля и отображение по конфигу `GET /tickets/{id}/client-card-view-config`. Есть fallback-настройка с блоками **Telegram**, **Профиль**, **Отдел**, **Рабочие данные**, **Верификация**; среди системных полей — `telegram_username`, `telegram_display_name`, фамилия/имя, `destination`, `sand_owner`, `sales_group`, `location_type`, `anydesk`, внутренний номер, Bitrix login/password/id и `is_verified`. **Это fallback, а не доказательство именно такого живого состава/порядка полей**: фактический список управляется серверным конфигом, флагами активности/видимости и правилами.

Конфиг поддерживает цвета, сортировку и сворачивание блоков, показ поля в карточке отдельно от редактора, `is_editable`, custom/system fields, select options, а также rule-условия (например `destination=Песок` → показывать `sand_owner`; `destination=Отдел Продаж` → `sales_group`; `location_type=Удалённый` → `anydesk`). Правила могут влиять на видимость, readonly и обязательность; у скрытого/readonly поля значения не отправляются из редактора, если этого требует runtime. Сворачивание блока сохраняется `PATCH /api/v1/users/me/preferences` как `client_card_collapsed_blocks`.

По кнопке редактирования UI получает **свежие** `GET /tickets/{id}/client-profile` и config (`cache:no-store`), затем открывает **инлайн**-форму, фиксирует исходные значения, сравнивает изменения, показывает подтверждение выхода без сохранения. При Save формирует `PATCH /tickets/{id}/client-profile` с фиксированными полями, `custom_fields` и допустимыми системными полями, затем обновляет карточку; пока идёт save элементы редактора блокируются. Отображение Bitrix-пароля имеет маску/отдельный reveal API и автоматическое скрытие; пароль WEB клиента обрабатывает подключаемый `ClientWebCredentials`. Не документировать секреты, не предполагать, что plaintext всегда загружается вместе с карточкой.

**Открытый продуктовый вопрос из прежнего журнала:** желательна ли обязательная `destination` / «подразделение» при `is_verified=true`? В просмотренном fallback нет такого простого прямого guard у checkbox; generic rules могут навязать требования к другим полям. Без точного сопоставления `destination`, `department`, server validation и живого конфига **не утверждать, что правило реализовано или отсутствует целиком**, и не изменять поведение по одному frontend-фрагменту.

## 13. Панель управления заявкой — кнопки и серверные пути

| Элемент | Фронтенд и условия | API |
|---|---|---|
| «Приветствие» | Не `closed`/read-only, не task/auto, допускают время/скрипт и ещё не отправлено | `POST /tickets/{id}/greeting` |
| «Уточнение проблемы» / «Иду к Вам» | После использования greeting, пока quick-action не использован; фиксированные тексты | `POST /tickets/{id}/reply` c `quick_action` |
| «Неверная проблема» | Не read-only/closed, не повторно и не group child; меню GET, выбор конечной кнопки и подтверждение | `GET /problem-menu`, `POST /wrong-problem` `{button_key}` |
| «Заморозить» / «Разморозить» | Не закрытая, не read-only; unassigned нельзя заморозить, можно передать `freeze_until` из `datetime-local` → ISO | `POST /freeze`, `POST /unfreeze` |
| «Закрыть заявку/задачу», «Решил на месте» | Видна `admin/agent`; нет active task uploads; обычное закрытие требует агентского сообщения в UI | `POST /close` |
| «Восстановить» | Closed, только не task/auto, `admin` или `closed_by_user_id=userId`; после успеха cooldown закрытия 10 секунд | `POST /restore` |
| «Таймер авто-закрытия» | Только обычный `ticket`, `ready` (не collecting), не special/closed/read-only | `PATCH /auto-close` `{auto_close_disabled}` |
| «Ответственный» | Селект только `admin` | `POST /api/v1/tickets/assign` |
| «Перенести в особые» | Только `admin`, `ticket/task`, ещё не special/closed | `POST /special` |
| «Принудительно закрыть» / «Удалить» | Только `admin`, подтверждение и флаг «Без ответа клиенту» | `POST /api/v1/tickets/admin/close`, `/admin/delete` |
| «Инструкция» | Отображается при `instruction_text` и роли не `chiki_piki` | Показывает уже полученный текст карточки |

UI имеет `stateActionInFlight` для блокировки одновременных `close/restore/freeze/unfreeze`; после restore есть локальный **10-секундный запрет повторного close**, который не следует принимать за универсальный backend cooldown. Кнопка `close` для `onsite_triggered` переименовывается; это визуальная метка, а не отдельный путь `close`. Для `wrong-problem` после задачи UI может вывести итог о создании корректной заявки и закрытии задачи; семантика подтверждается **сервером**, не только текстом frontend.

**Оговорки:** `hasAnyMessage && hasAgentMessage` в UI проверяет наличие агентского сообщения без полного server-filter статуса `deleted` и без всех backend-условий; сервер может запретить закрытие. UI-возможность `trainee` отправить текст не означает право закрывать. `freeze_until` преобразуется из локального поля браузера в ISO — серверный часовой пояс и срок необходимо сверять отдельно. `setStatus()` в `ticket.js` — пустой stub; не обещать видимого всплывающего сообщения после каждого вызова.

## 14. Обновления, ошибки и освобождение ресурсов

| Контур | Ритм / триггер | Особенности |
|---|---|---|
| `HelpdeskSidebar` | Около **5 сек**, дополнительно window focus / visibilitychange | Не опрашивает при `document.hidden`; обновляет counts/agents/status/session |
| `tickets-list` | Около **5 сек** | `loadTickets({silent:true})`; не опрашивает скрытую вкладку; параллельные загрузки коалесцируются через `pendingLoadOptions`; новые данные могут перестроить таблицу |
| `ticket-card` | Около **3 сек** | `loadCard({silent:true})`; останавливает запросы в hidden и пока открыт редактор клиента; concurrent reload requests объединяются |
| attachment-preloads | Около **1,5 сек** на файл в состоянии upload | Останавливается при `ready/failed/cancelled` и при destroy страницы |
| seen/read | **180 мс debounce** после наблюдения видимых частей | Только для ответственного; при ошибке повторяет при следующем событии |
| draft autosave | **400 мс debounce** после редактирования; мгновенный schedule при смене режима | Keepalive при навигации — best effort |

При выходе с карточки: таймеры/polling, sidebar subscription, слушатели scroll/resize/keydown, reading controller, preloads, Blob object URLs, sticker/Lottie/video, модальные окна и панели очищаются. У списка отключаются resize observer, drag и event controller, sidebar subscription, interval. При `401` фронтенд переводит на `/login`; сетевые ошибки показываются в модалке с возможностью копировать текст (с fallback clipboard). `403/404` первой загрузки карточки — отдельный случай. *Ошибки при silent polling могут не показываться пользователю*, что нельзя трактовать как отсутствие ошибок.
