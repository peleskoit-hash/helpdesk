# ES DESK — WEB-клиент

Отдельный клиент без сборщика и внешних UI-зависимостей. Для локального запуска нужен Node.js 20+; Docker-образ использует Node.js 24 LTS.

- `index.html`, `styles.css` — адаптивная страница и системная светлая/тёмная тема.
- `api.js` — WEB-авторизация и чтение клиентского меню.
- `app.js` — вход, проверка сессии, подключение макета и выход.
- `workspace.js`, `workspace.css` — изолированный клиентский UI-прототип.
- `appearance.js` — локальные настройки оформления по формулам агентского интерфейса.
- `Manrope-Variable.ttf`, `Manrope-OFL.txt` — шрифт агентского интерфейса и его лицензия.
- `dev-server.mjs` — локальная раздача страницы и proxy WEB-авторизации и GET меню.

## Docker DEV

Запускать из корня проекта только новый WEB-контейнер, когда существующий API
уже запущен и healthy:

```powershell
docker compose up -d --build --no-deps web_client
```

`--no-deps` исключает запуск, пересоздание и сборку API/PostgreSQL. При таком
запуске Compose не ждёт healthcheck зависимости: готовность существующего API
нужно проверить заранее (`docker compose ps api`). При обычном запуске сервиса
без `--no-deps` действует `depends_on: service_healthy`, но он может затронуть API.
В рамках этого шага контейнеры не запускаются.

Адрес браузера: **http://127.0.0.1:5173/**, доступ только с этого компьютера.
Внутри контейнера Node слушает `0.0.0.0:5173`, Docker публикует порт исключительно
на `127.0.0.1`. Upstream — `http://api:8000` в сети Compose.
Нет npm install, bind-mount исходников или общего node_modules; контекст сборки
ограничен `web-client/`, в образ копируются сервер, WEB-файлы макета, шрифт и его лицензия.

Остановка только WEB (не использовать `docker compose down`):

```powershell
docker compose stop web_client
```

При необходимости удалить только остановленный WEB-контейнер:

```powershell
docker compose rm -f web_client
```

Конфигурация задаётся отдельными переменными сервиса, реальный `.env` не меняется:

- `WEB_DOCKER_MODE=true` явно разрешает upstream `http://api:8000` и bind на `0.0.0.0`.
  Без режима разрешён только HTTP upstream на `127.0.0.1`, bind — `127.0.0.1`.
- `WEB_CLIENT_PORT=5173` — порт процесса внутри контейнера.
- `WEB_CLIENT_ORIGIN=http://127.0.0.1:5173` — точный адрес браузера для Host/Origin.
  Без переменной используется локальный адрес с портом процесса.
- `WEB_API_ORIGIN=http://api:8000` — внутренний адрес API, не адрес браузера.

Origin не подменяется. Для входа действующий API должен разрешать
`WEB_PUBLIC_BASE_URL=http://127.0.0.1:5173`; если он ещё не настроен, возможен 403.
Изменение `.env`, авторизации и пересоздание API не входят в этот шаг.

## Будущий отдельный PROD

PROD будет отдельной копией проекта на сервере `10.171.1.218`, со своей
конфигурацией и развёртыванием, независимо от DEV. Планируемые адреса:
API `http://10.171.1.218:8000`, WEB `http://10.171.1.218:<отдельный порт>`.
`WEB_CLIENT_ORIGIN` позволяет задать этот браузерный адрес независимо от
внутреннего upstream и порта процесса. Будущий PROD отдельно определит публикацию
порта во внутреннюю сеть и согласованную конфигурацию API/cookie/HTTPS.
Текущий DEV Compose не использует серверный IP или общие с PROD переменные.
`docker-compose.prod.yml` не меняется; PROD сейчас не запускается и не настраивается.

## Изолированный DEV-запуск

Этот способ не меняет действующий DEV API, `.env` или его БД. Нужны два терминала.
Существующий router авторизации запускается с синтетическим клиентом в SQLite memory.

В первом терминале запустить изолированный API на свободном порту 8001:

```powershell
cd c:\users\es\downloads\source\helpdesk; $env:WEB_CLIENT_TEST_API_PORT='8001'; $env:WEB_CLIENT_TEST_ORIGIN='http://127.0.0.1:5173'; .\.venv\Scripts\python.exe -u -c "import runpy; runpy.run_path('tests/web_client_api_fixture.py', run_name='__main__')"
```

Во втором терминале запустить WEB-клиент:

```powershell
cd c:\users\es\downloads\source\helpdesk; $env:WEB_API_ORIGIN='http://127.0.0.1:8001'; node web-client/dev-server.mjs
```

Открыть **http://127.0.0.1:5173/**. Тестовый логин `synthetic`, тестовый пароль
`Synthetic-Web-A1!`. Это вымышленные реквизиты только для изолированной проверки.
Данные исчезнут после остановки fixture. Тестовые часы зафиксированы на 19:00 МСК.
Для остановки нажать Ctrl+C в обоих терминалах. Если 8001 или 5173 занят,
выбрать свободные порты и согласованно изменить обе команды.

## Локальный запуск с существующим DEV API

1. Существующий API должен работать на `http://127.0.0.1:8000`.
2. В конфигурации **этого DEV API** должны быть отдельные адреса:

```dotenv
APP_PUBLIC_BASE_URL=http://127.0.0.1:8000
WEB_PUBLIC_BASE_URL=http://127.0.0.1:5173
```

   `APP_PUBLIC_BASE_URL` остаётся адресом агентского ES DESK и ссылок на заявки.
   `WEB_PUBLIC_BASE_URL` задаёт единственный разрешённый Origin для WEB CSRF.
   Изменение переменных окружения потребует **пересоздания API-контейнера**;
   сейчас менять текущий `.env` и пересоздавать контейнер нельзя. Это отдельный согласуемый шаг.

3. Запустить frontend из корня репозитория:

```powershell
cd c:\users\es\downloads\source\helpdesk; $env:WEB_API_ORIGIN='http://127.0.0.1:8000'; node web-client/dev-server.mjs
```

Открыть **http://127.0.0.1:5173/**. Не заменять `127.0.0.1` на `localhost`.
При запуске без Docker-режима Node-сервер слушает только локальный интерфейс.
Для остановки нажать Ctrl+C в терминале frontend.

Если API работает на другом порту, задать `WEB_API_ORIGIN`, например
`http://127.0.0.1:8001`. Порт frontend задаётся `WEB_CLIENT_PORT`; при его смене
`WEB_PUBLIC_BASE_URL` API должен совпасть с новым публичным origin.

**Текущая настройка до патча:** DEV `.env` содержит
`APP_PUBLIC_BASE_URL=http://127.0.0.1:8000`. Пока `WEB_PUBLIC_BASE_URL` не задан,
сохраняется прежняя WEB CSRF-проверка: `APP_PUBLIC_BASE_URL`, затем адрес запроса,
если оба параметра пусты. Поэтому вход с порта 5173 до применения отдельной WEB-настройки
получит 403. Proxy не подменяет Origin для обхода проверки; параметры staff-авторизации
и адреса в уведомлениях не меняются.

## Cookie и CSRF

Браузер обращается к относительным `/api/v1/web/auth/*` и `/api/v1/web/menu` на origin frontend;
proxy передаёт запросы существующему API. Origin и Sec-Fetch-Site сохраняются,
Host должен точно совпасть с браузерным адресом. Чужой Origin отвергается,
POST без Origin запрещён также на proxy. Серверная CSRF-проверка остаётся обязательной.
CORS не добавляется. Proxy пропускает только WEB-cookie и WEB Set-Cookie;
staff-cookie и произвольный X-Forwarded-For не передаются upstream.

`esdesk_web_session` остаётся HttpOnly, SameSite=Strict и Path=/api/v1/web.
В PROD серверная авторизация требует Secure; этот DEV-сервер не настраивает PROD.
Пароли и токены не сохраняются в browser storage. Поле пароля очищается сразу
после отправки. Пароль может предлагаться менеджером паролей браузера через стандартный autocomplete.

Проверка `/me` выполняется при загрузке и восстановлении страницы из back/forward cache.
Нет фонового polling или регистрации активности. Реальные действия с обращениями
и чат появятся в следующих патчах. Пока открыта страница, без нового
серверного запроса она не узнаёт об истечении сессии; перезагрузка или выход проверяют её заново.

## Адресные проверки

Из корня репозитория:

```powershell
cd c:\users\es\downloads\source\helpdesk; node --test tests/web_client_server.test.js tests/web_client_ui.test.js
```

Тесты используют существующий Playwright (при необходимости `PLAYWRIGHT_MODULE`
содержит путь к пакету, `PLAYWRIGHT_CHANNEL` — канал браузера, по умолчанию msedge).
Для реального HTTP smoke нужен `.venv` с зависимостями API; альтернативный Python
задаётся через `WEB_CLIENT_TEST_PYTHON`. Fixture поднимает существующий router
авторизации с синтетическими данными в SQLite memory, на случайном локальном порту;
пользовательский DEV API и его БД не используются и не перезапускаются.

Адресные серверные тесты не требуют Docker или действующего API: Docker DNS
подменяется только в тесте на изолированный HTTP upstream. Они проверяют режим,
Host/Origin с внешним портом, запрет staff-маршрутов, cookie и защитные заголовки.
Проверка Compose без вывода реальных значений `.env`: `docker compose config --quiet`.

## Клиентский UI-прототип

После обычного успешного WEB-входа открывается макет с колонками 1/3 и 2/3.
На узком экране блоки расположены последовательно. Экран входа сохранён.

Меню слева читается из действующих настроек Telegram и доступно только для просмотра.
Вложенность показана раскрытой; все кнопки disabled, обработчиков действий нет.
Порядок рядов и кнопок, подписи, видимость и цвета соответствуют Telegram.
Переписка независима от меню и остаётся демонстрационной: описание в чате →
«Отправка» показывает локальный пример задачи, «Закрыть обращение» блокирует ввод,
сохраняя переписку; «Новое обращение» после закрытия начинает демодиалог заново.
Уведомления, данные клиента и история — локальные примеры, история открывается в модалке.
Модалки закрываются кнопкой × или Escape.

Кнопка файлов показывает только пример имени; файловый диалог и загрузка отсутствуют.
Демодействия не вызывают API; существующие запросы авторизации работают как прежде.
История содержит фиксированные примеры, новые демодиалоги в неё не записываются.
Переписка сбрасывается при выходе или обновлении страницы. Настройки цвета раздельны
для светлой и тёмной тем и хранятся только до обновления страницы. Кастомных узоров нет.

Оформление перенесено из `api/app/static/desk-v2.css`, расчёт цвета — из `theme.js`;
агентские исходники не изменены. Стиль ограничен `#session-panel`. Используются
стандартный сетчатый фон, Manrope, цвета сообщений и элементы управления ES DESK+.
Свои сообщения расположены справа, ответы поддержки — слева.

Для просмотра в Docker DEV адрес прежний: http://127.0.0.1:5173/ после WEB-входа.
Исходники не подключены bind-mount: уже собранный контейнер автоматически не обновится.
Dockerfile подготовлен для включения новых файлов в будущую сборку. В рамках задачи
rebuild, запуск, перезапуск контейнеров и deploy не выполняются.

## GET /api/v1/web/menu

Защищён существующей WEB-сессией `esdesk_web_session`; `Cache-Control: no-store`.
Параметры выбора клиента/профиля не принимаются: клиент берётся из сессии.
Профиль определяется по ClientProfile.is_verified, temporary_rop_destination,
BotMenuDestinationBinding и available_menu_names, fallback — «Базовое», как в Telegram.
Сборщик меню не требует TelegramContact; требования существующей авторизации сохранены.

Ответ: `{ "menu_type": "Базовое", "rows": [[{ "id": "…", "label": "…", "style": "primary", "children": null }]] }`.
`style`: `primary`, `success`, `danger` или null. `children`: вложенные ряды либо null
для конечной кнопки; group_task остаётся конечным действием, как в Telegram.
Читаются только существующие BotButtonSetting и BotMenuLevelLayout. Служебные тексты,
автоматизации, callback_data, назначения сотрудников и файлы в ответ не включаются.
GET не регистрирует активность и не продлевает сессию. Невалидные сессии обрабатываются
существующей авторизацией; POST и другие методы недоступны.
На frontend предусмотрены загрузка, пустое меню, ошибка и ручной повтор.
Административные API недоступны через клиентский proxy; добавлен только точный GET-маршрут.
